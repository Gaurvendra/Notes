Optional
Video Reference: 
What is the problem for which Optional was introduced?
Methods generally return "null" which indicate value is not present and many times client forgot to add "null" check,
which led to NullPointerException.
In another terms we can say:
Earlier methods does not have a way to tell the clients that response value may or may not exist.
and that forced client to add repetitive null checks across the project to avoid NullPointerException.
Optional<T>:
Introduced in Java8, to solve the above discussed i.e. null-return problem.
API or methods, now can express their intention for ex:
Optional<User> as return type, tells client that -> return value may or may not exist.

Many times, engineer ask questions:
Hey, earlier we used to put If condition for null check, now after using optional, still we are using if condition what's
the advantage?
Advantages:
Clients now do not need to guess, whether return value can be null or not. If they see Optional<T> means developer
is saying, value may or may not exist.
       User findUserById(int id)  // return type does NOT tell caller that null may come
       Optional<User> findUserById(int id)  // API clearly says: value may be absent
Complier force us to handle the Optional return type.
             Optional<User> u = repo.findUserById(1);
             System.out.println(u.getName()); //this does not compile
Null return type do not give us anything, while Optional provide many utility methods to handle the response:
        - isPresent()
         - ifPresent()
         - orElse()
         - orElseGet() 
            etc.….
So, at compile time itself we can avoid mistakes.
