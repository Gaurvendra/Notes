## Why this matters

In 1991 a Patriot missile battery's clock drifted by about a third of a second after 100 hours of running. It counted
time in tenths of a second, and 0.1 has no exact binary form. Stored in a 24-bit register, each tick was off by about
0.000000095 seconds, and the error added up (US GAO report IMTEC-92-26).

The same effect shows up in everyday Java:
- billing code that adds prices in `double` and ends up a paisa out;
- a test that compares doubles with `==` and fails only on some inputs;
- a JavaScript client that silently changes a 64-bit ID.

This lesson explains exactly how `float` and `double` work, so none of these surprise you again.

## TL;DR

<Callout type="tldr">
- `float` (32 bits) and `double` (64 bits) are **IEEE 754 binary floating point**: a sign, an exponent and a fraction,
  like scientific notation in base 2. Java fixes these formats on every platform.
- Most decimal fractions (0.1, 0.7, 0.10 rupees) have **no exact binary form**. Each is stored as the **nearest**
  representable value, so `0.1 + 0.2 == 0.3` is `false`.
- Precision is **relative**: about 7 significant digits for `float`, 15–17 for `double`. Big numbers lose small steps,
  so a `float` counter stops at 16,777,216.
- Division by zero doesn't throw: it gives `Infinity` or `NaN`. **NaN is never equal to anything**, including itself.
- Compare doubles with a **tolerance**, never `==` after arithmetic. Round with `Math.round`, `Math.rint` or BigDecimal,
  knowing how each one rounds.
- For money and other exact decimals, use **`BigDecimal`** created from a `String`. Doubles are right for measurements,
  science, graphics and statistics.
</Callout>

## Mental model

A floating-point number is **scientific notation in base 2**: $4.125 = 1.00001_2 \times 2^2$. It stores three things:
the sign, the power of two (the **exponent**) and the digits after the leading 1 (the **fraction**, also called the
mantissa).

Because the number of digits is fixed, floating-point values are like a ruler whose ticks get twice as far apart in each
power-of-two range. Here is a toy format with only 2 fraction bits:

<FloatSpacing caption="A toy format with 2 fraction bits: 4 values per range. A real float has 8,388,608 values in every range, but the pattern is the same: the gap doubles each time." />

Every range from $2^n$ to $2^{n+1}$ has the **same number** of values. So close to zero the values are dense; far from
zero they are far apart. A number that falls between two ticks is **rounded to the nearest tick**. That is the whole
secret of floating-point error.

## Concept, step by step

### 1. The three fields

A `float` has 32 bits and a `double` 64 bits, split into three fields:

<BitLayout groups={[{ bits: '0', label: 'sign (1 bit)' }, { bits: '10000001', label: 'exponent (8 bits)' }, { bits: '00001000000000000000000', label: 'fraction (23 bits)' }]} caption="4.125f: sign 0 (positive), exponent 129, fraction 00001000…" />

- **Sign**: 0 for positive, 1 for negative.
- **Exponent**: the power of two, stored with a **bias** so that it can be negative without a sign bit. For `float`
  the bias is 127: a stored 129 means $2^{129-127} = 2^2$.
- **Fraction**: the binary digits after the point. Normal numbers always start with `1.`, so that 1 isn't stored: it is
  the **hidden bit**. That gives `float` 24 bits of precision from 23 stored bits.

The value of a normal `float` is:

$$
\text{value} = (-1)^{\text{sign}} \times 1.\text{fraction}_2 \times 2^{\text{exponent} - 127}
$$

### 2. Storing 4.125 by hand

These are the steps from the note, checked by the JVM:

1. **Convert to binary.** $4 = 100_2$ and $0.125 = 0.001_2$ (multiply the fraction by 2 repeatedly: 0.25 → 0,
   0.5 → 0, 1.0 → 1). So $4.125 = 100.001_2$.
2. **Normalise** to the form $1.\text{xxx} \times 2^e$: move the point 2 places left, so $100.001_2 = 1.00001_2 \times 2^2$.
3. **Add the bias** to the exponent: $2 + 127 = 129 = 10000001_2$.
4. **Fill the fields**: sign `0`, exponent `10000001`, fraction `00001` followed by zeros.

Going back: $(-1)^0 \times (1 + 0.03125) \times 2^{129-127} = 1.03125 \times 4 = 4.125$. This number is stored
**exactly**, because it is a sum of powers of two.

### 3. Why 0.7 can't be stored exactly

$0.7$ in binary never ends: $0.1\,0110\,0110\,0110\ldots_2$ (the `0110` repeats forever, like $1/3 = 0.333\ldots$ in
decimal). Normalised it is $1.0110\,0110\ldots_2 \times 2^{-1}$, so the stored exponent is $-1 + 127 = 126$. Only 23
fraction bits fit, so the rest must be **rounded to the nearest** representable value. Java (like IEEE 754) rounds; it
doesn't simply cut the extra bits off.

<JavaExample file="examples/src/main/java/track/floating_point/FloatAnatomy.java" snippet="anatomy" output />

`new BigDecimal(float)` shows the **exact** value that is stored: 0.699999988079071044921875, just below 0.7. The
difference is about 0.000000012, which is why `println` still shows `0.7`: it prints the shortest decimal that identifies
this float.

<Callout type="doubt" title="Where does the note's 0.699707031 come from?">
Working it out by hand with only the first 10 or so fraction bits, and dropping the rest, gives 0.699707031. The real
float keeps 23 bits and rounds the last one, so it is about 25,000 times closer to 0.7. The conclusion is the same:
**0.7 isn't stored exactly**.
</Callout>

### 4. `double`: the same idea with 64 bits

A decimal literal like `19.99` is a `double`. To make a `float` you need the `f` suffix:

<CompileResult case="floating_point/float-literal-without-f" />

| | `float` | `double` |
|---|---|---|
| Bits: sign + exponent + fraction | 1 + 8 + 23 = 32 | 1 + 11 + 52 = 64 |
| Exponent bias | 127 | 1023 |
| Precision (with the hidden bit) | 24 bits ≈ 7 decimal digits | 53 bits ≈ 15–17 decimal digits |
| Largest value | `3.4028235E38` | `1.7976931348623157E308` |
| Smallest normal value | `1.1754944E-38` | `2.2250738585072014E-308` |
| Smallest positive value (subnormal) | `1.4E-45` | `4.9E-324` |
| Every whole number is exact up to | $2^{24}$ = 16,777,216 | $2^{53}$ = 9,007,199,254,740,992 |
| Literal | `1.5f` | `1.5` or `1.5d` |

`double` isn't "more decimal places" of the same thing. It has more fraction bits **and** a much bigger exponent range,
but 0.1 is still not exact in either.

### 5. Precision is relative: the ULP

The gap between a number and the next representable one is called its **ULP** (unit in the last place). `Math.ulp`
returns it:

<JavaExample file="examples/src/main/java/track/floating_point/UlpTable.java" snippet="ulp" output />

At 1.0 a `float` can resolve steps of about 0.0000001, but at 16,777,216 the smallest step is 2. So there is no fixed
number of decimal places: precision is a fixed number of **significant digits**. You'll see the consequences in the
[scenarios](#scenarios).

### 6. Special values: ±0, ±Infinity, NaN and subnormals

Two exponent patterns are reserved:

| Exponent bits | Fraction | Meaning | Example |
|---|---|---|---|
| all 0 | 0 | **±0.0**: there are two zeros | `0.0`, `-0.0` |
| all 0 | not 0 | **Subnormal**: no hidden 1, so tiny values fade out gradually | `Double.MIN_VALUE` = `4.9E-324` |
| 1 … 254 (float) | any | **Normal** number | `4.125f` |
| all 1 | 0 | **±Infinity** | `1.0 / 0` |
| all 1 | not 0 | **NaN**, "not a number" | `0.0 / 0`, `Math.sqrt(-1)` |

Rules worth memorising:
- Floating-point arithmetic **never throws**. Only integer division by zero throws `ArithmeticException`.
- **NaN is unequal to everything, including itself**, and every `<`, `>`, `<=`, `>=` with NaN is `false`. Test with
  `Double.isNaN(x)`.
- `0.0 == -0.0` is `true`, but `1 / -0.0` is `-Infinity`.
- `Double.MIN_VALUE` is the smallest **positive** double, not the most negative one. That is `-Double.MAX_VALUE`.
- Casting NaN to `int` gives `0`, and values too big for `int` **saturate** at `Integer.MAX_VALUE` / `MIN_VALUE`.

### 7. Printing, comparing and rounding

**Printing.** `Double.toString` (used by `println` and `+`) prints the **shortest** decimal that uniquely identifies
the double. That is why `0.1` prints as `0.1` even though it isn't exact. To see the exact stored value, use
`new BigDecimal(x)` or `Double.toHexString(x)` (`0x1.999999999999ap-4` for 0.1).

**Comparing.** After arithmetic, compare with a tolerance. Combine a relative part (which scales with the numbers) and an
absolute part (for values near zero):

$$
|a - b| \le \max(\text{relTol} \times \max(|a|, |b|),\ \text{absTol})
$$

You'll implement exactly this in the [exercises](#exercises). `Double.compare(a, b)` and `Double.equals` are for
**ordering and collections**: they treat NaN as equal to NaN, and `-0.0` as smaller than `0.0`.

**Rounding.** Java has several ways to turn a fractional number into a whole one, and they differ:

| Expression | Result | Rule |
|---|---|---|
| `(int) 3.99`, `(int) -3.99` | `3`, `-3` | Truncate towards zero |
| `Math.round(2.5)`, `Math.round(-2.5)` | `3`, `-2` | $\lfloor x + 0.5 \rfloor$: halves go **up** |
| `Math.rint(2.5)`, `Math.rint(3.5)` | `2.0`, `4.0` | Halves go to the **even** neighbour |
| `Math.floor(-2.5)`, `Math.ceil(-2.5)` | `-3.0`, `-2.0` | Down / up |
| `BigDecimal.setScale(2, RoundingMode.X)` | you choose | `HALF_UP`, `HALF_EVEN`, `DOWN`, `CEILING`, … |

## Under the hood

<details>
<summary>What the JVM and CPU actually do</summary>

- **Every operation rounds once.** For `+`, `-`, `*`, `/` and `Math.sqrt`, IEEE 754 requires the result to be the exact
  mathematical result **rounded to the nearest** representable value (ties to even). So floating point isn't random or
  "approximate": it is exactly specified, and the error comes from rounding at every step.
- **Java is strict everywhere** <VersionBadge since={17} jep={306} />. Older x86 CPUs computed in 80-bit x87 registers,
  so intermediate results could differ between machines unless code was marked `strictfp`. Since Java 17 every
  expression is evaluated in exact `float`/`double` precision on every platform, and javac warns when it sees
  `strictfp`. On x86-64, HotSpot uses the SSE2 registers, which work in exactly these precisions.
- **Bytecode has separate instructions** per type: `fadd`/`dadd`, `fmul`/`dmul`, `fcmpl`/`dcmpg` and so on.
  [Bytecode and dispatch](/lessons/bytecode-and-dispatch/) shows how to read them with `javap -c`.
- **Errors accumulate, and some APIs compensate.** Adding 0.1 ten times rounds ten times.
  `DoubleStream.sum()` uses **compensated (Kahan) summation**, which carries the lost low-order bits along.
  `Math.fma(a, b, c)` computes `a × b + c` with a **single** rounding, which can reveal errors that ordinary arithmetic
  hides:

<JavaExample file="examples/src/main/java/track/floating_point/SummingErrors.java" snippet="sums" />

<JavaExample file="examples/src/main/java/track/floating_point/SummingErrors.java" snippet="fma" />

<Terminal command="java SummingErrors.java" outputFile="examples/src/test/resources/outputs/track/floating_point/SummingErrors.txt" title="Output of both snippets" />

- **`Math` vs `StrictMath`.** `StrictMath.sin`, `log`, `pow`… give bit-identical results everywhere. `Math` versions
  may use faster CPU instructions: each result is within 1 ULP of the exact answer, but the bits may differ between
  platforms (see the `Math` API docs).

</details>

## Myths vs facts

<MythVsFact myth="Stored as a float, 0.7 becomes about 0.699707031, because the extra mantissa bits are cut off." audit="4.19">
The extra bits are **rounded to the nearest** value (ties to even), not cut off. The stored value is
**0.699999988079071044921875** (`new BigDecimal(0.7f)`). The error is about 1.2 × 10⁻⁸, roughly 25,000 times smaller than
the hand calculation suggests. The conclusion still holds: 0.7 is not stored exactly.
</MythVsFact>

<MythVsFact myth="We should generally use BigDecimal instead of float and double." audit="4.21">
Use **BigDecimal for money and exact decimal rules** (prices, tax, interest), created from a `String` or with
`BigDecimal.valueOf`, never with `new BigDecimal(double)`. For measurements, science, graphics, statistics and machine
learning, `double` is correct and much faster. Its tiny relative errors are far below the precision of the input data.
</MythVsFact>

<MythVsFact myth="double works exactly like float, just with more decimal places." audit="4.20">
`double` has more fraction bits (52 vs 23) **and** a wider exponent (11 vs 8 bits, bias 1023). It still can't store 0.1
exactly, and it has the same special values: ±0.0, ±Infinity, NaN and subnormals.
</MythVsFact>

<MythVsFact myth="Floating-point results are random and can differ between machines.">
Every basic operation is exactly specified by IEEE 754: the correctly rounded exact result. Since Java 17 (JEP 306)
every expression gives the **same bits on every platform**. The error is deterministic; it's just not decimal.
</MythVsFact>

<MythVsFact myth="Double.MIN_VALUE is the most negative double.">
It is the smallest **positive** double, `4.9E-324`. The most negative double is `-Double.MAX_VALUE`. For integers,
`Integer.MIN_VALUE` *is* the most negative value, which is why this name catches so many people.
</MythVsFact>

## Doubts cleared

<FaqItem q="If 0.1 isn't exact, why does `System.out.println(0.1)` print `0.1`?">
`Double.toString` prints the **shortest** decimal that converts back to the same double. Many decimals round to that
double, and "0.1" is the shortest of them. The printed text is a label for the stored value, not the value itself. Use
`new BigDecimal(0.1)` to see 0.1000000000000000055511151231257827021181583404541015625.
</FaqItem>

<FaqItem q="Why is `0.1f + 0.2f == 0.3f` true when the double version is false?">
Luck of rounding. In `float` precision, the rounded sum of the rounded 0.1f and 0.2f happens to land on the same float
as the rounded 0.3f. In `double` precision it lands one step higher. It isn't a rule: don't rely on either.
</FaqItem>

<FaqItem q={'Why does `String.format("%.20f", 0.1)` print `0.10000000000000000000` instead of the hidden digits?'}>
Java's `Formatter` starts from the shortest decimal ("0.1") and pads it with zeros. It never shows digits beyond that.
Python's `'%.20f' % 0.1` shows `0.10000000000000000555`. In Java, `new BigDecimal(x)` shows the exact value.
</FaqItem>

<FaqItem q={'Why does `String.format("%.2f", 1.005)` print `1.01`, but `new BigDecimal(1.005).setScale(2, HALF_UP)` gives `1.00`?'}>
The double closest to 1.005 is 1.00499999999999989341858963598497211933135986328125. BigDecimal rounds that exact value,
so it gets 1.00. `Formatter` rounds the shortest decimal "1.005" with HALF_UP, so it gets 1.01. Python's
`'%.2f' % 1.005` prints `1.00`. When rounding matters, do it with BigDecimal first and format the result.
</FaqItem>

<FaqItem q="Is `float` faster than `double`?">
For single calculations on modern 64-bit CPUs the speed is about the same. `float` uses **half the memory**, so it wins
for very large arrays and SIMD code (twice as many values per vector register), as in graphics and machine learning.
For everything else, prefer `double`: the extra precision is free.
</FaqItem>

<FaqItem q="What are subnormal numbers, and do I need to care?">
When the exponent bits are all 0, the hidden 1 disappears and the exponent stays at its minimum, so values shrink
gradually towards zero instead of jumping to it ("gradual underflow"). `Float.MIN_VALUE` (1.4E-45) and
`Double.MIN_VALUE` (4.9E-324) are subnormal. You rarely meet them outside numerical code. On some hardware, maths on
subnormals is much slower.
</FaqItem>

<FaqItem q="Can I use a `Double` as a `HashMap` key?">
It works, because `Double.equals` and `hashCode` use the bit pattern: NaN equals NaN, and `0.0` and `-0.0` are two
different keys. But a key that is the *result of a calculation* rarely matches a stored key exactly. Round to a
`long` or use `BigDecimal` (with `stripTrailingZeros()`, or a `TreeMap`, because of the scale issue) for keys.
</FaqItem>

<FaqItem q="Where does `-0.0` come up, and does it matter?">
From results like `-1.0 / Double.POSITIVE_INFINITY`, `-0.0 * 5`, or rounding a tiny negative number. It keeps the
**sign** of a value that underflowed, which matters for `1 / x` (`-Infinity`), `Math.atan2` and some physics code. It
also prints as `-0.0`, which surprises people in reports: add `0.0` to turn `-0.0` into `0.0`.
</FaqItem>

<FaqItem q="Does the JIT compiler change floating-point results?">
No. Since Java 17 the results of `+ - * /` and conversions are fixed by the language, whether code is interpreted or
JIT-compiled. The only intended variation is in `Math` functions such as `sin` and `pow`: each result is within 1 ULP
of the exact answer, but the bits may differ across platforms. Use `StrictMath` if you need identical bits everywhere.
</FaqItem>

<FaqItem q="Is there a 16-bit float in Java?">
Not as a primitive type. Java 20 added `Float.floatToFloat16` and `Float.float16ToFloat`, which convert to and from the
IEEE 754 half-precision format stored in a `short` (used by ML models and GPUs). JDK 25 also has an **incubating**
`jdk.incubator.vector.Float16` class, which isn't a standard API yet.
</FaqItem>

<FaqItem q="Why can't `BigDecimal` compute 1 / 3?">
The exact answer, 0.333…, never ends, so `divide` without a rounding rule throws `ArithmeticException: Non-terminating
decimal expansion`. Give it a scale and a `RoundingMode`, or a `MathContext` with a precision.
</FaqItem>

## Pitfalls and best practices

| ✅ Do | ❌ Don't |
|---|---|
| Use `BigDecimal` (from a `String`) or `long` minor units for money | Store money in `float` or `double` |
| Compare computed doubles with a tolerance (relative + absolute) | Use `==` after arithmetic |
| Test for NaN with `Double.isNaN` | Write `x == Double.NaN` (always false) |
| Loop with an `int` counter and compute the double | Step a `double` by 0.1 and wait for an exact value |
| Use `double` by default; `float` only for huge arrays or SIMD | Pick `float` "to save memory" for a few variables |
| Use `DoubleStream.sum()` or BigDecimal for long sums | Add millions of doubles in a plain loop and trust every digit |
| Send 64-bit IDs as strings in JSON | Assume a `long` survives a trip through a double (it doesn't above 2⁵³) |
| Give BigDecimal division and `setScale` a `RoundingMode` | Call `divide` without one and get an exception in production |

## Senior lens

<Callout type="senior" title="Explain it to your team in 60 seconds">
"float and double are binary scientific notation. They store the nearest representable value, so decimal fractions
like 0.1 are slightly off, and the error is about one part in 10¹⁶ for double. That's perfect for measurements and
statistics, and wrong for money, where we use BigDecimal with explicit rounding rules. Never compare computed doubles
with `==`, watch out for NaN from division by zero, and send big IDs as strings because JavaScript parses numbers as
doubles."
</Callout>

**Money, end to end.** The code is only one layer:
- **Database**: `DECIMAL(p, s)` / `NUMERIC`, not `FLOAT` or `DOUBLE PRECISION`.
- **JSON**: send amounts and 64-bit IDs as strings, or document a decimal format, because JavaScript clients parse
  numbers into doubles.
- **Rounding policy**: which `RoundingMode`, at which step (per line or per total), and per currency. Make it a written,
  shared decision.
- **Splitting**: ₹100 split three ways must add up to exactly ₹100 (33.34 + 33.33 + 33.33).

**Numerics that scale.**
- Long sums of doubles: `DoubleStream.sum()` compensates rounding errors, and sorting by magnitude before summing also
  helps.
- Tests: `assertEquals(expected, actual, delta)` in JUnit, `isCloseTo(expected, within(delta))` in AssertJ, with a
  delta chosen from the problem's scale.
- Memory: a `double[]` of 100 million values is 800 MB; `float[]` halves that. The Vector API (incubating, JEP 537 in
  JDK 27) processes more floats per instruction.

**Code-review checklist**
- [ ] No `float`/`double` for money; no `new BigDecimal(double)`.
- [ ] No `==` / `!=` between computed doubles; NaN handled where division can hit zero.
- [ ] BigDecimal `divide`/`setScale` always has a `RoundingMode`; `compareTo` rather than `equals` for values.
- [ ] Loops count with integers; accumulations over large data use compensated summation.
- [ ] 64-bit IDs aren't serialised as JSON numbers for browser clients.

## Modern Java

- <VersionBadge since={9} /> `Math.fma(a, b, c)`: fused multiply-add with a single rounding.
- <VersionBadge since={17} jep={306} /> **Always-strict floating point**: `strictfp` is obsolete, and javac warns
  when it sees it.
- <VersionBadge since={19} /> **Shortest `toString`**: `Double.toString` and `Float.toString` now print the shortest
  decimal that identifies the value (JDK-4511638). For example, `2e23` prints as `2.0E23`; before JDK 19 it printed
  `1.9999999999999998E23`.
- <VersionBadge since={20} /> `Float.floatToFloat16` / `Float.float16ToFloat` convert to and from IEEE 754 half precision.
- <VersionBadge preview={25} jep={507} /> <VersionBadge preview={27} jep={532} /> **Primitive types in patterns**:
  `d instanceof float f` matches only when the conversion is **exact**. This is still a preview feature in JDK 27 (see
  the practice section).
- <VersionBadge incubator={25} /> `jdk.incubator.vector.Float16`, a half-precision number type in the Vector API
  incubator module.

<Exercise id="floating_point/Tolerance" difficulty="core" title="Compare doubles safely" needs="`if`, `Math.abs`, `Math.max`" hints={["Handle `a == b` first: it covers equal infinities and `0.0` vs `-0.0`.", "After that, any NaN or infinity means \"not close\".", "`!(tol >= 0)` is true for negative tolerances **and** for NaN, because every comparison with NaN is false."]}>

</Exercise>

## Cheat sheet

<CheatSheet>

| Topic | Remember |
|---|---|
| **Layout** | float 1 + 8 + 23 (bias 127), double 1 + 11 + 52 (bias 1023); value = (−1)ˢ × 1.f × 2^(e − bias) |
| **Precision** | float ≈ 7 digits (24 bits), double ≈ 15–17 (53 bits); `Math.ulp(x)` = gap to the next value |
| **Exact integers** | float up to 2²⁴ = 16,777,216; double up to 2⁵³ ≈ 9.007 × 10¹⁵ |
| **Not exact** | 0.1, 0.2, 0.7, 0.10…: stored as the nearest value; `0.1 + 0.2 = 0.30000000000000004` |
| **See the truth** | `new BigDecimal(x)` (exact value), `Double.toHexString(x)` |
| **Special values** | `1.0/0` → Infinity, `0.0/0` → NaN, `NaN != NaN`, `0.0 == -0.0`, `Double.MIN_VALUE` = 4.9E-324 > 0 |
| **Test for NaN** | `Double.isNaN(x)`; `Double.equals`/`compare`: NaN = NaN, −0.0 < 0.0 |
| **Compare** | `abs(a − b) <= max(rel × max(abs(a), abs(b)), abs)` |
| **Round** | cast truncates; `Math.round` half up; `Math.rint` half even; BigDecimal `setScale(n, RoundingMode)` |
| **Money** | `new BigDecimal("0.10")` / `BigDecimal.valueOf(0.1)`; `compareTo`, not `equals`; `divide(x, scale, mode)` |
| **Literals** | `19.99` is double; `19.99f` float; `1e-3`, `0x1p-3` (hex float = 0.125) |
| **Modern** | strict FP everywhere (17), shortest `toString` (19), float16 conversions (20), primitive patterns (preview) |

</CheatSheet>
