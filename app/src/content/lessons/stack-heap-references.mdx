## Why this matters

A service keeps a `static` map of "recent sessions" to speed up lookups. Nobody ever removes entries, because in a
garbage-collected language memory takes care of itself. Three days later the heap is full, the service spends most of
its time in garbage collection, and then dies with `OutOfMemoryError: Java heap space`. The garbage collector did its
job perfectly: every session was still **reachable** from a static field, so none of them was garbage. Knowing what
lives on the stack, what lives on the heap, and what keeps an object alive is the difference between guessing at
memory problems and reasoning about them.

## TL;DR

<Callout type="tldr">
- Each thread has a **stack** of frames holding **local variables**; all threads share the **heap**, where **every
  object and array** lives (fields and elements included).
- A variable of a reference type holds a **reference** to an object, never the object. `new` creates the object on the
  heap and gives back a reference to it.
- Copying a reference copies the arrow, not the object: two variables can **alias** one object. `==` compares
  references; `null` is a reference to nothing.
- Primitives are on the stack **only** when they're local variables; primitive fields live inside their object on the
  heap, and static fields with their class.
- An object stays alive while it's **reachable** from a GC root (thread stacks, static fields); unreachable objects,
  including cycles, can be reclaimed.
- The JVM has more areas than stack and heap: per-thread pc registers and native stacks, and the shared method area
  (Metaspace in HotSpot).
</Callout>

## Mental model

The heap is a **warehouse** full of boxes (objects). A stack frame is a **clipboard** with the notes a worker needs for
one task: small numbers written directly on it (local primitives) and **shelf labels** that say where a box is
(references). Two clipboards can carry labels for the same box; tearing up a clipboard (returning from a method)
doesn't touch any box. A box with no label anywhere, on any clipboard or on the warehouse's own notice board (static
fields), can be thrown out.

Where it breaks: boxes also carry labels to other boxes (fields that are references), and the warehouse staff (the
garbage collector) can move boxes to other shelves at any time and update every label, so a label is not a fixed shelf
number.

## Concept, step by step

### 1. The JVM's memory areas

The notes start with "2 types of memory: stack and heap". Those are the two you use every day, but the JVM
specification defines several **run-time data areas** (JVMS §2.5):

| Area | Per thread or shared | Holds | Full → |
|---|---|---|---|
| **JVM stack** | per thread | One frame per call in progress: locals, operand stack | `StackOverflowError` |
| **pc register** | per thread | Which instruction the thread is executing | – |
| **Native method stack** | per thread | Frames of native (C) code | `StackOverflowError` |
| **Heap** | shared | Every object and array | `OutOfMemoryError: Java heap space` |
| **Method area** | shared | Class metadata, bytecode, run-time constant pools (HotSpot: **Metaspace**, native memory) | `OutOfMemoryError: Metaspace` |

The JVM also uses native memory the specification doesn't name: the JIT's code cache, garbage-collector structures,
thread stacks themselves, and direct byte buffers. [JVM Memory Areas](/lessons/jvm-memory-areas/) goes deeper.

### 2. Stack vs heap

| | Stack (per thread) | Heap (shared) |
|---|---|---|
| **Holds** | Frames: local variables (primitives and references), parameters, `this` | Objects and arrays, with all their fields and elements |
| **Lifetime** | A frame lives exactly as long as its method call | An object lives while it's reachable, then until the GC reclaims it |
| **Order** | Strictly last in, first out | Allocation is fast and sequential; lifetimes are in any order |
| **Size** | `-Xss` per thread (1 MB by default on 64-bit Linux) | `-Xms`/`-Xmx` for the whole JVM |
| **Shared?** | No: only its thread sees it | Yes: every thread can reach any object it has a reference to |

The notes say heap allocation has "no order". Allocation itself is very orderly: each thread allocates from its own
chunk of the young generation (a **TLAB**) by bumping a pointer, which is about as cheap as pushing a stack frame.
What has no order is **how long** objects live: some die immediately, others survive for hours, which is why the heap
needs a garbage collector while the stack doesn't.

### 3. References

`new Employee()` allocates an object on the heap, runs its constructor and yields a **reference** to it; a variable of
type `Employee` stores that reference (the notes' picture: the variable "holds a reference" to the actual object).

```java title="References.java"
public class References {
    static class Employee {
        int empId;
    }

    public static void main(String[] args) {
        Employee a = new Employee();       // one object on the heap; a refers to it
        Employee b = a;                     // copies the reference: two variables, one object
        b.empId = 42;
        System.out.println(a.empId);        // the same object, seen through a

        Employee c = new Employee();        // a second object
        c.empId = 42;
        System.out.println((a == b) + " " + (a == c));   // == compares references

        a = null;                           // a refers to nothing now; the object is still reachable through b
        System.out.println(b.empId);
    }
}
```

```text output
42
true false
42
```

Three consequences to remember:

- **Assignment copies the reference** (aliasing): changes through one variable are visible through the others.
- **`==` compares references**: "same object?", not "equal content?"; `equals` is for content
  ([The Object Class Contracts](/lessons/object-class-contracts/)).
- **`null`** is a reference to no object. Using it to reach a member throws `NullPointerException`, whose message
  (Java 14+) says exactly what was null.

What a reference *is* inside the JVM is deliberately hidden. It's often a compressed 32-bit value rather than a raw
address, and the garbage collector moves objects and updates every reference to them. That's the difference from C++
pointers the notes compare them with: Java has no address-of operator, no pointer arithmetic, and a reference is always
either `null` or valid; it can't dangle.

### 5. Where primitives really live

"Primitives are stored in the stack" is true only for **local** variables. The rule is simply: a value lives wherever
its variable lives.

| Variable | Where its value lives |
|---|---|
| Local variable or parameter (`int count`) | In the frame, on the stack |
| Instance field (`int empId`) | Inside its object, on the heap |
| Static field (`static int created`) | With its class's `Class` object, on the heap (HotSpot, JDK 8+) |
| Array element (`int[] arr` → `arr[0]`) | Inside the array object, on the heap |
| Local reference (`Employee e`) | The reference in the frame; the object on the heap |

### 6. Reachability: what keeps objects alive

The garbage collector doesn't count references. It starts from **GC roots** (the local variables in every thread's
frames, static fields, and a few JVM-internal references), follows references, and treats everything it can reach as
**live**. Everything else is garbage, whether or not anything points at it: two objects that only reference each other
(an "island of isolation") are collected.

```java title="Islands.java"
public class Islands {
    static class Node {
        Node next;
    }

    public static void main(String[] args) {
        Node a = new Node();
        Node b = new Node();
        a.next = b;
        b.next = a;         // a cycle
        a = null;
        b = null;           // no root reaches the cycle any more: both are garbage
        System.out.println("both nodes are now unreachable");
    }
}
```

```text output
both nodes are now unreachable
```

"Garbage" means **eligible** for collection: the GC decides when, based on allocation pressure. A **memory leak** in
Java is the opposite problem: objects you no longer need but that are still reachable, typically from a static
collection, a cache without eviction or a listener nobody removed.

Stack slots always hold ordinary (strong) references. `WeakReference` and `SoftReference` are **objects on the heap**
that refer to another object in a way the GC may ignore; when it clears one, the variable holding the `WeakReference`
is untouched and `weak.get()` returns `null` (verified). They're covered in
[Soft, Weak & Phantom References](/lessons/java-reference-types/).

Reference fields default to `null`, and calling a method through `null` has no object to run on. Since Java 14 the

</TabItem>
<TabItem label="Anti-pattern → fix: the ever-growing static cache">

```java title="Anti-pattern"
import java.util.HashMap;
import java.util.Map;

class Sessions {
    static final Map<String, Session> RECENT = new HashMap<>();

    static void remember(Session s) {
        RECENT.put(s.id(), s);          // never removed: reachable forever
    }
}
```

A static field is a GC root for as long as its class is loaded, so every session stays reachable and the heap only
grows. Fixes: remove entries when they're done, bound the cache (a size limit or time-based eviction, as caching
libraries such as Caffeine provide), or don't cache at all. Heap dumps (`jcmd <pid> GC.heap_dump`) show which root
keeps the objects alive ([Memory Leaks & Diagnostics](/lessons/memory-leaks-and-diagnostics/)).

</TabItem>
<TabItem label="Edge case: == on objects">

```java title="Identity.java"
public class Identity {
    record Point(int x, int y) {
    }

    public static void main(String[] args) {
        Point p = new Point(1, 2);
        Point q = new Point(1, 2);
        System.out.println((p == q) + " " + p.equals(q));
    }
}
```

```text output

```

Two `new` expressions make two objects, so `==` (same object?) is false, while `equals` (same content?, generated for
records) is true. For strings and wrapper objects this trap looks even more random, because some values are shared:
see [Strings](/lessons/strings/) and [Wrappers & Autoboxing](/lessons/wrappers-boxing/).

## Under the hood

<details>
<summary>How HotSpot lays out and moves objects</summary>

- **Object headers.** Every object starts with a header: a mark word (hash code, lock state, GC age) and a class
  pointer, 12 bytes on a typical 64-bit JVM with compressed class pointers, and 8 with compact object headers
  (experimental in JDK 24 through JEP 450, a product option in JDK 25 through JEP 519, enabled with
  `-XX:+UseCompactObjectHeaders`). Fields follow, padded to 8 bytes
  ([Object Memory Layout](/lessons/object-memory-layout/)).
- **Compressed oops.** With heaps under about 32 GB, HotSpot stores references as 32-bit offsets scaled by 8, saving
  memory; the value in a reference field is then not a raw address at all.
- **TLABs and bump-pointer allocation.** Each thread gets a thread-local allocation buffer inside the young
  generation; allocating is a bounds check and a pointer increment. That's why short-lived objects are cheap.
- **Moving collectors.** Young collections copy live objects out of Eden, and compacting collectors slide objects
  together, so an object's address changes over its life. The collector updates every reference, in frames and in
  objects; Java code never notices.
- **Escape analysis.** When the JIT proves an object never escapes a method, it can replace it with plain local values
  (scalar replacement) and allocate nothing on the heap. The program behaves exactly as if the object existed.

</details>

## Myths vs facts

<MythVsFact myth="Java has two kinds of memory, the stack and the heap." audit="9.1">
Those are the two you meet most, but the JVM specification defines more run-time data areas: per-thread pc registers
and native method stacks, and the shared method area (HotSpot's Metaspace) with the run-time constant pools. The JVM
also uses other native memory (code cache, GC structures, direct buffers).
</MythVsFact>

<MythVsFact myth="Primitives are stored on the stack, objects on the heap." audit="9.3">
Only **local** primitives live on the stack. A primitive field lives inside its object on the heap, a static field with
its class, and array elements inside the array (audit 6.11 says the same about the notes' wrapper page).
</MythVsFact>

<MythVsFact myth="The stack stores strong, weak and soft references." audit="9.4">
Stack slots always hold ordinary (strong) references. `WeakReference`, `SoftReference` and `PhantomReference` are
objects on the heap; "weakly reachable" describes how the GC can reach the object they refer to, not what a stack slot
holds.
</MythVsFact>

<MythVsFact myth="There is no order when the heap allocates memory." audit="9.8">
Allocation is sequential and fast: bump-the-pointer inside each thread's TLAB. What's unordered is object **lifetime**,
unlike the strictly nested lifetimes of stack frames.
</MythVsFact>

<MythVsFact myth="A Java reference is the object's memory address, like a C++ pointer." audit="6.4">
It plays a similar role (sharing access to an object), but it's opaque: often a compressed value, updated when the GC
moves the object, with no address-of, no arithmetic, and no way to dangle. It's always `null` or a valid object.
</MythVsFact>

## Doubts cleared

<FaqItem q="Does `new` always allocate on the heap?">
In the language model, yes: objects and arrays are heap objects. The JIT may optimise away allocations it proves are
local to a method (escape analysis), but you can't observe the difference from Java code.
</FaqItem>

<FaqItem q="Is the stack faster than the heap?">
Allocating a frame and allocating an object in a TLAB are both a pointer bump. The real differences are lifetime
(frames vanish automatically, objects need a GC) and sharing (stacks are private to a thread).
</FaqItem>

<FaqItem q="Where do local variables of an instance method live?">
In the method's frame on the stack, like any local; `this` is one of them (slot 0). The object `this` refers to is on
the heap.
</FaqItem>

<FaqItem q="When is an object actually removed?">
When a garbage collection that looks at its region runs after it became unreachable. That depends on allocation
pressure and the collector; you can't rely on timing. `System.gc()` is only a request.
</FaqItem>

<FaqItem q="Do two objects that reference each other leak?">
No. Java's collectors trace from roots instead of counting references, so a cycle that no root reaches is garbage.
Leaks come from objects that **are** still reachable but no longer needed.
</FaqItem>

<FaqItem q="Can I get an object's address in Java?">
Not through the language. `System.identityHashCode` is an identity-based hash, not an address, and addresses change
when the GC moves objects anyway.
</FaqItem>

<FaqItem q="Why is the String pool mentioned in memory diagrams?">
String literals refer to shared `String` objects kept in a pool, which is part of the heap since Java 7. That sharing
is why `==` sometimes "works" for strings ([Strings](/lessons/strings/)).
</FaqItem>

<FaqItem q="What makes a thread stack big or small?">
`-Xss` sets the maximum per platform thread; the memory is reserved up front and committed as the stack grows.
Thousands of platform threads therefore reserve a lot of address space. Virtual threads avoid that: while one is
parked, its frames are kept as objects on the heap, sized to what it actually uses.
</FaqItem>

## Pitfalls and best practices

| ✅ Do | ❌ Don't |
|---|---|
| Copy collections and arrays when you need independence | Assume `b = a` makes a copy |
| Compare content with `equals`, identity with `==` | Use `==` to compare objects' content |
| Share immutable objects freely | Share mutable objects without meaning to |
| Bound or evict anything kept in a static collection | Cache "forever" in a static map |
| Think in reachability from roots when debugging memory | Hunt for "objects nobody points to" |
| Initialise reference fields or document when they may be null | Let `null` spread and add checks everywhere |

## Senior lens

<Callout type="senior" title="Explain it to your team in 60 seconds">
"Locals live in their thread's stack frame and vanish when the method returns. Every object lives on the shared heap,
and variables only hold references to it, so assignment shares objects and `==` compares identity. The GC keeps
whatever is reachable from thread stacks and static fields and reclaims the rest, cycles included. So a Java memory
leak is always 'something still reachable that shouldn't be': a static map, a cache, a listener. Heap dumps show which
root holds it."
</Callout>

**Memory problems and where they come from**

| Symptom | Likely cause | First step |
|---|---|---|
| `OutOfMemoryError: Java heap space`, heap grows steadily | A leak: objects kept reachable (statics, caches, listeners) | Heap dump, look at dominators and GC-root paths |
| High GC time, short-lived objects everywhere | High allocation rate in hot code | Allocation profiling (JFR, async-profiler) |
| `StackOverflowError` | Unbounded or deep recursion | Stack trace: repeating frames |
| `OutOfMemoryError: Metaspace` | Class-loader leak (redeploys, dynamic proxies) | Class histogram, loader analysis |
| Surprising shared changes | Aliasing of mutable objects | Look for missing copies at API boundaries |

**Code-review checklist**
- [ ] No static collections without a clear bound or removal.
- [ ] Mutable objects passed across boundaries are copied or deliberately shared (and documented).
- [ ] Object comparisons use `equals`, not `==`, unless identity is really meant.
- [ ] Reference fields are initialised or clearly nullable.

```java title="Point.java (solution)"
package track.stack_heap_references;

/** Reference solution for the Point exercise. */
public final class Point {
    private int x;
    private int y;

    public Point(int x, int y) {
        this.x = x;
        this.y = y;
    }

    public int x() {
        return x;
    }

    public int y() {
        return y;
    }

    public void moveBy(int dx, int dy) {
        x += dx;
        y += dy;
    }

    public Point copy() {
        return new Point(x, y);                      // a new object on the heap
    }

    public boolean sameObjectAs(Point other) {
        return this == other;                        // identity: the same reference
    }

    public boolean sameValuesAs(Point other) {
        return other != null && x == other.x && y == other.y;
    }

    public static Point[] shallowCopy(Point[] points) {
        return points.clone();                       // a new array; the elements are the same references
    }

    public static Point[] deepCopy(Point[] points) {
        Point[] out = new Point[points.length];
        for (int i = 0; i < points.length; i++) {
            out[i] = points[i] == null ? null : points[i].copy();
        }
        return out;
    }
}
```

```java title="Reachability.java (solution)"
package track.stack_heap_references;

import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.Collection;
import java.util.Deque;
import java.util.HashSet;
import java.util.List;
import java.util.Map;
import java.util.Set;

/** Reference solution for the Reachability exercise. */
public final class Reachability {

    private Reachability() {
    }

    public static List<Integer> reachable(Map<Integer, List<Integer>> heap, Collection<Integer> roots) {
        List<Integer> out = new ArrayList<>(mark(heap, roots));
        out.sort(null);
        return out;
    }

    public static List<Integer> garbage(Map<Integer, List<Integer>> heap, Collection<Integer> roots) {
        Set<Integer> live = mark(heap, roots);
        List<Integer> out = new ArrayList<>();
        for (Integer id : heap.keySet()) {
            if (!live.contains(id)) {
                out.add(id);
            }
        }
        out.sort(null);
        return out;
    }

    /** The mark phase: an explicit stack, so the depth of the heap doesn't matter. */
    private static Set<Integer> mark(Map<Integer, List<Integer>> heap, Collection<Integer> roots) {
        Set<Integer> marked = new HashSet<>();
        Deque<Integer> todo = new ArrayDeque<>();
        for (Integer r : roots) {
            if (!heap.containsKey(r)) {
                throw new IllegalArgumentException("root " + r + " is not in the heap");
            }
            todo.push(r);
        }
        while (!todo.isEmpty()) {
            Integer id = todo.pop();
            if (marked.add(id)) {
                for (Integer next : heap.get(id)) {
                    if (!marked.contains(next)) {
                        todo.push(next);
                    }
                }
            }
        }
        return marked;
    }
}
```

```java title="MiniHeapTest.java"
            return null;

            if (r != null && seen.add(r)) {
                todo.push(r);
            }

        int words = 0;
        while (!todo.isEmpty()) {
            Obj o = todo.pop();
            words += o.size();
            for (Obj t : o.refs) {
                if (t != null && seen.add(t)) {
                    todo.push(t);
                }
            }

            } else {
                visit(roots[k], heap.root(k), seen, todo);

                    assertThat(target).isEqualTo(-1);
                } else {
                    visit(o.refs[s], target, seen, todo);
                }
            }

        return seen;

    private static void visit(Obj o, int address, Map<Obj, Integer> seen, Deque<Obj> todo) {
        Integer known = seen.get(o);
        if (known == null) {
            assertThat(seen.containsValue(address)).as("address %d holds two different objects", address).isFalse();
            seen.put(o, address);
            todo.push(o);
        } else {
            assertThat(address).as("the same object must have one address").isEqualTo(known);
```

```java title="MiniHeap.java (solution)"
package track.stack_heap_references;

import java.util.ArrayDeque;
import java.util.Arrays;
import java.util.Deque;

/** Reference solution for the MiniHeap exercise. */
public final class MiniHeap {

    public static final int ROOTS = 8;
    private static final int HEADER = 2;                 // [0] reference count, [1] data words

    private final int[] memory;
    private final int[] roots = new int[ROOTS];
    private int top;                                     // the bump pointer: the next free word

    public MiniHeap(int capacity) {
        if (capacity < 0) {
            throw new IllegalArgumentException("negative capacity: " + capacity);
        }
        memory = new int[capacity];
        Arrays.fill(roots, -1);
    }

    public int allocate(int refs, int dataWords) {
        if (refs < 0 || dataWords < 0) {
            throw new IllegalArgumentException("negative size");
        }
        int size = HEADER + refs + dataWords;
        if (top + size > memory.length) {
            collect();
            if (top + size > memory.length) {
                throw new IllegalStateException("out of memory: " + size + " words needed, " + (memory.length - top) + " free");
            }
        }
        int address = top;
        memory[address] = refs;
        memory[address + 1] = dataWords;
        Arrays.fill(memory, address + HEADER, address + HEADER + refs, -1);       // null references
        Arrays.fill(memory, address + HEADER + refs, address + size, 0);
        top += size;                                                              // bump
        return address;
    }

    public void setRoot(int slot, int address) {
        checkRoot(slot);
        roots[slot] = address;
    }

    public int root(int slot) {
        checkRoot(slot);
        return roots[slot];
    }

    public void setRef(int address, int slot, int target) {
        memory[refIndex(address, slot)] = target;
    }

    public int ref(int address, int slot) {
        return memory[refIndex(address, slot)];
    }

    public void setData(int address, int index, int value) {
        memory[dataIndex(address, index)] = value;
    }

    public int data(int address, int index) {
        return memory[dataIndex(address, index)];
    }

    public int used() {
        return top;
    }

    public int collect() {
        int before = top;

        // 1. Mark everything reachable from the roots (an explicit stack: object graphs can be deep).
        boolean[] marked = new boolean[memory.length];
        Deque<Integer> stack = new ArrayDeque<>();
        for (int r : roots) {
            if (r >= 0) {
                stack.push(r);
            }
        }
        while (!stack.isEmpty()) {
            int a = stack.pop();
            if (marked[a]) {
                continue;
            }
            marked[a] = true;
            for (int s = 0; s < memory[a]; s++) {
                int target = memory[a + HEADER + s];
                if (target >= 0 && !marked[target]) {
                    stack.push(target);
                }
            }
        }

        // 2. Compute each live object's new address: live objects keep their order.
        int[] forward = new int[memory.length];
        int free = 0;
        for (int a = 0; a < top; a += size(a)) {
            if (marked[a]) {
                forward[a] = free;
                free += size(a);
            }
        }

        // 3. Update the roots and every reference inside live objects.
        for (int i = 0; i < ROOTS; i++) {
            if (roots[i] >= 0) {
                roots[i] = forward[roots[i]];
            }
        }
        for (int a = 0; a < top; a += size(a)) {
            if (marked[a]) {
                for (int s = 0; s < memory[a]; s++) {
                    int slot = a + HEADER + s;
                    if (memory[slot] >= 0) {
                        memory[slot] = forward[memory[slot]];
                    }
                }
            }
        }

        // 4. Slide the live objects down. Going upwards, each copy only overwrites memory already dealt with.
        int a = 0;
        while (a < top) {
            int size = size(a);
            if (marked[a]) {
                System.arraycopy(memory, a, memory, forward[a], size);
            }
            a += size;
        }
        top = free;
        return before - free;
    }

    private int size(int address) {
        return HEADER + memory[address] + memory[address + 1];
    }

    private int refIndex(int address, int slot) {
        checkAddress(address);
        if (slot < 0 || slot >= memory[address]) {
            throw new IllegalArgumentException("no reference slot " + slot + " in the object at " + address);
        }
        return address + HEADER + slot;
    }

    private int dataIndex(int address, int index) {
        checkAddress(address);
        if (index < 0 || index >= memory[address + 1]) {
            throw new IllegalArgumentException("no data word " + index + " in the object at " + address);
        }
        return address + HEADER + memory[address] + index;
    }

    private void checkAddress(int address) {
        if (address < 0 || address >= top) {
            throw new IllegalArgumentException("not an object address: " + address);
        }
    }

    private static void checkRoot(int slot) {
        if (slot < 0 || slot >= ROOTS) {
            throw new IllegalArgumentException("no root slot " + slot);
        }
    }
}
```

## Cheat sheet

<CheatSheet>

| Topic | Remember |
|---|---|
| **Areas** | Per thread: JVM stack, pc register, native stack · Shared: heap, method area (Metaspace) |
| **Stack** | Frames of locals (primitives + references); LIFO; `-Xss`; `StackOverflowError` |
| **Heap** | Every object and array (with fields/elements); shared; `-Xmx`; `OutOfMemoryError` |
| **Reference** | Opaque handle to an object or `null`; assignment copies it (aliasing); `==` compares it |
| **Primitives** | Local → frame; field → inside the object; static → with the class; element → inside the array |
| **Liveness** | Reachable from GC roots (stacks, statics) = live; cycles without a root = garbage |
| **Leak** | Something still reachable that isn't needed (static maps, caches, listeners) |
| **Allocation** | Bump pointer in a TLAB: cheap; objects may move later |
| **Notes' example** | `main` + `memoryManagementTest` frames, Person, MemoryManagement, `"24"` pooled vs `new String("24")` |

</CheatSheet>
