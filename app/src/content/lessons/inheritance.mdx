## Why this matters

Inheritance is the first tool most developers reach for to reuse code, and the one that causes the most expensive
surprises. A subclass of `HashSet` counts its additions twice because of how `HashSet` happens to be implemented.
`java.util.Stack` lets you insert in the middle of a stack because it extends `Vector`. A library adds a method to a
base class, and a subclass method with the same signature silently becomes an override. To use inheritance well you
need to know exactly what a subclass gets, how the compiler and the JVM look up members, and when an "is-a" relationship
is real.

## TL;DR

<Callout type="tldr">
- `class Car extends Vehicle`: a `Car` **is a** `Vehicle` and can be used wherever one is expected. A class extends
  exactly one class (`Object` if none is named).
- A subclass inherits the **accessible members** (fields, methods, nested types) of its superclass. **Private fields
  still exist inside the subclass object**, but its code can't name them. **Constructors are never inherited.**
- Members are looked up on the **declared type** of the expression: `vehicle.getCarType()` doesn't compile
  (audit 1.16). Overridden instance methods then run by the object's real class; fields and static methods don't.
- Kinds: single, multilevel, hierarchical; **multiple inheritance only of type** (interfaces), and of behaviour through
  `default` methods, never of state; **hybrid** mixes one superclass with several interfaces.
- Clashing default methods are resolved by rules: a class method wins, then the most specific interface; otherwise you
  must override, optionally calling `A.super.m()`.
- Inherit only for a real, substitutable is-a relationship; otherwise compose. Make classes `final` (or `sealed`) unless
  they're designed for extension.
</Callout>

## Mental model

A subclass is a new edition of a book that keeps every chapter of the previous edition and adds some, or rewrites a
few. Readers who only know the old edition's table of contents can still use the new one: every chapter they expect is
there. That's what "is a" means: a `Car` can stand in for a `Vehicle` because it has everything a `Vehicle` has.

Where the picture breaks: the new edition doesn't contain a copy of the old one. The superclass's code stays where it
is, and the new edition can't even read the old edition's private notes, although they're part of every printed copy.

## Concept, step by step

### 1. `extends`: a class built on another

The notes (01 p6) describe inheritance as a class's ability to inherit properties from its parent, both functions and
variables, so they don't have to be written again, using `extends` or interfaces. That's the idea; the details matter
(audit 1.14):

- A class has exactly one direct superclass. Without `extends`, it's `Object`.
- The subclass inherits the superclass's **accessible members**: public and protected ones always, package-private ones
  only within the same package. It can add new members and override inherited methods.
- The subclass becomes a **subtype**: wherever a `Vehicle` is expected, a `Car` can be used.

### 2. The notes' `Vehicle` and `Car`, corrected

The notes' demo (01 p7–8), with `String` for the notes' `string`:

```java title="Garage.java"
class Vehicle {
    boolean engine;

    boolean getEngine() {
        return this.engine;
    }
}

class Car extends Vehicle {
    String type;

    String getCarType() {
        return this.type;
    }
}

public class Garage {
    public static void main(String[] args) {
        Car swift = new Car();
        swift.type = "hatchback";
        System.out.println(swift.getEngine() + " " + swift.getCarType());
        Vehicle vehicle = new Vehicle();
        // vehicle.getCarType();             error: cannot find symbol: method getCarType(), location: variable vehicle of type Vehicle
    }
}
```

```text output
false hatchback
```

The notes say `vehicle.getCarType()` "should not work", and it doesn't: it's a **compile-time** error (audit 1.16). The
compiler looks for members on the **declared type** of the expression, and `Vehicle` has no `getCarType`. The same is
true for `Vehicle v = new Car(); v.getCarType();`: the object is a `Car`, but the compiler only knows it's a `Vehicle`.
You'd need a cast, `((Car) v).getCarType()`, which is checked at run time
([Polymorphism](/lessons/polymorphism/), [Reference Types](/lessons/reference-types/)).

### 3. What is and isn't inherited

| Superclass declaration | Inherited by the subclass? | Notes |
|---|---|---|
| `public` and `protected` fields and methods | Yes | Methods can be overridden |
| Package-private fields and methods | Only if the subclass is in the same package | |
| `private` fields | No: not members of the subclass | They still **exist in every subclass object**; superclass methods use them |
| `private` methods | No | A method with the same signature in the subclass is a new, unrelated method |
| Static fields and methods | Yes (if accessible) | One copy, in the superclass; static methods are hidden, not overridden |
| Nested classes and interfaces | Yes (if accessible) | |
| Constructors and initialisers | Never | Each class declares its own; subclass constructors call one with `super(...)` |

The private-field rule surprises people, so here it is in code:

```java title="Accounts.java"
class Account {
    private long balance;                     // exists in every SavingsAccount, invisible to its code

    void deposit(long amount) {
        balance += amount;
    }

    long balance() {
        return balance;
    }
}

class SavingsAccount extends Account {
    void addInterest(int percent) {
        // balance += balance * percent / 100;   error: balance has private access in Account
        deposit(balance() * percent / 100);     // through the inherited, accessible methods
    }
}

public class Accounts {
    public static void main(String[] args) {
        SavingsAccount s = new SavingsAccount();
        s.deposit(1000);
        s.addInterest(5);
        System.out.println(s.balance());
    }
}
```

```text output
1050
```

### 4. `super`, and members that are hidden rather than overridden

`super` reaches the superclass's version of something the subclass has replaced:

- `super.method(...)` calls the superclass's implementation, typically from an override that extends it rather than
  replacing it (`return super.describe() + ", " + type;`).
- `super(...)` calls a superclass constructor ([Constructor Chaining & Init Order](/lessons/constructor-chaining-init-order/)).
- `super.field` reaches a superclass field hidden by a subclass field of the same name.

Only instance methods are chosen by the object's real class at run time. **Fields and static methods are hidden, not
overridden:** which one you get depends on the declared type, as puzzles 1 and 2 show. A subclass field with the same
name as a superclass field doesn't replace it; the object then holds both. Avoid it.

### 5. The kinds of inheritance

<InheritanceKinds />

The notes (01 p8–9) list single, multilevel and hierarchical inheritance, and multiple inheritance as "not supported due
to the diamond problem, with a workaround through interfaces". More precisely (audit 1.15):

- **Classes** can only form single, multilevel and hierarchical inheritance: one superclass each.
- **Multiple inheritance of type** is fine: a class can implement any number of interfaces, and an interface can extend
  several.
- **Multiple inheritance of behaviour** arrived with Java 8's `default` methods.
- **Multiple inheritance of state** is what Java forbids: interfaces have no instance fields, so no object can get two
  copies of a field from two parents.
- **Hybrid** inheritance, missing from the notes, combines them: `class C extends A implements I, J`.

Default methods bring the diamond problem back for behaviour. The JLS rules for inheriting methods (§8.4.8, §9.4.1.3)
resolve it, and they come down to three:

1. **A class wins.** A method declared in a class or inherited from a superclass beats any interface default.
2. **The most specific interface wins.** If `FastWalker extends Walker` and both define `move()`, a class implementing
   both gets `FastWalker`'s.
3. **Otherwise the class must decide.** Two unrelated defaults with the same signature are a compile error ("inherits
   unrelated defaults") until the class overrides the method, possibly delegating with `Interface.super.method()`:

```java title="Ducks.java"
interface Walker {
    default String move() {
        return "walk";
    }
}

interface Swimmer {
    default String move() {
        return "swim";
    }
}

class Duck implements Walker, Swimmer {
    @Override
    public String move() {                     // required: two unrelated defaults
        return Walker.super.move() + " and " + Swimmer.super.move();
    }
}

public class Ducks {
    public static void main(String[] args) {
        System.out.println(new Duck().move());
    }
}
```

```text output
walk and swim
```

### 6. Closing a class to inheritance

- **`final` classes** can't be extended: `String`, `Integer`, `LocalDate`, every record. **`final` methods** can't be
  overridden. Both protect invariants that subclasses could otherwise break
  ([final & Constants](/lessons/final-and-constants/)).
- **`sealed` classes** (Java 17) allow exactly the subclasses they list, so a hierarchy can be open for a known set of
  cases and closed to everyone else ([Sealed Classes](/lessons/sealed-classes/)).
- **Classes designed for inheritance** document which methods call which overridable methods, provide `protected`
  hooks deliberately, and never call overridable methods from constructors (Effective Java item 19). Everything a
  subclass can see or override is part of the API, just like public methods.
- Otherwise, prohibit it: make the class `final`, or give it only private constructors and static factories
  ([Private Constructors & Static Factories](/lessons/private-constructors-static-factories/)).

### 7. When to inherit

Use inheritance when the subclass really **is a** kind of the superclass in every situation where the superclass is
used: the **Liskov substitution principle**. Code written for `Vehicle` must keep working, unchanged and correct, when
it receives a `Car`. A square that is a mutable rectangle fails this test: code that sets a rectangle's width and
expects its height to stay the same breaks when given a square (the core exercise shows how immutability fixes it).

When the relationship is "uses" or "has" rather than "is", or when you only want to reuse code, **compose** instead:
hold the other object in a field and forward to it (Effective Java item 18;
[IS-A, HAS-A & Composition](/lessons/relationships/)).

## Scenarios

<Tabs>
<TabItem label="Real world: the subclass that counted twice">

```java title="InstrumentedHashSet.java"
import java.util.Collection;
import java.util.HashSet;
import java.util.List;

public class InstrumentedHashSet<E> extends HashSet<E> {
    private int addCount = 0;

    @Override
    public boolean add(E e) {
        addCount++;
        return super.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);
    }

    public static void main(String[] args) {
        InstrumentedHashSet<String> s = new InstrumentedHashSet<>();
        s.addAll(List.of("Snap", "Crackle", "Pop"));
        System.out.println(s.addCount);
    }
}
```

```text output
6
```

Effective Java's classic example (item 18). `HashSet.addAll` is inherited from `AbstractCollection`, which calls `add`
for each element, so each element is counted twice. The subclass depended on an implementation detail of its
superclass that no documentation promised, and a future change to `HashSet` could break it again in the other
direction. The fix is composition: a class that holds a `Set`, implements `Set` by forwarding every call to it, and
counts in its own `add` and `addAll`. Its correctness then depends only on the `Set` interface's contract.

</TabItem>
<TabItem label="Edge case: an override nobody wrote">

```java
// Library version 1
public class Task {
    public void run() { ... }
}

// Your code, written against version 1
public class ReportTask extends Task {
    public void close() {                      // releases the report's file
        ...
    }
}

// Library version 2 adds lifecycle handling
public class Task {
    public void run() { ... }
    public void close() { ... }                // the framework now calls close() when a task is cancelled
}
```

With version 2 on the class path, `ReportTask.close()` is an override, recompiled or not: the JVM decides overriding
at run time, by method name and descriptor. The framework now calls it in situations its author never
imagined: at cancellation, perhaps more than once. Had version 2 declared `close()` with a different
return type, `ReportTask` would stop compiling instead. Subclasses depend on every method of their superclass, including
ones added later; `@Override` on intended overrides and `final` classes in libraries keep such surprises visible.

</TabItem>
<TabItem label="Anti-pattern → fix: inheriting for reuse">

```java title="Anti-pattern"
Stack<Integer> stack = new Stack<>();          // java.util.Stack extends Vector
stack.push(1);
stack.push(2);
stack.add(0, 99);                              // a Vector method: inserts at the bottom of the stack
System.out.println(stack);                     // [99, 1, 2]
```

`Stack` extends `Vector` to reuse its storage, so it inherits every list operation, and nothing stops callers from
breaking the last-in, first-out rule. `Properties extends Hashtable` has the same flaw: you can put non-string values
into it. Both date from Java 1.0; today you'd compose:

```java title="Fix"
Deque<Integer> stack = new ArrayDeque<>();     // push, pop and peek; no index-based insertion
stack.push(1);
stack.push(2);
```

</TabItem>

## Under the hood

<details>
<summary>Inheritance in the class file and the JVM</summary>

- **One `super_class` entry.** A class file names exactly one superclass; interfaces are listed separately. Loading a
  class loads its superclass first, and initialising it initialises the superclass first.
- **Object layout.** A subclass object holds the superclass's fields and its own; private superclass fields take space
  like any other. HotSpot keeps each inherited field at the same offset in every subclass object, so the superclass's
  compiled code finds its fields whatever the object's real class.
- **Method lookup.** `invokevirtual` finds the implementation through the class's method table (vtable), which starts
  with the superclass's entries and replaces the overridden ones. `super.m()` compiles to `invokespecial`, a call to one
  exact implementation with no dynamic dispatch ([Polymorphism](/lessons/polymorphism/)).
- **Nothing is copied.** Inherited methods aren't duplicated into subclasses; their code stays in the class that
  declares them.

</details>

## Myths vs facts

<MythVsFact myth="A subclass inherits everything from its parent, private fields and constructors included." audit="1.14">
Only accessible members are inherited. Private fields still exist inside every subclass object, but the subclass's code
can't name them, and constructors are never inherited.
</MythVsFact>

<MythVsFact myth="Inheritance copies the parent's methods into the child class." audit="1.14">
Nothing is copied. The methods stay in the superclass, and calls on a subclass object are looked up through the class
hierarchy.
</MythVsFact>

<MythVsFact myth="Java doesn't support multiple inheritance." audit="1.15">
It doesn't support multiple inheritance of state (classes). It does support multiple inheritance of type through
interfaces, and of behaviour through default methods.
</MythVsFact>

<MythVsFact myth="Interfaces solve the diamond problem completely." audit="1.15">
Two unrelated default methods with the same signature still clash. The compiler reports it, and the class must override
the method, choosing or combining the versions with `Interface.super.method()`.
</MythVsFact>

<MythVsFact myth="vehicle.getCarType() fails at run time." audit="1.16">
It fails at compile time: the compiler looks up members on the declared type, and `Vehicle` has no `getCarType`, whatever
object the variable refers to.
</MythVsFact>

## Doubts cleared

<FaqItem q="Does a subclass object really contain the superclass's private fields?">
Yes. The superclass's methods, which the subclass inherits, read and write them. The subclass just can't refer to them
by name.
</FaqItem>

<FaqItem q="Why can't a class extend two classes?">
Two superclasses could both give it a field or a method body with the same name, and both constructors would need to
run, with no clear order. Java avoids that whole class of problems by allowing one superclass and any number of
interfaces, which carry no instance state.
</FaqItem>

<FaqItem q="What's the difference between extends and implements?">
A class `extends` one class, inheriting its state and behaviour, and `implements` interfaces, taking on their types and
any default methods. An interface `extends` other interfaces.
</FaqItem>

<FaqItem q="Can a subclass call super.super.method()?">
No. A class can only reach its direct superclass's implementation with `super`. If you need a grandparent's behaviour
specifically, the hierarchy is probably wrong.
</FaqItem>

<FaqItem q="Are static fields shared between a class and its subclasses?">
There's one copy, in the class that declares it. `Child.count` and `Parent.count` name the same variable if `Child`
inherits it, unless `Child` declares its own `count`, which then hides the parent's.
</FaqItem>

<FaqItem q="Do interfaces extend Object?">
No, but every interface type has `Object`'s public methods as members, because every object that implements it is an
`Object` ([The Object Class Contracts](/lessons/object-class-contracts/)).
</FaqItem>

<FaqItem q="How deep should a class hierarchy be?">
There's no technical limit, but each level couples subclasses to more implementation details. Deep hierarchies are hard
to change; two or three levels, with abstract classes and interfaces at the top, is common in well-designed code.
</FaqItem>

<FaqItem q="Can protected members be accessed through any object of the superclass?">
Only within the same package. Outside it, a subclass can use them on itself (`this`, `super`) or through references
whose type is the subclass or one of its subclasses, not through a plain superclass reference. The full rule is in
[Packages & Access Modifiers](/lessons/packages-access-modifiers/).
</FaqItem>

## Pitfalls and best practices

| ✅ Do | ❌ Don't |
|---|---|
| Inherit only for a real, substitutable is-a relationship | Extend a class just to reuse its code |
| Put `@Override` on every intended override | Rely on matching a superclass method signature by eye |
| Make classes `final` or `sealed` unless they're designed for extension | Leave every class open "just in case" |
| Document self-use in classes meant to be extended | Let subclasses depend on undocumented call patterns |
| Call superclass behaviour with `super.method()` when extending it | Declare fields with the same name as superclass fields |
| Compose when the relationship is "has" or "uses" | Build deep hierarchies for small variations |

## Senior lens

<Callout type="senior" title="Explain it to your team in 60 seconds">
"Extending a class makes us a subtype and couples us to the superclass's implementation, including details nobody
documented. So we inherit only when the subclass can stand in for the superclass everywhere, from classes designed for
it, with `@Override` on every override. Everything else is final or sealed, and reuse goes through composition. Java
gives us multiple inheritance of types and behaviour through interfaces, never of state, and makes us resolve clashing
defaults explicitly."
</Callout>

**Where it goes wrong in production**

| Symptom | Cause | Fix |
|---|---|---|
| Counts, caches or hooks fire twice or not at all | The subclass relies on the superclass's self-use | Composition and forwarding |
| Behaviour changes after a library upgrade | A new superclass method became an accidental override | `@Override` discipline; final classes in libraries |
| Callers break a subclass's rules through inherited methods | Inheritance used for reuse (`Stack extends Vector`) | Composition exposing only the right operations |
| Code works for the base class, fails for a subclass | Liskov violation | Fix the hierarchy (immutability, separate types) |
| Every change ripples through many classes | Deep hierarchies, wide protected APIs | Flatten; interfaces plus composition |

**Code-review checklist**
- [ ] Every subclass passes the "can it stand in for the superclass everywhere?" test.
- [ ] Classes not designed for extension are `final` or `sealed`.
- [ ] Every override has `@Override`; no field hides a superclass field.
- [ ] Superclasses don't call overridable methods from constructors and document self-use.
- [ ] Code reuse without an is-a relationship uses composition.

## Modern Java

- <VersionBadge since={8} /> Default and static methods in interfaces: multiple inheritance of behaviour, with the
  diamond-resolution rules.
- <VersionBadge since={9} /> Private interface methods, to share code between defaults.
- <VersionBadge since={16} jep={395} /> Records: final classes that extend `java.lang.Record` and can implement
  interfaces.
- <VersionBadge since={17} jep={409} /> Sealed classes and interfaces: inheritance limited to a listed set of
  subclasses.
- <VersionBadge since={21} jep={441} /> Pattern matching for `switch`, which can check that a sealed hierarchy's cases
  are all handled.
- <VersionBadge since={25} jep={513} /> Flexible constructor bodies: a subclass constructor can check or prepare its
  arguments before calling `super(...)`.

```java title="Rectangle.java (solution)"
package track.inheritance;

/** Reference solution for the Rectangle part of the Square exercise. */
public class Rectangle {
    private final double width;
    private final double height;

    public Rectangle(double width, double height) {
        this.width = checked(width, "width");
        this.height = checked(height, "height");
    }

    private static double checked(double side, String name) {
        if (!(side > 0) || Double.isInfinite(side)) {           // also rejects NaN
            throw new IllegalArgumentException(name + " must be finite and > 0: " + side);
        }
        return side;
    }

    public double width() {
        return width;
    }

    public double height() {
        return height;
    }

    public double area() {
        return width * height;
    }

    public boolean isSquare() {
        return width == height;
    }

    public Rectangle withWidth(double width) {
        return new Rectangle(width, height);
    }

    public Rectangle withHeight(double height) {
        return new Rectangle(width, height);
    }

    public Rectangle scaled(double factor) {
        return new Rectangle(width * factor, height * factor);
    }

    @Override
    public boolean equals(Object o) {
        return o instanceof Rectangle r
                && Double.compare(width, r.width) == 0
                && Double.compare(height, r.height) == 0;
    }

    @Override
    public int hashCode() {
        return 31 * Double.hashCode(width) + Double.hashCode(height);
    }

    @Override
    public String toString() {
        return "Rectangle " + width + " x " + height;
    }
}
```

```java title="BoundedList.java (solution)"
package track.inheritance;

import java.util.AbstractList;
import java.util.ArrayList;
import java.util.Collection;
import java.util.List;
import java.util.Objects;

/** Reference solution for the BoundedList exercise. */
public final class BoundedList extends AbstractList<String> {
    private final List<String> items = new ArrayList<>();
    private final int capacity;

    public BoundedList(int capacity) {
        if (capacity < 0) {
            throw new IllegalArgumentException("negative capacity: " + capacity);
        }
        this.capacity = capacity;
    }

    @Override
    public String get(int index) {
        return items.get(index);
    }

    @Override
    public int size() {
        return items.size();
    }

    @Override
    public String set(int index, String element) {               // size unchanged: no modCount change
        return items.set(index, Objects.requireNonNull(element));
    }

    @Override
    public void add(int index, String element) {                 // add(e), addAll and listIterator().add land here
        Objects.requireNonNull(element);
        if (items.size() == capacity) {
            throw new IllegalStateException("the list is full: capacity " + capacity);
        }
        items.add(index, element);
        modCount++;                                              // lets the inherited iterators fail fast
    }

    @Override
    public String remove(int index) {                            // remove(Object), removeIf, clear, subList land here
        String removed = items.remove(index);
        modCount++;
        return removed;
    }

    @Override
    public boolean addAll(Collection<? extends String> c) {
        return super.addAll(checkedCopy(c));
    }

    @Override
    public boolean addAll(int index, Collection<? extends String> c) {
        return super.addAll(index, checkedCopy(c));
    }

    /**
     * All-or-nothing: the inherited addAll methods add element by element and would stop halfway. The copy also
     * makes list.addAll(list) safe: iterating a list while adding to it would fail fast.
     */
    private List<String> checkedCopy(Collection<? extends String> c) {
        List<String> copy = List.copyOf(c);                      // NullPointerException if any element is null
        if (copy.size() > remainingCapacity()) {
            throw new IllegalStateException(copy.size() + " elements don't fit in " + remainingCapacity() + " free places");
        }
        return copy;
    }

    public int capacity() {
        return capacity;
    }

    public int remainingCapacity() {
        return capacity - items.size();
    }
}
```

## Cheat sheet

<CheatSheet>

| Topic | Remember |
|---|---|
| **extends** | One direct superclass (`Object` by default); the subclass is a subtype |
| **Inherited** | Accessible members: fields, methods, nested types |
| **Not inherited** | Constructors, initialisers, private members (private fields still exist in the object) |
| **Lookup** | Members found on the declared type at compile time; overridden instance methods run by the object's class |
| **Hiding** | Fields and static methods are hidden, never overridden |
| **super** | `super.m()`, `super(...)`, `super.field`; no `super.super` |
| **Kinds** | Single, multilevel, hierarchical; multiple only via interfaces; hybrid = class + interfaces |
| **Default diamond** | Class wins → more specific interface wins → else override (`I.super.m()`) |
| **Closing** | `final` classes and methods; `sealed` (17); records are final |
| **When** | Real, substitutable is-a (Liskov); otherwise composition |
