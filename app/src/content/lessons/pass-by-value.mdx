## Why this matters

A settings loader is written as `void load(Settings settings, String file)`. Inside, it builds a fresh object with
`settings = new Settings(...)` and fills it in. Every test of the loader itself passes, yet the application keeps
running with the defaults: the caller's `settings` variable never changed. The opposite bug is just as common: a
helper that "only reads" a list sorts it in place, and the caller's data comes back reordered. Both come from one rule
that the notes state in a single line: **in Java, everything is pass by value**. Knowing exactly what gets copied
tells you what a method can and can't do to your data, and it's one of the most common interview questions of all.

## TL;DR

<Callout type="tldr">
- Calling a method creates **new parameter variables** and initialises them with **copies of the argument values**
  (JLS §8.4.1). There's no other way to pass arguments in Java.
- For a primitive, the value is the number: the method can't change the caller's variable.
- For an object, the value is a **reference**: the method gets a second arrow to the **same object**. It can **mutate**
  that object (the caller sees it) but **reassigning** the parameter only moves its own copy.
- So a `swap(a, b)` method can never swap the caller's variables. Swap elements or fields, or return the result.
- Immutable objects (`String`, `Integer` and the other wrappers, records of immutable values) can't be changed at all,
  so a method can't change what the caller has. Wrappers do **not** give "pass-by-reference" (audit 6.10).
- Get results out with **return values** (a record for several values). Copy mutable data that crosses a boundary.
</Callout>

## Mental model

Calling a method is handing over a **photocopy** of each argument. If the argument is a number, the copy is the
number: scribble on it all you like, the original is untouched. If the argument is an object, what you copy is the
**address label** of the box on the warehouse shelf. With the copied label the method can walk to the box and change
what's inside, and the caller will see the change. But if the method writes a different address on its copy of the
label, the caller's label still points to the original box.

Where it breaks: nothing is ever passed "by photocopying the box". Java never copies an object when you pass it; if you
want an independent copy, you make one explicitly.

## Concept, step by step

### 1. What the two terms really mean

The terms describe **what the parameter is**, not what kind of data you pass:

| | Pass-by-value | Pass-by-reference |
|---|---|---|
| **The parameter is** | A new variable holding a copy of the argument's value | Another name (an alias) for the caller's **variable** |
| **Assigning to the parameter** | Changes only the copy | Changes the caller's variable |
| **Examples** | Java (always), C, Python, JavaScript | C++ `int&` parameters, C# `ref`, Pascal `var` |

The Java Language Specification leaves no room for doubt: when a method is invoked, "the values of the actual argument
expressions initialize newly created parameter variables" (JLS §8.4.1). A frame is created for the call
([The Call Stack](/lessons/call-stack/)) and the parameters are ordinary local variables in it.

The confusion comes from the word "reference". In Java a **reference** is a value that points to an object. Passing a
reference by value is not the same thing as passing a variable by reference. Some texts use the term **call by
sharing** (from the CLU language) for exactly this: the caller and the method share the object, not the variable.

### 2. Primitives: the number is copied

You saw this in [Methods](/lessons/methods-basics/): `reset(count)` with `n = 0` inside leaves `count` alone. The
parameter is a separate variable that starts with the same number. A method that computes something from a primitive
must **return** the result.

### 3. References: the arrow is copied

Two rules fall out of it, and they're all you need:

1. **Mutation through the parameter is visible to the caller.** `account.balance = …` follows the copied reference to
   the one shared object (`deposit`).
2. **Reassigning the parameter is invisible to the caller.** `account = new Account()` changes the method's own
   variable; the caller's variable is somewhere else, in another frame, and the method has no access to it
   (`replace`).

### 4. The swap test

If Java had pass-by-reference, you could write a method that swaps the caller's two variables. You can't:

```java title="Swap.java"
public class Swap {
    static void swap(String a, String b) {
        String tmp = a;
        a = b;
        b = tmp;
        System.out.println("inside: " + a + " " + b);
    }

    public static void main(String[] args) {
        String x = "left";
        String y = "right";
        swap(x, y);
        System.out.println("after:  " + x + " " + y);
    }
}
```

```text output
inside: right left
after:  left right
```

Inside the method, the two **copies** were swapped. `x` and `y` never were. What does work:

- **Swap inside a shared object**: `swap(array, i, j)` exchanges two elements of the caller's array, because the array
  is shared, and only its contents change.
- **Return the result**: `record Pair(String first, String second)` with a `swapped()` method that returns a new pair;
  the caller assigns it: `pair = pair.swapped();`.

### 5. Immutable objects: nothing to change

The notes give this reason for wrapper classes: "we get the advantages of passing by reference … if we change an
`Integer` later it'll change in memory". That's **incorrect** (audit 6.10):

```java title="Wrappers.java"
public class Wrappers {
    static void change(Integer x) {
        x = x + 1;          // unbox, add, box a NEW Integer, assign it to the parameter
    }

    public static void main(String[] args) {
        Integer value = 10;
        change(value);
        System.out.println(value);
    }
}
```

```text output
10
```

This result was checked on a JVM. `Integer` objects are **immutable**: there's no method that changes the number
inside one. `x + 1` unboxes the value, adds 1, and boxes the result into a different `Integer` object; the assignment
then re-points the parameter, exactly like `replace` above. The caller's `value` still refers to the `Integer` 10. The
same holds for `String`: `s = s.trim()` inside a method creates a new string and changes only the parameter.

The real reasons wrappers exist are different: collections and generics need objects (`List<Integer>`), `null` can
mean "no value", and they hold the utility methods and constants (`Integer.parseInt`, `Integer.MAX_VALUE`). See
[Wrappers & Autoboxing](/lessons/wrappers-boxing/).

### 6. Arrays, collections and varargs

Arrays and collections are objects, so methods that receive them can change their contents. That's why
`Arrays.sort(numbers)` and `Collections.sort(list)` return `void`: they sort **your** array or list, in place.
Variable-arity parameters show both sides of the rule in one method:

```java title="Varargs.java"
public class Varargs {
    static void zeroFirst(int... values) {
        values[0] = 0;
    }

    public static void main(String[] args) {
        int single = 5;
        zeroFirst(single);          // the compiler creates a new int[] {5} for this call
        int[] array = {5, 6};
        zeroFirst(array);           // the caller's own array is passed
        System.out.println(single + " " + array[0]);
    }
}
```

```text output
5 0
```

With separate arguments, the method changes a temporary array the compiler built for the call. With an array
argument, it changes the caller's array ([Varargs](/lessons/varargs/)).

### 7. Getting results out of a method

| Need | Best tool |
|---|---|
| One result | **Return it**: `String cleaned = clean(input);` |
| Several results | Return a **record**: `record Stats(int min, int max)` |
| Maybe no result | Return `Optional<T>` (or an empty collection), not `null` |
| Fill or change something the caller owns | Mutate it deliberately and say so in the name and docs: `sortInPlace`, `appendTo(StringBuilder)` |
| A counter changed inside a lambda | Prefer a stream operation (`count`, `sum`); a holder such as `AtomicInteger` only as a last resort |

A parameter can be declared `final` so the method can't reassign it by accident. That doesn't stop anyone from
mutating the object it refers to ([final & Constants](/lessons/final-and-constants/)).

### 8. Sharing across boundaries: defensive copies

Because a method and its caller share every object passed between them, a class that **stores** an argument, or
**returns** one of its fields, shares that object with someone else:

```java title="Sharing.java"
import java.util.ArrayList;
import java.util.List;

public class Sharing {
    static final class Team {
        private final List<String> members;

        Team(List<String> members) {
            this.members = members;             // stores the caller's reference: both share one list
        }

        int size() {
            return members.size();
        }
    }

    public static void main(String[] args) {
        List<String> names = new ArrayList<>(List.of("Ann", "Bo"));
        Team team = new Team(names);
        names.add("Cy");                        // the caller keeps using its own list
        System.out.println(team.size());
    }
}
```

```text output
3
```

The team changed without calling any of its methods. The fix is a **defensive copy** on the way in
(`this.members = List.copyOf(members);`, or `array.clone()` for arrays), and on the way out if the field is mutable.
`List.copyOf` returns an unmodifiable list, so it can be returned as is. Immutable objects never need copies, which is
one of their big advantages ([Immutable & Final Classes](/lessons/immutable-and-final-classes/)).

```java title="Loader.java"
public class Loader {
    static class Settings {
        int timeoutSeconds = 30;
```


`load` configured a new object that nobody can reach once it returns. Fix the design, not just the line: make it

</TabItem>
<TabItem label="Edge case: a String parameter">

```java title="Clean.java"
public class Clean {
    static void clean(String s) {
        s = s.strip().toLowerCase();                        // a new String, assigned to the parameter
    }

    public static void main(String[] args) {
        String input = "  Hello ";
        clean(input);
        System.out.println("[" + input + "]");
    }
}
```

```text output
[  Hello ]
```

Strings are immutable, so no method can change the caller's text: every "change" makes a new string. Methods on
strings always **return** the result: `input = clean(input);` with `static String clean(String s)`.

</TabItem>
<TabItem label="Anti-pattern → fix: output parameters">

```java title="Anti-pattern"
// C-style: results smuggled out through arrays the caller passes in
static void stats(int[] values, int[] minOut, int[] maxOut) {
    minOut[0] = Arrays.stream(values).min().orElseThrow();
    maxOut[0] = Arrays.stream(values).max().orElseThrow();
}
```

It works (it mutates shared arrays), but the call site is hard to read, the "outputs" can be mixed up, and nothing
stops a caller from passing the same array twice. Return a value instead:

```java title="Fix"
record Stats(int min, int max) {
}

static Stats stats(int[] values) {
    IntSummaryStatistics s = Arrays.stream(values).summaryStatistics();
    return new Stats(s.getMin(), s.getMax());
}
```

</TabItem>
<TabItem label="Edge case: the helper that sorts your data">

```java title="Median.java"
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public class Median {
    static int median(List<Integer> values) {
        Collections.sort(values);                           // sorts the caller's list
        return values.get(values.size() / 2);
    }

    public static void main(String[] args) {
        List<Integer> readings = new ArrayList<>(List.of(5, 1, 4));
        System.out.println(median(readings) + " " + readings);
    }
}
```

```text output
4 [1, 4, 5]
```

The caller asked for a median and got its data reordered as a side effect; with an unmodifiable list such as
`List.of(5, 1, 4)` the same call throws `UnsupportedOperationException`. A method that only needs to read should work
on a copy: `List<Integer> sorted = new ArrayList<>(values); Collections.sort(sorted);`, or
`values.stream().sorted().toList()`.

</TabItem>

## Under the hood

<details>
<summary>What the JVM does with arguments</summary>

- **Arguments become locals.** The caller pushes the argument values on its operand stack; the invoke instruction
  pops them into the new frame's local variables. For an instance method, local 0 is the receiver (`this`) and the
  arguments follow; `long` and `double` take two slots each (JVMS §2.6.1). The JIT then maps all of this onto CPU
  registers, but the semantics stay the same.
- **Passing an object costs a reference.** Only the reference is copied (4 bytes with compressed references, 8
  otherwise), however big the object is. Java never copies objects implicitly; there are no copy constructors called
  behind your back as with C++ objects passed by value.
- **`this` is passed too, but it isn't a variable.** It's an implicit argument, and `this = …` doesn't compile.
- **Lambdas capture values.** A lambda that uses a local variable gets a copy of its value when the lambda is created.
  That's why captured locals must be final or effectively final (JLS §15.27.2): a copy can then never disagree with
  the variable ([Lambda Expressions](/lessons/lambda-expressions/)).
- **Return values are copied the same way.** `return list;` hands the caller a copy of the reference, so the caller
  and the method's object then share the list.

</details>

## Myths vs facts

<MythVsFact myth="Java passes primitives by value and objects by reference.">
Java passes **everything** by value. For objects, the value copied is a reference, so the method shares the object but
can't touch the caller's variable. The swap test settles it: no Java method can swap two of its caller's variables.
</MythVsFact>

<MythVsFact myth="Wrapper classes give the advantages of pass-by-reference: change an Integer in a method and it changes in memory." audit="6.10">
Wrappers are immutable, and Java is always pass-by-value. `x = x + 1` inside the method boxes a **new** `Integer` and
re-points the parameter; the caller still sees 10 (checked on a JVM). Wrappers exist for collections and generics,
for `null`, and for their utility methods.
</MythVsFact>

<MythVsFact myth="Passing a reference variable works like a C++ reference parameter." audit="6.4">
It works like passing a C++ **pointer by value** (`void f(Account* a)`): the method can change the object through it,
and changing the pointer itself stays local. C++ `Account&` parameters alias the caller's variable, which Java can't
do; and unlike pointers, Java references have no arithmetic and can't dangle.
</MythVsFact>

<MythVsFact myth="Since arguments are copies, a method can't change anything its caller has.">
It can't change the caller's **variables**, but it can change any mutable **object** it received: fill an array,
sort a list, append to a `StringBuilder`, set a field. That's useful when intended and a nasty bug when not.
</MythVsFact>

<MythVsFact myth="Declaring a parameter final protects the caller's object.">
`final` only stops the method from reassigning the parameter. Methods can still mutate the object; to protect it, pass
an immutable object or a copy.
</MythVsFact>

## Doubts cleared

<FaqItem q="So is Java pass-by-reference for objects?">
No. It passes a **reference by value**. The test is whether a method can make the caller's variable refer to a
different object: in Java it can't.
</FaqItem>

<FaqItem q="Then why does `Arrays.sort(numbers)` change my array?">
Because it never reassigns anything: it follows the copied reference and rearranges the elements of the one array you
both share.
</FaqItem>

<FaqItem q="Does passing a big object copy it? Is it slow?">
No. Only the reference is copied, a few bytes, whatever the object's size. If you need a copy, you make it explicitly
(`clone()`, `List.copyOf`, a copy constructor).
</FaqItem>

<FaqItem q="Are return values copied too?">
Yes, by value as well: a returned primitive is a copy of the number, a returned object is a copy of the reference, so
the caller shares the object the method returned.
</FaqItem>

<FaqItem q="How do I return two values?">
Return a record (`record MinMax(int min, int max)`) or another small class. Record patterns (Java 21) make it easy to
take the result apart: `if (minMax(values) instanceof MinMax(int lo, int hi)) …`.
</FaqItem>

<FaqItem q="Should I declare every parameter final?">
Some teams do, so that reassigning a parameter is a compile error. Many rely on a linter rule against parameter
reassignment instead. Either way, `final` doesn't make the object immutable.
</FaqItem>

<FaqItem q="Why must local variables used in a lambda be effectively final?">
The lambda gets a copy of the value. If the variable could change afterwards, the lambda's copy and the variable
would silently disagree, so the language forbids it (JLS §15.27.2).
</FaqItem>

<FaqItem q="Is it bad practice for a method to modify its argument?">
Not if that's its job and its name says so (`Collections.sort`, `List.addAll`, `appendTo(StringBuilder)`). It's a
problem when a method that looks like a query changes its input as a side effect.
</FaqItem>

<FaqItem q={'What does "call by sharing" mean?'}>
A name for Java's (and Python's) model: arguments are passed by value, and since the values are references, the
caller and the method share the objects. It describes the same rules, not a third mechanism.
</FaqItem>

## Pitfalls and best practices

| ✅ Do | ❌ Don't |
|---|---|
| Return results, and a record for several values | Reassign a parameter and expect the caller to see it |
| Name methods that mutate arguments clearly (`sortInPlace`) | Change an argument inside a method that looks like a query |
| Copy mutable arguments you store, and mutable fields you return | Store or hand out a caller's list or array as is |
| Prefer immutable types for values passed around | Use wrappers or one-element arrays to fake pass-by-reference |
| Work on a copy when you only need to read and reorder | Sort or clear a collection you were only given to read |

## Senior lens

<Callout type="senior" title="Explain it to your team in 60 seconds">
"Java copies every argument into a new parameter variable. For objects that copy is a reference, so the method shares
the caller's object: it can mutate it, but reassigning the parameter never affects the caller, which is why swap can't
work. In our code that means: return results instead of filling in parameters, don't mutate what you were given to
read, copy mutable data at API boundaries, and prefer immutable types so sharing is harmless."
</Callout>

**Where pass-by-value shows up in production bugs**

| Symptom | Cause | Fix |
|---|---|---|
| A method "does nothing" for its caller | It reassigned a parameter | Return the new value |
| Data changes after being passed to a harmless-looking helper | The helper mutated a shared list or array | Work on a copy; make inputs immutable |
| An object's state changes without any call to it | It stored a caller's mutable object | Defensive copy in the constructor |
| Callers can corrupt internal state | A getter returns a mutable field | Return a copy or an unmodifiable view |

**Code-review checklist**
- [ ] No parameter is reassigned with the expectation that the caller sees it.
- [ ] Methods that change their arguments say so in their name and documentation.
- [ ] Mutable arguments stored in fields are copied; mutable fields aren't returned directly.
- [ ] Several results come back as a record, not through output parameters.

## Modern Java

- <VersionBadge since={8} jep={126} /> Lambdas may use only final or effectively final local variables, because they
  capture copies of their values.
- <VersionBadge since={10} /> `List.copyOf`, `Set.copyOf` and `Map.copyOf`: one-line defensive copies that are
  unmodifiable.
- <VersionBadge since={16} jep={395} /> Records: the natural way to return several values from a method.
- <VersionBadge since={21} jep={440} /> Record patterns, to take a returned record apart where it's used.
- <VersionBadge since={25} /> The rule itself has never changed: arguments have been passed by value since Java 1.0.

```java title="Results.java (solution)"
package track.pass_by_value;

import java.util.Locale;

/** Reference solution for the Results exercise. */
public final class Results {

    public record Pair(int first, int second) {
    }

    public record MinMax(int min, int max) {
    }

    private Results() {
    }

    public static void swap(int[] values, int i, int j) {
        int tmp = values[i];                    // the array is shared: the caller sees the exchange
        values[i] = values[j];
        values[j] = tmp;
    }

    public static Pair swapped(Pair pair) {
        return new Pair(pair.second(), pair.first());
    }

    public static MinMax minMax(int[] values) {
        if (values.length == 0) {
            throw new IllegalArgumentException("no values");
        }
        int min = values[0];
        int max = values[0];
        for (int v : values) {                  // read only: sorting would reorder the caller's array
            min = Math.min(min, v);
            max = Math.max(max, v);
        }
        return new MinMax(min, max);
    }

    public static void rotateRight(int[] values) {
        if (values.length < 2) {
            return;
        }
        int last = values[values.length - 1];
        System.arraycopy(values, 0, values, 1, values.length - 1);    // overlapping copies are handled correctly
        values[0] = last;
    }

    public static String shout(String text) {
        return text.strip().toUpperCase(Locale.ROOT) + "!";
    }
}
```

```java title="Roster.java (solution)"
package track.pass_by_value;

import java.util.ArrayList;
import java.util.Comparator;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

/** Reference solution for the Roster exercise. */
public final class Roster {
    private final List<String> players;                     // an unmodifiable copy
    private final int[] scores;                             // our own array, never handed out
    private final Map<String, Integer> index = new HashMap<>();

    public Roster(List<String> players, int[] scores) {
        this.players = List.copyOf(players);                // copy in (null list or player → NPE)
        this.scores = scores.clone();                       // copy in (null array → NPE)
        if (this.players.size() != this.scores.length) {
            throw new IllegalArgumentException(this.players.size() + " players but " + this.scores.length + " scores");
        }
        for (int i = 0; i < this.players.size(); i++) {
            if (index.put(this.players.get(i), i) != null) {
                throw new IllegalArgumentException("duplicate player: " + this.players.get(i));
            }
        }
    }

    public List<String> players() {
        return players;                                     // safe to share: nobody can modify it
    }

    public int[] scores() {
        return scores.clone();                              // copy out
    }

    public int score(String player) {
        return scores[indexOf(player)];
    }

    public void addPoints(String player, int points) {
        scores[indexOf(player)] += points;
    }

    public List<String> top(int k) {
        if (k < 0) {
            throw new IllegalArgumentException("negative k: " + k);
        }
        List<String> ranking = new ArrayList<>(players);    // sort a copy, never our own state
        ranking.sort(Comparator.comparingInt((String p) -> score(p)).reversed()
                .thenComparing(Comparator.naturalOrder()));
        return List.copyOf(ranking.subList(0, Math.min(k, ranking.size())));
    }

    private int indexOf(String player) {
        Integer i = index.get(player);
        if (i == null) {
            throw new IllegalArgumentException("unknown player: " + player);
        }
        return i;
    }
}
```

```java title="GraphCopy.java"
                }
```

```java title="GraphCopy.java (solution)"
package track.pass_by_value;

import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.Collections;
import java.util.Deque;
import java.util.IdentityHashMap;
import java.util.List;
import java.util.Map;
import java.util.Set;

/** Reference solution for the GraphCopy exercise. */
public final class GraphCopy {

    /** A node: identity matters, so it deliberately doesn't override equals and hashCode. */
    public static final class Node {
        public int value;
        public final List<Node> next = new ArrayList<>();

        public Node(int value) {
            this.value = value;
        }
    }

    private GraphCopy() {
    }

    public static Node deepCopy(Node root) {
        return deepCopyAll(Collections.singletonList(root)).get(0);
    }

    public static List<Node> deepCopyAll(List<Node> roots) {
        Map<Node, Node> copies = new IdentityHashMap<>();       // original → its copy, by identity
        Deque<Node> todo = new ArrayDeque<>();                  // originals whose references still need copying
        List<Node> out = new ArrayList<>(roots.size());
        for (Node root : roots) {
            out.add(root == null ? null : copyOf(root, copies, todo));
        }
        while (!todo.isEmpty()) {
            Node original = todo.pop();
            Node copy = copies.get(original);
            for (Node target : original.next) {
                copy.next.add(target == null ? null : copyOf(target, copies, todo));
            }
        }
        return out;
    }

    public static int countNodes(Node root) {
        if (root == null) {
            return 0;
        }
        Set<Node> seen = Collections.newSetFromMap(new IdentityHashMap<>());
        Deque<Node> todo = new ArrayDeque<>();
        seen.add(root);
        todo.push(root);
        while (!todo.isEmpty()) {
            for (Node target : todo.pop().next) {
                if (target != null && seen.add(target)) {
                    todo.push(target);
                }
            }
        }
        return seen.size();
    }

    /** The copy of a node: created, and queued for its references, the first time the node is met. */
    private static Node copyOf(Node original, Map<Node, Node> copies, Deque<Node> todo) {
        Node copy = copies.get(original);
        if (copy == null) {
            copy = new Node(original.value);
            copies.put(original, copy);
            todo.push(original);
        }
        return copy;
    }
}
```

| **Object argument** | The reference is copied: one object, two arrows |
| **Mutate** | `param.field = …`, `list.add`, `arr[i] = …`: the caller sees it |
| **Reassign** | `param = new …`: only the method's copy moves |
| **Swap test** | No method can swap its caller's variables; swap elements or return a pair |
| **Immutables** | `String`, wrappers, records of immutables: a method can't change them at all (audit 6.10) |
| **Results** | Return a value; a record for several; `Optional` for maybe |
| **Boundaries** | Copy mutable arguments you keep and mutable fields you hand out (`List.copyOf`, `clone()`) |
