## Why this matters

In 2006 Joshua Bloch reported that the binary search in `java.util.Arrays`, used for about nine years, had a bug in a
single line: `int mid = (low + high) / 2;`. For arrays larger than about a billion elements, `low + high` overflows
and becomes negative, and the search throws `ArrayIndexOutOfBoundsException`. The same week, somebody else's code
divided `done / total` in `int` and showed a progress bar stuck at 0%, and another service crashed on
`name.isEmpty() || name == null`. Operators look like school maths, but each one has precise Java rules: types,
evaluation order, what happens at the edges. Those rules are this lesson.

## TL;DR

<Callout type="tldr">
- An **operator** is an action, an **operand** is what it acts on, and an **expression** combines them into a value
  of one type.
- `+ - * / %` follow the operand types: `int` division **truncates toward zero** (`-5 / 2 == -2`), `%` has the **sign
  of the dividend** (`-5 % 2 == -1`), and integer division by zero throws `ArithmeticException`, while `5.0 / 0` is
  `Infinity`.
- `+` with a `String` operand **concatenates**, left to right: `1 + 2 + "3"` is `"33"`, `"1" + 2 + 3` is `"123"`.
- Comparisons `== != < > <= >=` promote numbers first and produce a `boolean`. On objects, `==` compares
  **identity**, not contents; with `NaN` every comparison except `!=` is false.
- `&&` and `||` **short-circuit**: the right operand is evaluated only if the left one doesn't decide the result.
  `&`, `|` and `^` on booleans always evaluate both sides.
</Callout>

## Mental model

An expression is a small **assembly line**. Each operator is a machine that takes typed parts (operands) and produces
one typed part. The machine is chosen by the **types** of its inputs: `+` on two `int`s is an integer adder, on a
`String` it's a text joiner, on two `double`s a floating-point adder. The line runs **left to right**.

`&&` and `||` are machines with a **shortcut**: they look at the left part first, and if that already decides the
answer, the right part is never built, including any work (or crash) it would have caused.

Where it breaks: precedence decides which machine gets which parts (`a + b * c`), but not the order in which the parts
are produced. That's always left to right ([Ternary, instanceof & Precedence](/lessons/ternary-instanceof-precedence/)).

## Concept, step by step

### 1. Operators, operands, expressions

Your notes define the three terms well:

- An **operator** says which action to perform: `+`, `<`, `&&`.
- An **operand** is an item the action applies to: in `5 + 3`, the operands are `5` and `3`.
- An **expression** consists of one or more operands and zero or more operators, and produces a value: `5 + 3` as a
  whole. A lone `5` or a variable `x` is an expression too.

Every expression has a **type**, known at compile time: `5 + 3` is an `int`, `5 + 3.0` a `double`, `5 < 3` a
`boolean`. That type decides what the operator does and where the result may go.

### 2. Arithmetic: `+ - * / %`

With your notes' demo values:

```java title="Arithmetic.java"
public class Arithmetic {
    public static void main(String[] args) {
        int a = 5, b = 2;
        System.out.println(a + b);     // 7
        System.out.println(a - b);     // 3
        System.out.println(a * b);     // 10
        System.out.println(a / b);     // 2: integer division
        System.out.println(a % b);     // 1: the remainder
    }
}
```

```text output
7
3
10
2
1
```

The operand types decide the kind of arithmetic ([binary numeric promotion](/lessons/type-conversion/#3-numeric-promotion-in-expressions)):
two `int`s give `int` arithmetic, and one `double` operand makes it `double` arithmetic. The rules that surprise
people, all verified on a JVM:

| Expression | Result | Rule |
|---|---|---|
| `5 / 2`, `-5 / 2` | `2`, `-2` | Integer division **truncates toward zero** |
| `-5 % 2`, `5 % -2` | `-1`, `1` | `%` is a **remainder**: its sign is the sign of the **dividend** (left operand) |
| `Math.floorMod(-5, 2)` | `1` | The mathematical modulo: sign of the divisor, always `0..b-1` for positive `b` |
| `5 / 0`, `5 % 0` | `ArithmeticException: / by zero` | Only for **integer** types |
| `5.0 / 0`, `-5.0 / 0`, `0.0 / 0` | `Infinity`, `-Infinity`, `NaN` | Floating point follows IEEE 754 ([Floating Point](/lessons/floating-point/)) |
| `5.5 % 2` | `1.5` | `%` works on `double`s too |
| `Integer.MAX_VALUE + 1` | `-2147483648` | Integer overflow wraps silently ([Integer Types](/lessons/integer-types/)) |

`(a / b) * b + (a % b) == a` always holds for integers (except division by zero): division and remainder are two
halves of one operation.

### 3. `+` on strings: concatenation

If **either** operand of `+` is a `String`, the other is converted to a string and the two are joined
(JLS §15.18.1). Because `+` groups **left to right**, the position of the string matters:

```java title="Concatenation"
System.out.println(1 + 2 + "3");        // "33": 1 + 2 is 3 first, then "3" + "3"
System.out.println("1" + 2 + 3);        // "123": "1" + 2 is "12", then "12" + 3
System.out.println("1" + (2 + 3));      // "15": parentheses first
System.out.println('a' + 'b' + "c");    // "195c": char + char is int arithmetic
System.out.println("Total: " + null);   // "Total: null"
```

Any value can be concatenated: objects through `toString()`, `null` as `"null"`. Inside loops, repeated `s += x`
creates a new string each time; use a `StringBuilder` ([Strings](/lessons/strings/)).

### 4. Relational operators: comparing values

`==`, `!=`, `<`, `>`, `<=` and `>=` compare two operands and produce a `boolean`. With your notes' values
`a = 4`, `b = 7`: `a == b` is `false`, `a != b` is `true`, `a > b` is `false`, `a < b` is `true`, `a >= b` is `false`
and `a <= b` is `true`.

Things to know:

- **Numbers are promoted first.** `'a' < 98` compares 97 with 98 (true). `0.1f == 0.1` is **false**: the `float`
  is widened to the `double` 0.10000000149011612, which isn't the `double` 0.1.
- **NaN is unordered.** `NaN == NaN`, `NaN < 1` and `NaN > 1` are all false; only `NaN != x` is true. Use
  `Double.isNaN(x)`.
- **`==` on objects compares identity**: are they the same object? Two equal strings can be different objects, so
  compare contents with `equals`. `Integer` values from −128 to 127 are cached, so `==` on boxed numbers even seems to
  work sometimes (`Integer` 127 == 127 is true, 128 == 128 false, verified). See
  [Wrappers & Boxing](/lessons/wrappers-boxing/).
- **No chaining.** `1 < x < 5` doesn't compile: `1 < x` is a `boolean`, and `boolean < int` makes no sense. Write
  `1 < x && x < 5`.

### 5. Logical operators and short-circuiting

`&&` (and), `||` (or) and `!` (not) combine `boolean` values:

| `a` | `b` | `a && b` | `a \|\| b` | `a ^ b` | `!a` |
|---|---|---|---|---|---|
| false | false | false | false | false | true |
| false | true | false | true | true | true |
| true | false | false | true | true | false |
| true | true | true | true | false | false |

Your notes say "if one condition is false, `&&` won't evaluate further conditions". The precise rule is about
**order**: operands are evaluated **left to right**, and `&&` skips its **right** operand when the **left** one is
false; `||` skips its right operand when the left one is **true**.

<ShortCircuit />

```java title="ShortCircuit.java"
public class ShortCircuit {
    public static void main(String[] args) {
        int x = 0;
        System.out.println((x != 0) && (10 / x > 1));   // false: 10 / x never runs
        System.out.println((x == 0) || (10 / x > 1));   // true: 10 / x never runs
        System.out.println((x != 0) & (10 / x > 1));    // & evaluates both: ArithmeticException
    }
}
```

```text output
false
true
Exception in thread "main" java.lang.ArithmeticException: / by zero
	at ShortCircuit.main(ShortCircuit.java:6)
```

This is why `if (name != null && !name.isEmpty())` is safe, and why the order of the checks matters. On booleans,
`&`, `|` and `^` (exclusive or: true when exactly one side is true) are the **non-short-circuit** versions: both sides
always run. They're rarely what you want, except when the right side has a side effect that must always happen.

Two rewriting rules (De Morgan's laws) help simplify conditions: `!(a && b)` equals `!a || !b`, and `!(a || b)`
equals `!a && !b`.

## Scenarios

<Tabs>
<TabItem label="Real world: a progress bar stuck at 0%">

```java title="Progress.java"
public class Progress {
    public static void main(String[] args) {
        int done = 37, total = 80;
        int wrong = done / total * 100;            // 37 / 80 is 0 in int arithmetic
        int better = done * 100 / total;           // 3700 / 80 = 46
        long rounded = Math.round(100.0 * done / total);   // 46.25 → 46
        System.out.println(wrong + " " + better + " " + rounded);
    }
}
```

```text output
0 46 46
```

`done / total` truncates to 0 for every `done` below `total`, so the bar jumps from 0 to 100 at the end. Multiply
first, or compute in `double` and round deliberately. Watch the range when multiplying first: `done * 100` overflows
an `int` for `done` above 21 million; use `long` or `double` then.

</TabItem>
<TabItem label="Edge case: the order of a null check">

```java title="NullCheck.java"
public class NullCheck {
    static boolean isBlank(String s) {
        return s == null || s.isBlank();             // null is checked first: safe
    }

    static boolean isBlankBroken(String s) {
        return s.isBlank() || s == null;             // NullPointerException before the null check runs
    }

    public static void main(String[] args) {
        System.out.println(isBlank(null));
        System.out.println(isBlank("  "));
        System.out.println(isBlankBroken(null));
    }
}
```

```text output
true
true
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "String.isBlank()" because "<parameter1>" is null
	at NullCheck.isBlankBroken(NullCheck.java:7)
	at NullCheck.main(NullCheck.java:13)
```

Short-circuiting protects you only if the guard comes **first**. The same applies to bounds checks
(`i < arr.length && arr[i] > 0`) and to expensive checks: put the cheap, likely-to-decide condition on the left. (The
exact NullPointerException message depends on whether the class was compiled with parameter names.)

</TabItem>
<TabItem label="Real world: the binary search midpoint">

```java title="Midpoint.java"
public class Midpoint {
    public static void main(String[] args) {
        int low = 1_500_000_000, high = 2_000_000_000;
        System.out.println((low + high) / 2);        // overflow: negative
        System.out.println(low + (high - low) / 2);  // stays in range
        System.out.println((low + high) >>> 1);      // unsigned shift: also correct
    }
}
```

```text output
-397483648
1750000000
1750000000
```

`low + high` is 3,500,000,000, beyond `Integer.MAX_VALUE`, so it wraps to −794,967,296, and half of that is a
negative index. `low + (high - low) / 2` never exceeds `high`. `(low + high) >>> 1` treats the wrapped sum as an
unsigned 32-bit number, which is still correct for non-negative `low` and `high` ([Bitwise & Shift
Operators](/lessons/bitwise-and-shift-operators/)); it's the fix the JDK adopted.

</TabItem>
<TabItem label="Anti-pattern → fix: == on strings">

```java title="Anti-pattern"
String answer = readLine();                     // the user types: yes
if (answer == "yes") { … }                      // false: a different String object
```

`==` asks "the same object?", and a string read at run time is a new object even if its characters are `yes`. It may
seem to work in tests with literals (identical literals share one object), which makes the bug worse.

```java title="Fix"
if ("yes".equals(answer)) { … }                 // compares contents; also safe when answer is null
if ("yes".equalsIgnoreCase(answer)) { … }       // if case doesn't matter
```

</TabItem>
</Tabs>

## Under the hood

<details>
<summary>What the compiler and the JVM do with these operators</summary>

- **Typed instructions.** `int` arithmetic compiles to `iadd`, `isub`, `imul`, `idiv`, `irem`; `long` to `ladd`…;
  `double` to `dadd`…, `ddiv`, `drem`. Only `idiv`, `irem`, `ldiv` and `lrem` throw `ArithmeticException` on a zero
  divisor; the floating-point instructions follow IEEE 754 (JVMS §6.5).
- **There is no "and" instruction for `&&`.** `a && b` compiles to conditional jumps: test `a`, jump past `b` if it's
  false. That jump *is* the short circuit. `a & b` on booleans compiles to `iand`, after both operands are on the
  stack.
- **Comparisons are jumps too.** `if (x < y)` becomes `if_icmpge` (jump to the else branch). For `double`, `dcmpl`
  and `dcmpg` differ only in how they treat NaN, so that every comparison with NaN comes out false.
- **String concatenation** has compiled to a single `invokedynamic` call since Java 9 (JEP 280). The JVM then builds
  an optimised concatenation strategy at run time, instead of the old chain of `StringBuilder.append` calls.
- **The JIT optimises arithmetic.** Division by a constant typically becomes a multiplication and shifts, and many
  checks are removed when the compiler can prove they're redundant. Write the clear version; measure before
  hand-optimising.

</details>

## Myths vs facts

<MythVsFact myth="&& stops evaluating as soon as any condition is false." audit="20.5">
Evaluation is strictly **left to right**. `a && b` skips `b` only when `a` (the **left** operand) is false; `a || b`
skips `b` when `a` is **true**. In a chain `a && b && c`, each `&&` applies the rule to what's on its left. The
non-short-circuit `&`, `|` and `^` always evaluate both sides (verified: `&` triggered the division by zero that `&&`
avoided).
</MythVsFact>

<MythVsFact myth="There are 7 categories of operators in Java." audit="20.2">
The notes themselves list **9**: arithmetic, relational, logical, unary, assignment, bitwise, shift, ternary and type
comparison (`instanceof`). The JLS doesn't define "categories" at all: it specifies each operator in chapter 15, and
the grouping is a teaching device.
</MythVsFact>

<MythVsFact myth="% is the modulo operator.">
It's the **remainder** operator: its result has the sign of the dividend, so `-5 % 2` is −1, not 1. That breaks
"is it odd?" checks (`n % 2 == 1` is false for −3) and cyclic indexes. Use `n % 2 != 0`, or `Math.floorMod` when you
need a result from 0 to `b − 1`.
</MythVsFact>

<MythVsFact myth="Dividing by zero always throws an exception.">
Only **integer** division and remainder throw (`ArithmeticException: / by zero`). Floating-point division gives
`Infinity`, `-Infinity` or `NaN` without any error, so a zero divisor in `double` code silently spreads `NaN`.
</MythVsFact>

<MythVsFact myth="== compares values.">
For primitives, yes. For objects, `==` compares **references**: whether both sides are the same object. Strings,
boxed numbers and all other objects need `equals` for a content comparison.
</MythVsFact>

## Doubts cleared

<FaqItem q="Why is `-5 / 2` equal to −2 and not −3?">
Java's integer division truncates toward zero (JLS §15.17.2), like C and most CPUs. Mathematical floor division gives
−3: that's `Math.floorDiv(-5, 2)`.
</FaqItem>

<FaqItem q="How do I check whether a number is odd?">
`n % 2 != 0` works for negative numbers too. `n % 2 == 1` fails for negative odd numbers, because `-3 % 2` is −1.
(`(n & 1) == 1` also works; see the bitwise lesson.)
</FaqItem>

<FaqItem q={'Why does `1 + 2 + "3"` give 33, but `"1" + 2 + 3` give 123?'}>
`+` is evaluated left to right. In the first expression `1 + 2` is integer addition (3) before a string appears; in
the second, `"1" + 2` is already a string, so every following `+` concatenates.
</FaqItem>

<FaqItem q="Should I use `&` or `&&` in conditions?">
`&&` (and `||`), almost always. They skip work and protect guarded expressions. Use `&`/`|` on booleans only when both
sides must run, for example two validation methods that each record their own error, and write a comment saying so.
</FaqItem>

<FaqItem q="Can I compare strings with `<` or `>`?">
No: relational operators work only on numbers (and `char`). Use `a.compareTo(b)` (negative, zero or positive), or a
`Comparator` such as `String.CASE_INSENSITIVE_ORDER` ([Comparable & Comparator](/lessons/comparable-and-comparator/)).
</FaqItem>

<FaqItem q="Why is `0.1 + 0.2 == 0.3` false?">
None of the three values is exactly representable in binary, and the rounded sum differs from the rounded 0.3 in the
last bit. Compare with a tolerance (`Math.abs(a - b) < 1e-9`) or use `BigDecimal` for exact decimals
([Floating Point](/lessons/floating-point/)).
</FaqItem>

<FaqItem q="What happens with `Integer.MIN_VALUE / -1`?">
The true result, 2,147,483,648, doesn't fit, so it wraps to `Integer.MIN_VALUE` without an exception (JLS §15.17.2).
`Math.divideExact` (Java 18) throws instead.
</FaqItem>

<FaqItem q="Is `a + b` evaluated before `c` in `a + b * c`?">
The **operands** are evaluated left to right: `a`, then `b`, then `c`. Precedence only decides the **grouping**: the
multiplication `b * c` happens before the addition. With plain variables the difference is invisible; with method
calls or `++` it matters ([Ternary, instanceof & Precedence](/lessons/ternary-instanceof-precedence/)).
</FaqItem>

## Pitfalls and best practices

| ✅ Do | ❌ Don't |
|---|---|
| Multiply before dividing, or compute in `double`, for ratios and percentages | Write `done / total * 100` with `int`s |
| Put null and bounds checks on the **left** of `&&` / `\|\|` | Call a method before checking its receiver for null |
| Use `Math.floorMod` for cyclic indexes and "clock" arithmetic | Assume `%` never returns a negative number |
| Compute midpoints as `low + (high - low) / 2` | Write `(low + high) / 2` for large ranges |
| Compare objects with `equals`, strings with `"literal".equals(x)` | Compare strings or boxed numbers with `==` |
| Check `Double.isNaN` explicitly | Expect `x == Double.NaN` to ever be true |

## Senior lens

<Callout type="senior" title="Explain it to your team in 60 seconds">
"Java operators are typed: the operand types, not the values, decide whether you get integer or floating-point
arithmetic and whether `+` adds or concatenates. Integer division truncates and `%` keeps the dividend's sign; floats
never throw on zero. `&&` and `||` evaluate left to right and stop early, so guards go first. And `==` on objects is
identity: we compare contents with `equals`."
</Callout>

**Where these operators cause production bugs**

| Place | Symptom | Prevention |
|---|---|---|
| Ratios, percentages, averages | Always 0 or rounded down | Widen or multiply first; tests with non-divisible values |
| Midpoints, sums of indexes, sizes | Negative indexes on huge inputs | Overflow-safe formulas, `Math.addExact` |
| Hash buckets, time slots, ring buffers | Negative index for negative input | `Math.floorMod` |
| Validation chains | `NullPointerException` on missing input | Guard first; `Objects.requireNonNull` at boundaries |
| Money totals compared with `==` | Equal amounts reported as different | `BigDecimal.compareTo` or integer minor units |
| String or `Integer` comparison with `==` | Works in tests, fails in production | `equals`; static analysis (reference equality checks) |

**Code-review checklist**
- [ ] Every `/` on integers: is truncation intended? Could the divisor be zero?
- [ ] Every `%`: can the dividend be negative?
- [ ] Conditions: guards first; no `&`/`|` on booleans without a comment.
- [ ] No `==` between objects unless identity is really meant.

## Modern Java

- <VersionBadge since={8} /> `Math.floorDiv`, `Math.floorMod`, and the exact methods (`Math.addExact`…).
- <VersionBadge since={9} /> String concatenation compiled to `invokedynamic` (JEP 280): faster, with no change to
  the language.
- <VersionBadge since={11} /> `String.isBlank()`, handy for input checks like the one above.
- <VersionBadge since={18} /> `Math.ceilDiv`, `Math.ceilMod` and `Math.divideExact`.
- The operators themselves haven't changed since Java 1.0. What changed is around them: pattern matching makes
  `instanceof` checks and `switch` more expressive (see the next lessons).

```java title="FloorMath.java (solution)"
package track.operators_arithmetic_relational_logical;

/** Reference solution for the FloorMath exercise. */
public final class FloorMath {

    private FloorMath() {
    }

    public static int floorDiv(int a, int b) {
        int q = a / b;                                  // truncates toward zero; throws for b == 0
        boolean inexact = a % b != 0;
        boolean signsDiffer = (a < 0) != (b < 0);
        return inexact && signsDiffer ? q - 1 : q;      // negative, inexact quotients round down one more
    }

    public static int floorMod(int a, int b) {
        int r = a % b;                                  // has the sign of a
        boolean signsDiffer = (r < 0) != (b < 0);
        return r != 0 && signsDiffer ? r + b : r;       // move it into b's sign: a - floorDiv(a, b) * b
    }
}
```

```java title="Calculator.java (solution)"
package track.operators_arithmetic_relational_logical;

/** Reference solution for the Calculator exercise: a recursive-descent parser that computes as it parses. */
public final class Calculator {

    private final String text;
    private int pos;

    private Calculator(String text) {
        this.text = text;
    }

    public static int evaluate(String expression) {
        Calculator c = new Calculator(expression);
        int value = c.expression();
        c.skipSpaces();
        if (c.pos != c.text.length()) {
            throw new IllegalArgumentException("unexpected '" + c.text.charAt(c.pos) + "' at " + c.pos);
        }
        return value;
    }

    private int expression() {
        int value = term();
        while (true) {
            if (accept('+')) {
                value = value + term();         // int arithmetic: overflow wraps, exactly like Java
            } else if (accept('-')) {
                value = value - term();
            } else {
                return value;
            }
        }
    }

    private int term() {
        int value = factor();
        while (true) {
            if (accept('*')) {
                value = value * factor();
            } else if (accept('/')) {
                value = value / factor();       // truncates; throws ArithmeticException for 0
            } else if (accept('%')) {
                value = value % factor();
            } else {
                return value;
            }
        }
    }

    private int factor() {
        if (accept('-')) {
            return -factor();
        }
        if (accept('(')) {
            int value = expression();
            if (!accept(')')) {
                throw new IllegalArgumentException("missing ')' at " + pos);
            }
            return value;
        }
        skipSpaces();
        int start = pos;
        while (pos < text.length() && Character.isDigit(text.charAt(pos))) {
            pos++;
        }
        if (start == pos) {
            throw new IllegalArgumentException("number expected at " + pos);
        }
        return Integer.parseInt(text, start, pos, 10);  // at most 2147483647 by the grammar
    }

    private boolean accept(char c) {
        skipSpaces();
        if (pos < text.length() && text.charAt(pos) == c) {
            pos++;
            return true;
        }
        return false;
    }

    private void skipSpaces() {
        while (pos < text.length() && text.charAt(pos) == ' ') {
            pos++;
        }
    }
}
```

## Cheat sheet

<CheatSheet>

| Topic | Remember |
|---|---|
| **Terms** | operator = action · operand = input · expression = operands + operators → one typed value |
| **Categories** | arithmetic, relational, logical, unary, assignment, bitwise, shift, ternary, `instanceof` (9, not 7) |
| **Integer `/` and `%`** | `/` truncates toward zero (`-5/2 == -2`); `%` has the dividend's sign (`-5%2 == -1`); `/ 0` throws |
| **Floor versions** | `Math.floorDiv(-5, 2) == -3`, `Math.floorMod(-5, 2) == 1` |
| **Floating point** | `5.0/0` = `Infinity`, `0.0/0` = `NaN`, `5.5 % 2` = `1.5`; never throws |
| **String `+`** | left to right: `1 + 2 + "3"` = `"33"`, `"1" + 2 + 3` = `"123"`; `'a' + 'b'` = 195 |
| **Comparisons** | promote first (`0.1f == 0.1` is false); NaN compares false; `==` on objects = identity |
| **Logical** | `&&` skips right if left false; `\|\|` skips right if left true; `& \| ^` evaluate both |
| **De Morgan** | `!(a && b) == !a \|\| !b` · `!(a \|\| b) == !a && !b` |
