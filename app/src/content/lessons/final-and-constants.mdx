## Why this matters

A team changes `public static final int MAX_RETRIES = 3;` to `5` in a shared library, releases a new jar, and upgrades
it in production. The services keep retrying 3 times. Nobody made a mistake in the code: the value `3` was copied
into every class that used it when **those** classes were compiled, and they weren't recompiled. In another service, a
`public static final List<String> ADMINS` "constant" gains an entry at run time because some code calls
`ADMINS.add(...)`. `final` looks like a simple keyword, but what it guarantees (and what it doesn't) decides whether
your constants are really constant and whether your objects are really safe to share.

## TL;DR

<Callout type="tldr">
- `final` on a variable means it can be **assigned only once** (JLS §4.12.4). The compiler checks it; a `final` field
  must be assigned by the end of every constructor (or static initializer, for `static` fields).
- A constant is `static final` **with a type**: `static final int VAR = 10;` (the notes' `static final VAR = 10;`
  doesn't compile). By convention it's named in `UPPER_SNAKE_CASE`.
- `final` fixes the **variable**, not the **object**: a `final List` can still be modified. For true constants, use
  immutable objects (`List.of`, records, `String`).
- A `final` variable of primitive or `String` type initialised with a constant expression is a **compile-time
  constant**: usable in `case` labels, foldable, and **copied into other classes at compile time**.
- **Effectively final** locals (never reassigned) can be captured by lambdas and anonymous classes.
- `final` on methods forbids overriding, on classes forbids subclassing. `final` fields also give safe publication in
  concurrent code, and JDK 26 starts warning when reflection changes them.
</Callout>

## Mental model

A variable is a **labelled arrow**. `final` **welds the arrow in place**: once it points somewhere, it can never be
pointed elsewhere. Whether the thing it points to can change is a separate question: a welded arrow can point to a
whiteboard (a mutable object) that anyone can still write on, or to a printed page (an immutable object) that can't
change. Only a welded arrow to a printed page is a true constant.

Compile-time constants are special: the compiler doesn't even keep the arrow; it **photocopies the value** into every
place that uses it.

## Concept, step by step

### 1. `final` variables: assigned exactly once

`final` can be applied to every kind of variable ([Kinds of Variables](/lessons/variable-kinds/)):

```java title="FinalBasics.java"
public class FinalBasics {
    static final double VAT_RATE = 0.2;          // a constant: static (one copy) and final (never reassigned)
    private final String id;                     // a blank final field: assigned once, in the constructor

    FinalBasics(String id) {
        this.id = id;
    }

    public static void main(String[] args) {
        final int limit;                          // a blank final local
        limit = args.length > 0 ? 10 : 5;         // assigned exactly once
        FinalBasics order = new FinalBasics("A-17");
        // limit = 20;                           // error: variable limit might already have been assigned
        // order.id = "B";                       // error: cannot assign a value to final variable id
        System.out.println(order.id + " " + limit + " " + VAT_RATE);
    }
}
```

```text output
A-17 5 0.2
```

| Kind | Where it must be assigned | Typical use |
|---|---|---|
| `final` local | Before its first use, once (a **blank final** may be assigned after the declaration) | Values that mustn't change in a long method |
| `final` parameter | By the call; can't be reassigned in the body | Style: prevents accidental reassignment |
| `final` instance field | In its initializer, an instance initializer, or **every** constructor | Immutable state of an object |
| `static final` field | In its initializer or a static initializer | Constants and shared, never-replaced objects |

The compiler enforces "exactly once" with **definite assignment** analysis (JLS chapter 16): it rejects code where a
`final` variable might be read before it's assigned, or assigned twice.

### 2. Declaring constants: the notes' example, corrected

The notes write a constant as `static final VAR = 10;` and explain it well: `static` means only one copy exists,
`final` means the value can't be changed. The declaration itself is missing its **type**, so it doesn't compile
(audit 6.13). The correct form:

```java title="Limits.java"
import java.time.Duration;

public final class Limits {
    public static final int MAX_USERS = 100;                  // UPPER_SNAKE_CASE for constants
    public static final String DEFAULT_REGION = "eu-west-1";
    public static final Duration TIMEOUT = Duration.ofSeconds(30);   // an immutable object: also constant

    private Limits() {
    }
}
```

`static` isn't what makes it constant: it makes one shared copy instead of one per object. A `final` instance field is
fixed per object (an order's id) but differs between objects. Put constants in the class that owns the concept, use an
**enum** for a fixed set of related values ([Enums in Depth](/lessons/enums/)), and avoid "constant interfaces" that
exist only to hold constants.

### 3. `final` is not immutable

```java title="FinalRefs.java"
import java.util.ArrayList;
import java.util.List;

public class FinalRefs {
    public static void main(String[] args) {
        final List<String> names = new ArrayList<>();
        names.add("Ann");                             // fine: the list itself is mutable
        final int[] scores = {1, 2};
        scores[0] = 99;                               // fine: array elements can change
        final List<String> frozen = List.of("Bo");
        // names = new ArrayList<>();                // error: cannot assign a value to final variable names
        try {
            frozen.add("Cy");                         // compiles, but the list is unmodifiable
        } catch (UnsupportedOperationException e) {
            System.out.println("frozen stays " + frozen);
        }
        System.out.println(names + " " + scores[0]);
    }
}
```

```text output
frozen stays [Bo]
[Ann] 99
```

`final` stops you from re-pointing the variable; it says nothing about the object. A `public static final` mutable
collection or array is a **global mutable variable** in disguise. Constants of reference type should hold immutable
objects: `List.of`, `Set.of`, `Map.of`, records of immutable values, `String`, `Duration`, enums. How to design your
own immutable classes is the subject of [Immutable & Final Classes](/lessons/immutable-and-final-classes/).

### 4. Compile-time constants

A **constant variable** is a `final` variable of primitive or `String` type initialised with a **constant expression**
(JLS §4.12.4, §15.29): literals, operators, casts and other constant variables, nothing computed at run time.

| Declaration | Constant variable? | Why |
|---|---|---|
| `static final int MAX = 100;` | Yes | `final`, `int`, literal |
| `static final int DOUBLE_MAX = MAX * 2;` | Yes | Operators on constants |
| `static final String GREETING = "Hi, " + NAME;` (with a constant `NAME`) | Yes | String concatenation of constants |
| `final int local = 7;` (a local) | Yes | Locals can be constants too |
| `static final long STARTED = System.currentTimeMillis();` | No | A method call, computed at run time |
| `static final Integer BOXED = 5;` | No | `Integer` isn't a primitive or `String` |
| `static final List<String> NAMES = List.of("a");` | No | A reference type other than `String` |

Constant variables are special in four ways:

- **They can label `case` branches** (and be used wherever the language requires a constant).
- **They're folded**: expressions made of constants are computed by the compiler, which also allows narrowing
  assignments like `byte sum = a + b;` when `a` and `b` are constants whose sum fits (this was checked on a JVM).
- **They're copied into other classes**: a class that uses `Limits.MAX_USERS` contains the value `100` itself, not a
  reference to the field (JLS §13.1). Scenario 1 shows the consequence.
- **Reading one doesn't initialise its class**, because there's nothing left to read at run time
  ([static vs Instance](/lessons/static-vs-instance/)).

```java title="Constants.java"
public class Constants {
    static final int SMALL = 1;
    static final int LARGE = 3;

    static String size(int n) {
        return switch (n) {
            case SMALL -> "small";                  // case labels need constant expressions
            case LARGE -> "large";
            default -> "medium";
        };
    }

    public static void main(String[] args) {
        final byte a = 10;
        final byte b = 20;
        byte sum = a + b;                           // compiles: a + b is a constant that fits in a byte
        System.out.println(size(1) + " " + size(2) + " " + sum);
    }
}
```

```text output
small medium 30
```

Remove `final` from `a` and `b`, and `byte sum = a + b;` fails with "possible lossy conversion from int to byte"
([Type Conversion & Casting](/lessons/type-conversion/)).

### 5. Effectively final and lambdas

Since Java 8, a local variable or parameter that is **never reassigned** after initialisation is **effectively
final**, even without the keyword (JLS §4.12.4). Lambdas and anonymous classes may only use local variables that are
final or effectively final, because they capture a **copy** of the value
([Pass-by-Value](/lessons/pass-by-value/)):

```java title="Capture.java"
import java.util.List;

public class Capture {
    public static void main(String[] args) {
        int base = 10;                                    // effectively final: never reassigned
        List<Integer> shifted = List.of(1, 2, 3).stream().map(n -> n + base).toList();
        System.out.println(shifted);
        // base++;  would make the lambda above fail to compile with:
        // "local variables referenced from a lambda expression must be final or effectively final"
    }
}
```

```text output
[11, 12, 13]
```

The rule is about the **variable**, not the object: a lambda may call `list.add(...)` on a captured effectively final
list. That's allowed, and in concurrent code it's often a bug ([Lambda Expressions](/lessons/lambda-expressions/)).

### 6. `final` methods and classes

The same keyword has a related meaning on methods and classes:

- A `final` **method** can't be overridden in a subclass (use it for methods whose behaviour must not change, such as
  those called from constructors). `private` and `static` methods can't be overridden anyway.
- A `final` **class** can't be extended: `String`, the wrappers and every record are final. That's one ingredient of
  immutability, not a guarantee of it ([Inheritance](/lessons/inheritance/)). **Sealed** classes (Java 17) are the
  middle ground: extension only by listed subclasses ([Sealed Classes](/lessons/sealed-classes/)).

### 7. `final` fields, construction and threads

`final` fields have two more guarantees and one weak spot:

- **Safe publication.** Once a constructor finishes, every thread that sees the object sees its `final` fields fully
  initialised, without synchronisation (JLS §17.5), as long as `this` didn't escape during construction. It's what
  makes immutable objects thread-safe by construction ([The Java Memory Model](/lessons/java-memory-model/)).
- **The default value is visible during construction.** A `final` field holds `0`, `false` or `null` until it's
  assigned; a method called from a superclass constructor can observe that (scenario 4).
- **Reflection.** Deep reflection (`Field.setAccessible(true)` then `set`) can still change a non-static `final` field
  of an ordinary class. It can't change `static final` fields or record fields (both checked on a JVM), and JDK 26
  (JEP 500) prints a warning when code does it, as a first step towards making final mean final everywhere
  ([Reflection in Practice](/lessons/reflection-in-practice/)).

<Tabs>
<TabItem label="Real world: the constant that didn't change">

```java title="Config.java (library, version 1)"
public class Config {
    public static final int MAX_RETRIES = 3;
}
```

```java title="Client.java (compiled against version 1)"
public class Client {
    public static void main(String[] args) {
        System.out.println(Config.MAX_RETRIES);       // javac writes the value 3 into Client.class
    }
}
```

Now change `MAX_RETRIES` to `5`, recompile **only** `Config.java`, and run `Client` again:

```text output
3
```

`Client.class` holds the literal `3`; it never reads the field (`javap -c Client` shows the constant, not the
field). The JLS describes exactly this (§13.4.9): changing a constant variable's value is not binary compatible with
already-compiled users. Fixes: rebuild everything that depends on the library (normal with a build tool and a
version bump), and don't use compile-time constants for values that are meant to change between releases; use a
static method, configuration, or a non-constant initializer.

</TabItem>
<TabItem label="Edge case: a final field seen too early">

```java title="EarlyRead.java"
public class EarlyRead {
    static class Base {
        Base() {
            describe();                           // calls the subclass override before its fields are set
        }

        void describe() {
        }
    }

    static class Product extends Base {
        private final String name;

        Product(String name) {
            this.name = name;
        }

        @Override
        void describe() {
            System.out.println("name = " + name);
        }
    }

    public static void main(String[] args) {
        new Product("pen").describe();
    }
}
```

```text output
name = null
name = pen
```

`new Product("pen")` runs `Base()` first, which calls the overridden `describe()` while `name` still has its default
value. A `final` field can be observed twice with different values. Don't call overridable methods from constructors.
Since Java 25 (JEP 513, flexible constructor bodies) a constructor may also assign its fields **before** calling
`super(...)`: writing `this.name = name;` and then `super();` in `Product`'s constructor makes both lines print `pen`
([Constructor Chaining & Init Order](/lessons/constructor-chaining-init-order/)).

</TabItem>
<TabItem label="Anti-pattern → fix: a public mutable constant">

```java title="Anti-pattern"
public class Roles {
    public static final List<String> ADMINS = new ArrayList<>(List.of("root"));   // final, but mutable
    public static final String[] LEVELS = {"low", "high"};                          // arrays are always mutable
}
// anywhere else: Roles.ADMINS.add("mallory"); Roles.LEVELS[0] = "none";
```

Both fields are shared global state that any code can change. Make the object immutable too:

```java title="Fix"
public final class Roles {
    public static final List<String> ADMINS = List.of("root");
    public static final List<String> LEVELS = List.of("low", "high");   // or an enum

    private Roles() {
    }
}
```

</TabItem>
<TabItem label="Edge case: final is not a thread-safety switch">

```java title="Counter.java"
import java.util.ArrayList;
import java.util.List;

public class Counter {
    private final List<Integer> seen = new ArrayList<>();   // final reference, mutable, unsynchronised list

    void record(int value) {
        seen.add(value);                                     // concurrent calls can corrupt the list
    }
}
```

`final` guarantees that other threads see the `ArrayList` object that the constructor stored. It doesn't make the
list's later changes thread-safe: concurrent `record` calls still race. Use a concurrent or synchronised collection, or
immutable snapshots.

</TabItem>

## Under the hood

<details>
<summary>What final becomes in bytecode and in the JVM</summary>

- **Locals.** `final` on a local variable or parameter leaves no trace in the bytecode: it's purely a compile-time
  check. That's also why it can't make code faster.
- **Constant variables.** A `static final` constant field gets a `ConstantValue` attribute, and uses of it in other
  classes are replaced by the value (an `ldc`, `bipush` or `iconst` instruction), so there's no `getstatic`. That's
  the mechanism behind the stale-constant scenario.
- **Fields.** `final` fields carry the `ACC_FINAL` flag; the verifier and the JVM refuse writes from outside the
  constructor (or static initializer). The JIT treats `static final` fields as constants and can fold them into
  compiled code; it trusts instance `final` fields only in some cases (records, hidden classes, some JDK classes),
  precisely because reflection can change them. JEP 500 (JDK 26) is the first step towards trusting them everywhere.
- **Memory model.** Writes to `final` fields in a constructor are followed by a "freeze": the JIT keeps them from
  being reordered after the reference to the new object is published (JLS §17.5).

</details>

## Myths vs facts

<MythVsFact myth="static final VAR = 10; declares a constant." audit="6.13">
It's missing a type and doesn't compile. Write `static final int VAR = 10;` (by convention `UPPER_SNAKE_CASE`). The
notes' explanation is right: `static` gives one copy, `final` prevents reassignment.
</MythVsFact>

<MythVsFact myth="A final variable refers to an object that can't change." audit="6.13">
`final` fixes the variable, not the object. A `final List` or `final int[]` can be modified freely. Immutability comes
from the object's class: `List.of`, records, `String`, well-designed immutable classes.
</MythVsFact>

<MythVsFact myth="Every static final field is a compile-time constant.">
Only `final` variables of primitive or `String` type initialised with constant expressions are. `static final Integer`,
`static final List`, or anything computed by a method call are ordinary final fields: not inlined, not usable in
`case` labels.
</MythVsFact>

<MythVsFact myth="Changing a constant in a library updates every program that uses the new jar.">
Compile-time constants are copied into the classes that use them when those classes are compiled. Until they're
recompiled, they keep the old value (JLS §13.4.9).
</MythVsFact>

<MythVsFact myth="final makes code faster.">
On locals and parameters it changes nothing in the bytecode. The JIT does exploit `static final` fields (and
compile-time constants are folded by javac), but use `final` for correctness and clarity, not speed.
</MythVsFact>

## Doubts cleared

<FaqItem q="Is final the same as const in C++?">
No. Java's `final` only prevents reassigning the variable; C++'s `const` can also forbid modifying the object through
that reference. Java has no way to mark a reference "read-only"; you use immutable types instead. (`const` is a
reserved word in Java, but unused.)
</FaqItem>

<FaqItem q="What is a blank final?">
A `final` variable declared without an initializer. It must be assigned exactly once before use: a local in the
method, an instance field in every constructor, a static field in a static initializer.
</FaqItem>

<FaqItem q="Should I mark every local variable and parameter final?">
It's a style choice. Some teams do, so any reassignment is a compile error; others rely on keeping methods short and on
linters. Fields are different: make every field that doesn't need to change `final`, since it documents intent and
gives thread-safety guarantees.
</FaqItem>

<FaqItem q="Can I assign a final field in a normal method, like an init() method?">
No: only in its declaration, an initializer block, or a constructor (a static final: its declaration or a static
initializer). That's what lets the compiler prove it's assigned exactly once.
</FaqItem>

<FaqItem q="Why must variables captured by a lambda be effectively final?">
The lambda holds a copy of the value. If the variable could be reassigned afterwards, the copy and the variable would
silently disagree, so the language forbids it.
</FaqItem>

<FaqItem q="Where should constants live?">
In the class or enum that owns the concept, private if only that class needs them. A final utility class with a
private constructor for truly shared ones. Not in an interface created only to hold constants.
</FaqItem>

<FaqItem q="Is `static final Logger log = …` a constant? Should it be upper case?">
It's a final field of reference type, not a compile-time constant. Conventions differ: many style guides reserve
`UPPER_SNAKE_CASE` for deeply immutable values, and name loggers and other final-but-stateful objects in lower camel
case.
</FaqItem>

<FaqItem q="Does a final class make its objects immutable?">
No. It only prevents subclassing. An immutable class also needs private final fields, no mutators, and defensive
copies of mutable inputs and outputs.
</FaqItem>

## Pitfalls and best practices

| ✅ Do | ❌ Don't |
|---|---|
| Declare constants as `static final` with a type and `UPPER_SNAKE_CASE` | Write the notes' typeless `static final VAR = 10;` |
| Make fields `final` unless they must change | Leave fields reassignable "just in case" |
| Put immutable objects in constants (`List.of`, records, enums) | Expose `public static final` arrays or mutable collections |
| Rebuild clients when library constants change; use methods for values that change | Assume a new jar updates inlined constants |
| Keep constructors free of overridable calls | Let a superclass constructor see a subclass's unset `final` fields |
| Use enums for fixed sets of related constants | Use `int` constants as ad-hoc enums |

## Senior lens

<Callout type="senior" title="Explain it to your team in 60 seconds">
"`final` means the variable is assigned once; it says nothing about the object. So our constants are `static final`
and point to immutable values, and our fields are `final` by default because that documents intent and gives safe
publication. Compile-time constants get copied into client classes, so a changed library constant needs a rebuild of
its users, and values that change between releases shouldn't be compile-time constants at all."
</Callout>

**Where final (or its absence) shows up in production**

| Symptom | Cause | Fix |
|---|---|---|
| New library version, old behaviour | Inlined compile-time constant | Recompile dependents; don't use constants for tunable values |
| "Constant" data modified at run time | `static final` mutable collection or array | Immutable collections, enums, defensive copies |
| `null` or 0 seen in a field that's always set | Overridable method called from a constructor | Call only private/final methods from constructors; JEP 513 prologue |
| Race conditions in "immutable" objects | Non-final fields, or `this` escaping the constructor | `final` fields, no escaping `this`, immutable components |
| Warnings about final field mutation on JDK 26 | Frameworks or tests setting final fields reflectively | Constructor injection, or update the library |

**Code-review checklist**
- [ ] Every field that doesn't need to change is `final`.
- [ ] `public static final` fields hold immutable objects (no arrays, no mutable collections).
- [ ] Values expected to change between releases aren't compile-time constants.
- [ ] Constructors don't call overridable methods or leak `this`.

## Modern Java

- <VersionBadge since={5} /> Enums: type-safe groups of constants instead of `int` constants.
- <VersionBadge since={8} jep={126} /> Effectively final locals, captured by lambdas.
- <VersionBadge since={16} jep={395} /> Records: final classes with final fields that reflection can't change.
- <VersionBadge since={25} jep={513} /> Flexible constructor bodies: fields can be assigned before `super(...)`.
- <VersionBadge preview={25} jep={502} /> Stable values (preview): a field-like holder that is set at most once, later,
  and then treated by the JVM like a constant.
- <VersionBadge since={26} jep={500} /> "Prepare to make final mean final": warnings when deep reflection mutates
  `final` fields.

```java title="Team.java (solution)"
package track.final_and_constants;

import java.util.ArrayList;
import java.util.List;
import java.util.Objects;
import java.util.Set;

/** Reference solution for the Team exercise. */
public final class Team {
    public static final int MAX_MEMBERS = 5;                  // a compile-time constant

    private final String name;
    private final List<String> members;                       // final reference to an immutable list

    public Team(String name, List<String> members) {
        this.name = Objects.requireNonNull(name, "name");
        this.members = List.copyOf(members);                  // an unmodifiable copy; rejects null members
        if (this.members.size() > MAX_MEMBERS) {
            throw new IllegalArgumentException("at most " + MAX_MEMBERS + " members");
        }
        if (Set.copyOf(this.members).size() != this.members.size()) {
            throw new IllegalArgumentException("duplicate member");
        }
    }

    public String name() {
        return name;
    }

    public List<String> members() {
        return members;                                       // safe to share: nobody can modify it
    }

    public Team withMember(String member) {
        List<String> next = new ArrayList<>(members);
        next.add(Objects.requireNonNull(member, "member"));
        return new Team(name, next);                          // the constructor validates again
    }

    public Team renamed(String newName) {
        return new Team(newName, members);
    }
}
```

```java title="Lazy.java (solution)"
package track.final_and_constants;

import java.util.Objects;
import java.util.function.Function;
import java.util.function.Supplier;

/** Reference solution for the Lazy exercise. */
public final class Lazy<T> {
    private Supplier<? extends T> supplier;       // null once the value is computed
    private T value;

    private Lazy(Supplier<? extends T> supplier) {
        this.supplier = supplier;
    }

    public static <T> Lazy<T> of(Supplier<? extends T> supplier) {
        return new Lazy<>(Objects.requireNonNull(supplier, "supplier"));
    }

    public synchronized T get() {
        if (supplier != null) {
            T computed = Objects.requireNonNull(supplier.get(), "the supplier returned null");
            value = computed;                     // store only after a successful computation
            supplier = null;                      // done: the supplier can be garbage-collected
        }
        return value;
    }

    public synchronized boolean isComputed() {
        return supplier == null;
    }

    public <R> Lazy<R> map(Function<? super T, ? extends R> f) {
        Objects.requireNonNull(f, "f");
        return Lazy.of(() -> f.apply(get()));
    }
}
```

```java title="FreezerTest.java"
                assertDeeplyUnmodifiable(e.getValue());
            }
```

```java title="Freezer.java (solution)"
package track.final_and_constants;

import java.lang.reflect.Array;
import java.math.BigDecimal;
import java.math.BigInteger;
import java.util.ArrayList;
import java.util.Collections;
import java.util.HashMap;
import java.util.IdentityHashMap;
import java.util.List;
import java.util.Map;
import java.util.Objects;
import java.util.Set;

/** Reference solution for the Freezer exercise. */
public final class Freezer {
    /** Exact classes whose instances can never change. */
    private static final Set<Class<?>> LEAVES = Set.of(String.class, Integer.class, Long.class, Short.class,
            Byte.class, Double.class, Float.class, Character.class, Boolean.class, BigInteger.class, BigDecimal.class);

    private Freezer() {
    }

    public static Object freeze(Object value) {
        return freeze(value, new IdentityHashMap<>(), Collections.newSetFromMap(new IdentityHashMap<>()));
    }

    private static Object freeze(Object value, Map<Object, Object> done, Set<Object> inProgress) {
        Objects.requireNonNull(value, "null can't be frozen");
        if (LEAVES.contains(value.getClass()) || value instanceof Enum<?>) {
            return value;                                            // already immutable
        }
        Object known = done.get(value);
        if (known != null) {
            return known;                                            // shared parts stay shared
        }
        if (!inProgress.add(value)) {
            throw new IllegalArgumentException("the structure contains itself");
        }
        Object result;
        if (value instanceof List<?> list) {
            List<Object> out = new ArrayList<>(list.size());
            for (Object e : list) {
                out.add(freeze(e, done, inProgress));
            }
            result = List.copyOf(out);
        } else if (value instanceof Set<?> set) {
            List<Object> out = new ArrayList<>(set.size());
            for (Object e : set) {
                out.add(freeze(e, done, inProgress));
            }
            result = Set.copyOf(out);
        } else if (value instanceof Map<?, ?> map) {
            Map<Object, Object> out = new HashMap<>();
            for (Map.Entry<?, ?> e : map.entrySet()) {
                out.put(freeze(e.getKey(), done, inProgress), freeze(e.getValue(), done, inProgress));
            }
            result = Map.copyOf(out);
        } else if (value.getClass().isArray()) {
            int n = Array.getLength(value);                          // works for int[], String[], Object[]…
            List<Object> out = new ArrayList<>(n);
            for (int i = 0; i < n; i++) {
                out.add(freeze(Array.get(value, i), done, inProgress));
            }
            result = List.copyOf(out);
        } else {
            throw new IllegalArgumentException("can't freeze a " + value.getClass().getName());
        }
        inProgress.remove(value);
        done.put(value, result);
        return result;
    }
}
```

| Topic | Remember |
|---|---|
| **final variable** | Assigned exactly once; checked by definite assignment |
| **final field** | Assigned in the initializer or every constructor; safe publication |
| **Constant** | `static final int VAR = 10;` (type required), `UPPER_SNAKE_CASE`, immutable value |
| **Not immutable** | `final List`/arrays can still change; use `List.of`, records, enums |
| **Compile-time constant** | final + primitive/String + constant expression: `case` labels, folding, inlined into other classes |
| **Stale constants** | Recompile clients when a library constant changes (JLS §13.4.9) |
| **Effectively final** | Never reassigned: capturable by lambdas and anonymous classes |
| **final method / class** | No overriding / no subclassing (String, wrappers, records) |
| **Construction** | Final fields read too early are 0/null; JEP 513 allows assignment before `super()` |
| **Reflection** | Can change instance finals of ordinary classes; JDK 26 warns (JEP 500) |
