## Why this matters

A team caches expensive results in a `HashMap` keyed by a small `CacheKey` class. They overrode `equals` and forgot
`hashCode`. The cache never hits: every lookup builds a new key whose identity hash code points at a different bucket,
so the map keeps adding entries until the service runs out of memory. Nothing failed to compile and no test failed.
`HashMap`, `HashSet`, `List.contains`, `assertEquals`, logging, debuggers and frameworks all call the methods every
class inherits from `java.lang.Object`, and they all trust that your class keeps those methods' contracts.

## TL;DR

<Callout type="tldr">
- Every class extends `Object`, directly or indirectly; arrays do too, and interface types have `Object`'s public
  methods as well.
- **`equals`** must be an equivalence relation (reflexive, symmetric, transitive), consistent, and false for `null`.
  `Object`'s version compares identity.
- **`hashCode`**: equal objects must have equal hash codes (unequal ones may share one), and the value mustn't change
  while the fields `equals` uses don't. Override both or neither.
- **Inheritance and equality don't mix easily:** a subclass that adds a field to `equals` breaks symmetry or
  transitivity. Prefer composition, `final` classes or records; `getClass()` or a `canEqual` method otherwise.
- **`toString`** is for people: include the key state, never secrets, and don't parse it.
- **`clone()`** is a broken design (shallow, skips constructors, needs `Cloneable`); use copy constructors or
  factories. `finalize()` is deprecated for removal.
- **Records** generate `equals`, `hashCode` and `toString` from their components.
</Callout>

## Mental model

Think of `equals` and `hashCode` as an airport's passport check. `equals` answers "is this the same traveller?";
`hashCode` decides which queue a traveller joins. The rule is simple: the same traveller must always be sent to the
same queue. Many different travellers can share a queue (collisions are fine), but if one traveller could be sent to two
queues, the officer at the wrong desk would never find them.

Where the picture breaks: "the same traveller" is whatever your class decides. Identity for most objects, the same
values for value objects, and Java can't check that your decision is consistent; only your tests can.

## Concept, step by step

### 1. `java.lang.Object`: the root of every class

A class without `extends` extends `Object`, so every object, every array included, has these methods. Interface types
have them too: the compiler treats every interface as declaring `Object`'s public methods (JLS §9.2), which is why
`Runnable r = ...; r.toString()` compiles.

| Method | What it does by default | Override? |
|---|---|---|
| `boolean equals(Object)` | `this == other`: identity | In value classes |
| `int hashCode()` | An identity hash code | Whenever you override `equals` |
| `String toString()` | Class name, `@`, hash code in hex | Almost always |
| `Class<?> getClass()` | The runtime class | Can't: it's `final` |
| `Object clone()` | Field-by-field copy, if the class implements `Cloneable` | Prefer copy constructors |
| `void finalize()` | Nothing | Never: deprecated for removal |
| `wait`, `notify`, `notifyAll` | Low-level thread coordination | Can't: `final` ([Synchronization & Locks](/lessons/synchronization-and-locks/)) |

### 2. `equals`: an equivalence relation

`Object.equals` documents five rules. For any non-null references `x`, `y`, `z`:

- **Reflexive:** `x.equals(x)` is true.
- **Symmetric:** `x.equals(y)` is true exactly when `y.equals(x)` is.
- **Transitive:** if `x.equals(y)` and `y.equals(z)`, then `x.equals(z)`.
- **Consistent:** repeated calls give the same answer as long as the objects don't change.
- **Not null:** `x.equals(null)` is false (and doesn't throw).

The recipe for a class whose instances are equal when their significant fields are:

```java title="Point.java"
public final class Point {
    private final int x;
    private final int y;

    public Point(int x, int y) {
        this.x = x;
        this.y = y;
    }

    @Override
    public boolean equals(Object o) {           // Object, never Point: an overload isn't called by collections
        if (this == o) {
            return true;                        // a cheap shortcut
        }
        return o instanceof Point other         // false for null and for other types
                && x == other.x && y == other.y;
    }

    @Override
    public int hashCode() {
        return 31 * x + y;                      // equal points, equal hash codes
    }

    @Override
    public String toString() {
        return "(" + x + ", " + y + ")";
    }
}
```

Common mistakes:

- **`equals(Point other)`** is an overload, not an override, so `HashSet` and `List.contains` never call it
  ([Overloading](/lessons/overloading-resolution/)). `@Override` catches this at compile time.
- **Comparing `double` or `float` fields with `==`** breaks reflexivity for `NaN` (`NaN != NaN`) and treats `0.0` and
  `-0.0` as equal although they print differently. Use `Double.compare(a, b) == 0`, as records do.
- **Comparing array fields with `==` or `equals`** compares identity; use `Arrays.equals`.
- **Fields that change** make an object "move" while it's in a hash set
  ([Classes & Objects in Depth](/lessons/classes-objects-deep/)).
- **Casting without checking** (`Point other = (Point) o;`) throws for `null` or other types instead of returning
  false.

### 3. `hashCode`: equal objects, equal hash codes

The contract has three parts:

1. Calling `hashCode` repeatedly on an unchanged object returns the same value (within one run of the program).
2. **If `a.equals(b)`, then `a.hashCode() == b.hashCode()`.**
3. Unequal objects may have the same hash code; fewer collisions just make hash tables faster.

The second rule exists because of how hash tables search:

<HashLookup />

```java title="NoEquals.java"
import java.util.HashMap;
import java.util.Map;

public class NoEquals {
    static class Key {
        final int id;

        Key(int id) {
            this.id = id;
        }

        @Override
        public int hashCode() {                 // hashCode overridden, equals not
            return id;
        }
    }

    public static void main(String[] args) {
        Map<Key, String> map = new HashMap<>();
        map.put(new Key(1), "first");
        map.put(new Key(1), "second");
        System.out.println(map.get(new Key(1)) + " " + map.size());
    }
}
```

```text output
null 2
```

All three keys land in the same bucket, but `Object.equals` compares identity, so none of them matches another. The
opposite mistake, `equals` without `hashCode`, usually sends equal keys to different buckets, with the same result.

Writing a good `hashCode`:

- Combine the fields `equals` uses, and no others: `31 * h + fieldHash`, starting from one field, or
  `Objects.hash(a, b, c)`, which is shorter but creates an array and boxes primitives on every call.
- Use `Integer.hashCode`, `Long.hashCode`, `Double.hashCode`, `Objects.hashCode` (null-safe) and `Arrays.hashCode`
  for the parts.
- Immutable classes can compute it once and cache it, as `String` does.

### 4. Equality across a class hierarchy

Effective Java (item 10) shows the problem with a `ColorPoint` that adds a colour to `Point`:

```java title="Symmetry.java"
public class Symmetry {
    static class Point {
        final int x;
        final int y;

        Point(int x, int y) {
            this.x = x;
            this.y = y;
        }

        @Override
        public boolean equals(Object o) {
            return o instanceof Point p && p.x == x && p.y == y;
        }

        @Override
        public int hashCode() {
            return 31 * x + y;
        }
    }

    static class ColorPoint extends Point {
        final String color;

        ColorPoint(int x, int y, String color) {
            super(x, y);
            this.color = color;
        }

        @Override
        public boolean equals(Object o) {
            return o instanceof ColorPoint cp && super.equals(cp) && cp.color.equals(color);
        }
    }

    public static void main(String[] args) {
        Point p = new Point(1, 2);
        ColorPoint cp = new ColorPoint(1, 2, "red");
        System.out.println(p.equals(cp) + " " + cp.equals(p));
    }
}
```

```text output
true false
```

The point says yes, the coloured point says no: symmetry is broken, and whether `list.contains(...)` finds an element
now depends on which object is asking. Making `ColorPoint.equals` ignore the colour when comparing with a plain
`Point` restores symmetry but breaks transitivity (two differently coloured points would both equal one plain point).
There's no way to extend an instantiable class with a new field in `equals` and keep every rule with `instanceof`. The
options:

- **Composition:** `ColorPoint` *has* a `Point` instead of being one ([IS-A, HAS-A & Composition](/lessons/relationships/)).
  Effective Java's recommendation.
- **`final` classes and records:** no subclasses, no problem. Most value classes should be final anyway.
- **`getClass()` instead of `instanceof`:** `o != null && o.getClass() == getClass()`. Symmetric and transitive, but
  a subclass that adds nothing (an anonymous subclass, a framework proxy) is never equal to its parent.
- **A `canEqual` method** (Odersky, Spoon and Venners): each class says which objects may be equal to it, and
  subclasses that add state override it. Subclasses that add nothing stay equal to the parent. The core exercise
  builds this.

### 5. `toString`: for people

`Object.toString` returns `getClass().getName() + "@" + Integer.toHexString(hashCode())`, such as `Point@1b6d3586`:
the class name and the identity hash code, not a memory address. String concatenation, `println`, loggers and
debuggers all call `toString`, so overriding it is almost always worth it:

- Include the state that identifies the object or explains it: `(1, 2)`, `Order#42[3 lines, SUBMITTED]`.
- **Never include secrets** (passwords, tokens, personal data): `toString` output ends up in logs. Records print every
  component, so a record holding a secret needs its own `toString`.
- Keep it cheap and side-effect free; it may run often, and in debuggers.
- Don't parse it. If callers need the parts, give them accessors. If the format is part of your API, document it.
- Arrays don't override it: use `Arrays.toString` and `Arrays.deepToString`.

### 6. `getClass`, `clone` and the rest

- **`getClass()`** returns the object's runtime class, the one `new` created, whatever the variable's declared type
  ([Reference Types](/lessons/reference-types/)). It's `final`. For a `Point p`, its type is `Class<? extends Point>`.
- **`clone()`** is protected in `Object`. It throws `CloneNotSupportedException` unless the class implements the
  `Cloneable` marker interface, and then copies the fields one by one: a **shallow** copy that **runs no constructor**.
  Effective Java (item 13) lists the problems: no constructor checks, `final` fields that can't be given fresh copies,
  a checked exception and a cast. Prefer a copy constructor (`new Point(other)`) or a factory (`Point.copyOf(other)`).
  Arrays are the exception: `array.clone()` is public, typed and fine for arrays of primitives
  ([Arrays](/lessons/arrays/)).
- **`finalize()`** is deprecated for removal; release resources with `close()`
  ([Classes & Objects in Depth](/lessons/classes-objects-deep/)).
- **`wait`, `notify`, `notifyAll`** coordinate threads through an object's monitor. They're final and low-level;
  `java.util.concurrent` offers better tools ([Threads](/lessons/threads-basics/)).

### 7. Records: the contracts for free

```java title="Records.java"
import java.util.List;

public class Records {
    record Point(int x, int y) {
    }

    record Tags(String[] names, List<String> list) {
    }

    public static void main(String[] args) {
        System.out.println(new Point(1, 2).equals(new Point(1, 2)) + " " + new Point(1, 2));
        Tags a = new Tags(new String[] {"x"}, List.of("x"));
        Tags b = new Tags(new String[] {"x"}, List.of("x"));
        System.out.println(a.equals(b) + " " + a.list().equals(b.list()));
    }
}
```

```text output
true Point[x=1, y=2]
false true
```

A record's `equals` compares every component: primitives with the wrapper's `compare` method, references with
`Objects.equals`. Its `hashCode` combines the same components, and its `toString` lists them. Records are final, so the
hierarchy problem can't arise. Array components still compare by identity, as the second line shows; use a `List` or
write the methods yourself ([Records & Pattern Matching](/lessons/records-and-pattern-matching/)).

## Scenarios

<Tabs>
<TabItem label="Real world: a cache that never hits">

```java title="Anti-pattern"
final class CacheKey {
    private final String customer;
    private final LocalDate day;

    CacheKey(String customer, LocalDate day) {
        this.customer = customer;
        this.day = day;
    }

    @Override
    public boolean equals(Object o) {
        return o instanceof CacheKey k && k.customer.equals(customer) && k.day.equals(day);
    }
    // no hashCode: every new key has its own identity hash code
}

Map<CacheKey, Report> cache = new HashMap<>();
cache.computeIfAbsent(new CacheKey(id, today), k -> expensiveReport(id, today));
```

Each lookup builds a new key, its identity hash code picks a more or less random bucket, and the map adds another
entry: the cache never hits and grows until memory runs out. The fix is one line:

```java title="Fix"
record CacheKey(String customer, LocalDate day) {
}
```

A record has the right `equals` and `hashCode` by construction, and can't drift out of sync when a field is added.

</TabItem>
<TabItem label="Edge case: doubles, NaN and -0.0">

```java title="Doubles.java"
public class Doubles {
    public static void main(String[] args) {
        double nan = Double.NaN;
        System.out.println((nan == nan) + " " + (Double.compare(nan, nan) == 0));
        System.out.println((0.0 == -0.0) + " " + (Double.compare(0.0, -0.0) == 0));
        System.out.println(Double.valueOf(nan).equals(nan) + " " + Double.valueOf(0.0).equals(-0.0));
    }
}
```

```text output
false true
true false
true false
```

`==` follows IEEE 754 arithmetic: NaN is unequal to everything, itself included, and the two zeros are equal. An
`equals` built on `==` is therefore not reflexive for NaN, so a `HashSet` can hold the "same" NaN measurement
twice. `Double.compare` and `Double.equals` treat NaN as equal to itself and the zeros as different, which is what an
equivalence relation needs, and what records use ([Floating Point (IEEE 754)](/lessons/floating-point/)).

</TabItem>
<TabItem label="Anti-pattern → fix: a toString that leaks">

```java title="Anti-pattern"
record Credentials(String user, String password) {
}

log.info("connecting with {}", credentials);   // Credentials[user=ann, password=hunter2]
```

```java title="Fix"
record Credentials(String user, String password) {
    @Override
    public String toString() {
        return "Credentials[user=" + user + ", password=***]";
    }
}
```

A record's generated `toString` prints every component. For types that hold secrets, override it (or keep the secret
in a type whose `toString` masks it), so that no log line, exception message or debugger view reveals it.

</TabItem>

## Under the hood

<details>
<summary>Identity hashes, String, HashMap and records</summary>

- **Identity hash codes** are generated the first time they're needed and then stored with the object (in HotSpot, in
  its header), so they stay the same even when the garbage collector moves the object. They're not addresses.
- **`String.hashCode`** is specified: `s[0]·31^(n−1) + s[1]·31^(n−2) + … + s[n−1]` in `int` arithmetic, and it's cached
  after the first call. That's why strings make good keys, and why a specification change is impossible: hash codes
  of strings are stored in files and used in `switch` statements on strings.
- **`HashMap` uses the hash twice:** it mixes the high bits into the low ones (`h ^ (h >>> 16)`), uses the low bits as
  the bucket index, and stores each entry's hash to skip `equals` calls on obvious mismatches. Since Java 8, a bucket
  with many colliding entries becomes a balanced tree, so even a poor `hashCode` doesn't degrade to linear scans
  ([HashMap Internals](/lessons/hashmap-internals/)).
- **Records' methods** are generated through `invokedynamic` with `java.lang.runtime.ObjectMethods` as the bootstrap,
  so the class file stays small and the JVM can optimise them.

</details>

## Myths vs facts

<MythVsFact myth="Objects with the same hash code are equal." audit="1.22">
The rule only goes one way: equal objects must have equal hash codes. Unequal objects may share one ("Aa" and "BB" do),
which is why a hash map still calls `equals`.
</MythVsFact>

<MythVsFact myth="Overriding equals is enough; hashCode is optional." audit="1.22">
Without a matching `hashCode`, equal objects usually get different hash codes, and `HashMap`, `HashSet` and every
other hash-based structure stop finding them. Override both or neither.
</MythVsFact>

<MythVsFact myth="clone() returns a deep, independent copy." audit="1.22">
`Object.clone()` copies field values, so references still point to the same objects (a shallow copy), and it doesn't
run a constructor. A deep copy needs code you write, typically in a copy constructor.
</MythVsFact>

<MythVsFact myth="The default toString prints the object's memory address." audit="1.22">
It prints the class name, `@` and the identity hash code in hexadecimal. The identity hash isn't an address; objects
move, and their hash codes don't.
</MythVsFact>

<MythVsFact myth="Interfaces don't have toString and equals, because they don't extend Object." audit="1.22">
An interface type includes `Object`'s public methods as members (JLS §9.2), so you can call `equals` or `toString` on
any interface-typed reference: the object behind it is always an `Object`.
</MythVsFact>

## Doubts cleared

<FaqItem q="Should equals use instanceof or getClass()?">
For final classes and records it makes no difference. For classes that may be subclassed, `instanceof` lets
subclasses that add nothing (proxies, anonymous classes) stay equal, but breaks once a subclass adds state to `equals`;
`getClass()` is always symmetric but never lets a subclass equal its parent. `canEqual` gets both right at the cost of
one more method.
</FaqItem>

<FaqItem q="Why 31 in hash codes?">
It's an odd prime, so multiplying spreads bits without losing information through overflow, and `31 * h` can be
computed as `(h << 5) - h`. It's also what `String`, `List` and `Arrays.hashCode` use. Any reasonable combination works;
consistency with `equals` is what matters.
</FaqItem>

<FaqItem q="Is Objects.hash too slow?">
It allocates an array for its varargs and boxes primitive fields on every call. That's irrelevant for most classes and
measurable only for keys hashed in hot loops, where a hand-written `31 * h + …` is better.
</FaqItem>

<FaqItem q="Can hashCode return the same value for every object?">
Legally, yes; the contract only requires equal objects to have equal hash codes. But every object then lands in the same
bucket, turning a hash map into one long list (or one tree, since Java 8).
</FaqItem>

<FaqItem q="What must x.equals(null) do?">
Return false, without throwing. `o instanceof T t` handles it, since `null instanceof T` is false.
</FaqItem>

<FaqItem q="Why is clone protected and Cloneable empty?">
It's a known design flaw: `Cloneable` has no methods; it only changes how `Object.clone()` behaves (copy instead of
throwing). A class has to override `clone()` as public to make it callable at all, which is why most modern code
avoids it.
</FaqItem>

<FaqItem q="Can I compare enum constants with ==?">
Yes. Each constant is the only instance of its value, so `==` and `equals` give the same answer, and `==` also works
on `null` without a NullPointerException ([Enums in Depth](/lessons/enums/)).
</FaqItem>

<FaqItem q="Does compareTo have to agree with equals?">
It's strongly recommended, but not required. `BigDecimal` is the famous exception: `2.0` and `2.00` are not `equals`
but compare as 0, so a `HashSet` keeps both and a `TreeSet` keeps one
([Comparable & Comparator](/lessons/comparable-and-comparator/)).
</FaqItem>

## Pitfalls and best practices

| ✅ Do | ❌ Don't |
|---|---|
| Write `equals(Object)` with `@Override` | Write `equals(MyType)`: an overload collections never call |
| Override `equals` and `hashCode` together, from the same fields | Override one of them |
| Compare doubles with `Double.compare`, arrays with `Arrays.equals` | Use `==` on doubles or arrays in `equals` |
| Make value classes final or records | Add fields to `equals` in a subclass of a concrete class |
| Override `toString` with useful, non-secret state | Log objects whose `toString` reveals passwords or tokens |
| Copy with copy constructors or factories | Implement `Cloneable` in new code |

## Senior lens

<Callout type="senior" title="Explain it to your team in 60 seconds">
"Every class inherits `equals`, `hashCode` and `toString`, and half the JDK depends on them. `equals` must behave like
equality in mathematics, `hashCode` must agree with it or hash maps silently lose objects, and both must use the same
fields. Inheritance makes `equals` hard, so value types are final classes or, better, records, which generate all three
correctly. `toString` is for humans and goes into logs, so it never contains secrets. And we don't use `clone`."
</Callout>

**Where it goes wrong in production**

| Symptom | Cause | Fix |
|---|---|---|
| A cache never hits; memory grows | `equals` without `hashCode` on the key | Records as keys; tests of the contract |
| Duplicates in a `HashSet` | Same cause, or `equals(MyType)` overload | `@Override equals(Object)` + `hashCode` |
| `contains` depends on argument order | Asymmetric `equals` across a hierarchy | Final classes, composition, `canEqual` |
| Entities lost from sets after updates | `hashCode` on mutable fields | Identity or stable-ID equality |
| Passwords in logs | Generated or careless `toString` | Mask secrets in `toString` |
| Invariants broken by copies | `clone()` bypassing constructors | Copy constructors and factories |

Contract bugs are cheap to prevent and expensive to find, so test them directly: Guava's `EqualsTester`, the
EqualsVerifier library, or a small helper of your own (the challenge exercise) run every rule against a few groups of
equal objects.

**Code-review checklist**
- [ ] `equals` takes `Object`, has `@Override`, handles `null` and other types without throwing.
- [ ] `equals` and `hashCode` use exactly the same fields, none of them mutable for objects used as keys.
- [ ] Doubles, floats and arrays are compared with the right helpers.
- [ ] Value classes are final or records; subclass equality is a conscious decision.
- [ ] `toString` is useful and leaks nothing sensitive.
- [ ] No new `Cloneable` implementations.

## Modern Java

- <VersionBadge since={7} /> `java.util.Objects`: `equals`, `hash`, `hashCode`, `toString`, all null-safe.
- <VersionBadge since={8} jep={180} /> `HashMap` turns heavily colliding buckets into balanced trees.
- <VersionBadge since={16} jep={394} /> Pattern matching for `instanceof`: `o instanceof Point p && ...` in `equals`.
- <VersionBadge since={16} jep={395} /> Records generate `equals`, `hashCode` and `toString`.
- <VersionBadge since={18} jep={421} /> `finalize()` deprecated for removal.
- Value classes (JEP 401, not in any GA JDK yet) would make `==` compare the field values of value objects, since they
  have no identity.

```java title="EqualsTester.java (solution)"
package track.object_class_contracts;

import java.util.ArrayList;
import java.util.List;
import java.util.Objects;

/** Reference solution for the EqualsTester exercise. */
public final class EqualsTester {
    private static final Object UNRELATED = new Unrelated();

    /** Stands for "an object of some other class": no equals should accept it. */
    private static final class Unrelated {
        @Override
        public String toString() {
            return "an unrelated object";
        }
    }

    private final List<Object> objects = new ArrayList<>();
    private final List<Integer> groupOf = new ArrayList<>();
    private int groups;

    public EqualsTester addEqualityGroup(Object... group) {
        if (group.length == 0) {                                    // NullPointerException for a null array
            throw new IllegalArgumentException("an equality group needs at least one object");
        }
        for (Object o : group) {
            Objects.requireNonNull(o, "an element of the group");  // check everything before adding anything
        }
        for (Object o : group) {
            objects.add(o);
            groupOf.add(groups);
        }
        groups++;
        return this;
    }

    public List<String> violations() {
        List<String> found = new ArrayList<>();
        for (Object x : objects) {
            if (Boolean.FALSE.equals(call(x, x, found))) {
                found.add("not reflexive: " + x);
            }
            if (Boolean.TRUE.equals(call(x, null, found))) {
                found.add(x + ".equals(null) is true");
            }
            if (Boolean.TRUE.equals(call(x, UNRELATED, found))) {
                found.add(x + ".equals(" + UNRELATED + ") is true");
            }
        }
        for (int i = 0; i < objects.size(); i++) {
            for (int j = 0; j < objects.size(); j++) {
                if (i == j) {
                    continue;
                }
                Object x = objects.get(i);
                Object y = objects.get(j);
                boolean sameGroup = groupOf.get(i).equals(groupOf.get(j));
                Boolean result = call(x, y, found);
                if (result != null && result != sameGroup) {
                    found.add(x + (sameGroup ? " should equal " : " should not equal ") + y);
                }
                if (sameGroup && i < j && x.hashCode() != y.hashCode()) {
                    found.add("hash codes differ: " + x + ", " + y);
                }
            }
        }
        return found;
    }

    /** x.equals(y), or null after recording the exception it threw. */
    private static Boolean call(Object x, Object y, List<String> found) {
        try {
            return x.equals(y);
        } catch (RuntimeException e) {
            found.add(x + ".equals(" + y + ") throws " + e.getClass().getSimpleName());
            return null;
        }
    }
}
```

## Cheat sheet

<CheatSheet>

| Topic | Remember |
|---|---|
| **Object** | Root of every class and array; interface types have its public methods too |
| **equals rules** | Reflexive, symmetric, transitive, consistent, `x.equals(null)` false |
| **equals recipe** | `@Override equals(Object o)`, `o instanceof T t`, compare significant fields |
| **hashCode rule** | Equal ⇒ same hash; same hash ⇏ equal; stable while fields unchanged |
| **Together** | Override both or neither, from the same fields |
| **Doubles, arrays** | `Double.compare`, `Arrays.equals` / `Arrays.hashCode` |
| **Hierarchies** | Adding a field in a subclass breaks `equals`: composition, final, records, `getClass()`, `canEqual` |
| **toString** | Default `Name@hexhash`; override with useful state; no secrets; don't parse |
| **clone** | Shallow, skips constructors, needs `Cloneable`: use copy constructors (arrays are fine) |
| **Records** | Generate all three from components (arrays by identity!) |
