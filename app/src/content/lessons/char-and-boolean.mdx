## Why this matters

A user signs up with the display name "Emoji fan 😀". Your code cuts names to 11 characters with `substring`, the
database stores a `?` where the emoji was, and the profile page shows garbage. Another team counts "characters" with
`length()` and rejects a valid 280-character message. Both bugs come from one fact: a Java `char` is **not** a
character as a person sees it. It's a 16-bit piece of text in the UTF-16 encoding, and some characters need two of
them. `boolean` looks simpler, but it has its own traps: your notes say its default is `true` (it's `false`), and
`if (done = true)` compiles and is always taken. This lesson makes both types precise.

## TL;DR

<Callout type="tldr">
- **`char`** is an unsigned 16-bit integer type (0 to 65,535, default `'\u0000'`) holding one **UTF-16 code unit**,
  not an ASCII code. ASCII is just the first 128 values.
- Unicode has more than 65,536 characters (code points up to U+10FFFF). Characters above U+FFFF, such as most emoji,
  take **two** `char` values, a **surrogate pair**: `"😀".length()` is **2**.
- `char` is numeric: `'A' + 1` is the `int` 66, `(char) ('A' + 1)` is `'B'`, and `'a' + 'b'` is 195, not `"ab"`.
- Use the **code point** methods (`codePointAt`, `codePoints()`, `codePointCount`, `Character.toChars`) for text
  that may contain emoji or rare scripts; never cut strings in the middle of a pair.
- **`boolean`** has exactly two values, `true` and `false`; the field default is **`false`**. There is no conversion
  to or from numbers: `if (1)` and `(int) flag` don't compile.
- The JLS doesn't fix a boolean's size. The JVM computes with booleans as `int`s, and HotSpot stores a boolean field
  or array element in one byte.
</Callout>

## Mental model

Think of a Java `String` as a **row of 16-bit boxes**, one `char` per box. Most characters in everyday text (all
Latin, Greek, Cyrillic, Arabic and common Chinese characters) fit in one box. Characters from the "upper floors" of
Unicode, such as emoji, many math symbols and rare scripts, don't fit, so Java stores them as **two glued boxes**, a
surrogate pair. And what a reader sees as one character can be several code points: `é` can be one code point or `e`
plus a combining accent, and 👍🏽 is a thumb plus a skin-tone modifier.

A `boolean` is a **light switch**: on or off, nothing in between, and not a number. You can't do arithmetic with it,
and it never silently turns into 0 or 1.

Where the box model breaks: `length()`, `charAt` and `substring` count boxes, not characters. That's fine for
identifiers and ASCII protocols, and wrong for user-visible text.

## Concept, step by step

### 1. `char`: a 16-bit Unicode code unit

| Property | Value |
|---|---|
| Size | 16 bits (`Character.SIZE`), 2 bytes (`Character.BYTES`) |
| Range | `'\u0000'` to `'￿'`, that is 0 to 65,535: **unsigned**, the only unsigned primitive |
| Field default | `'\u0000'` (the NUL character, numeric value 0), not a space and not `null` |
| What it holds | One **UTF-16 code unit** (JLS §4.2.1) |

Your notes describe `char` as the "character representation of ASCII values". That's how it looks for English text,
because **ASCII is the first 128 values of Unicode**: `'A'` is 65 in both. But a `char` can hold `'é'` (233),
`'Ω'` (937) or `'漢'` (28,450), none of which exist in ASCII. Java was designed around Unicode from day one.

Character literals:

| Literal | Meaning |
|---|---|
| `'A'`, `'7'`, `'é'` | The character itself (the source file is read as UTF-8 by default since Java 18) |
| `'\n'` `'\t'` `'\r'` `'\b'` `'\f'` | Newline, tab, carriage return, backspace, form feed |
| `'\''` `'\"'` `'\\'` | Single quote, double quote, backslash |
| `'\s'` | Space (Java 15, added with text blocks) |
| `'é'` | A **Unicode escape**: `é` written in pure ASCII |
| `'\101'` | An octal escape (65, `'A'`): legal, but avoid it |
| `65` | An `int` constant that fits, so `char c = 65;` compiles and holds `'A'` |

There's no empty char literal (`''` doesn't compile), and a `char` can never be `null`: it's a primitive.

### 2. `char` is a number

The JLS counts `char` among the **integral types**, so you can compare and compute with it:

```java title="CharArithmetic.java"
public class CharArithmetic {
    public static void main(String[] args) {
        char c = 'A';
        System.out.println(c + 1);            // 66: char + int is an int
        System.out.println((char) (c + 1));   // B: cast back to char
        c++;                                  // ++ and += include the cast
        System.out.println(c);                // B
        System.out.println('7' - '0');        // 7: the digit's value
        System.out.println((int) 'é');        // 233
        for (char letter = 'a'; letter <= 'e'; letter++) {
            System.out.print(letter);         // abcde
        }
        System.out.println();
    }
}
```

```text output
66
B
B
7
233
abcde
```

- In arithmetic, `char` is **promoted to `int`**, like `byte` and `short` (see
  [Type Conversion](/lessons/type-conversion/)). That's why `'a' + 'b'` is 195 and not `"ab"`: only a `String`
  operand turns `+` into concatenation.
- `char c = 65;` compiles because 65 is a constant that fits. `char c = -1;` and `char c = someInt;` don't: they need a
  cast.
- `char` and `short` are both 16 bits but not interchangeable: `short` is signed (−32,768 to 32,767), `char` is
  unsigned (0 to 65,535), so each needs a cast to become the other.

### 3. Unicode, code points and surrogate pairs

**Unicode** gives every character a number, its **code point**, written U+0041 for `A` or U+1F600 for 😀. Code
points run from U+0000 to **U+10FFFF**: room for 1,114,112 values, far more than a `char` can hold.

When Java 1.0 appeared in 1996, Unicode was a 16-bit code, so a 16-bit `char` could hold any character. Unicode 2.0
(1996) grew beyond 16 bits, and Java 5 added support for the new characters (JSR 204) without changing `char`. The
solution is **UTF-16**:

- Code points U+0000 to U+FFFF, the **Basic Multilingual Plane (BMP)**, take one `char`.
- Code points U+10000 to U+10FFFF, the **supplementary characters**, take two `char`s: a **high surrogate**
  (`\uD800` to `\uDBFF`) followed by a **low surrogate** (`\uDC00` to `\uDFFF`). Those ranges are reserved, so a
  surrogate never means anything alone.

How 😀 (U+1F600) becomes two `char`s: subtract 0x10000, which leaves a 20-bit number, and split it into two 10-bit
halves:

<BitLayout groups={[{ bits: '0000111101', label: 'high 10 bits = 0x3D → 0xD800 + 0x3D = \\uD83D' }, { bits: '1000000000', label: 'low 10 bits = 0x200 → 0xDC00 + 0x200 = \\uDE00' }]} caption="U+1F600 − 0x10000 = 0x0F600. Its top 10 bits are added to 0xD800 (high surrogate), its bottom 10 bits to 0xDC00 (low surrogate)." />

So in Java, `"😀"` is the same string as `"😀"`, and:

| Method | Counts or returns | For `"Hi😀"` |
|---|---|---|
| `length()` | `char` values (code units) | 4 |
| `charAt(2)` | one code unit | `'\uD83D'`, half an emoji |
| `codePointCount(0, s.length())` | code points | 3 |
| `codePointAt(2)` | the whole code point starting at index 2 | 0x1F600 (128,512) |
| `codePoints()` | an `IntStream` of code points | 72, 105, 128512 |
| `Character.toChars(0x1F600)` | the code point as `char[]` | `{'\uD83D', '\uDE00'}` |
| `Character.charCount(0x1F600)` | `char` values needed | 2 |
| `Character.toString(0x1F600)` | a `String` (Java 11) | `"😀"` |

- Compare **café** with **cafe + ◌́**. They look identical, but one has the precomposed `é` (U+00E9), the other `e` plus
  a combining accent (U+0301): different lengths, and `equals` says they differ.
- **👍🏽** is two code points (a thumb and a skin-tone modifier), four `char`s, and one character to a reader.
- **🇮🇳** is two "regional indicator" code points that together display as one flag.

### 4. The `Character` class

`Character` is the wrapper class of `char` and a toolbox of static methods. Most have two versions: one taking a
`char`, and one taking an `int` code point (which also works for supplementary characters).

| Method | Returns |
|---|---|
| `Character.isLetter(cp)`, `isDigit(cp)`, `isLetterOrDigit(cp)`, `isWhitespace(cp)` | Unicode-aware tests: `isDigit` is also true for `'٣'` (Arabic-Indic three) |
| `Character.toUpperCase(cp)`, `toLowerCase(cp)` | Simple one-to-one case mapping: `toUpperCase('ß')` stays `'ß'` |
| `Character.getNumericValue('7')`, `Character.digit('f', 16)` | 7, 15 |
| `Character.isHighSurrogate(c)`, `isLowSurrogate(c)`, `isSurrogate(c)` | Surrogate checks for a `char` |
| `Character.getName(cp)` | The Unicode name, e.g. `"GRINNING FACE"` (Java 7) |
| `Character.MIN_VALUE`, `MAX_VALUE`, `MAX_CODE_POINT` | `'\u0000'`, `'￿'`, 0x10FFFF |

For whole strings, prefer the `String` methods: `"straße".toUpperCase(Locale.ROOT)` is `"STRASSE"`, because
`String` case conversion handles mappings that change the length; the `Character` methods can't.

### 5. Unicode escapes are processed first

A `\uXXXX` escape isn't limited to literals: the compiler replaces every Unicode escape in the source **before** it
splits the code into tokens (JLS §3.3). Usually that's invisible, but it has two famous consequences:

- `char c = '\u000A';` **doesn't compile**. `\u000A` becomes a real line break, which ends the literal. The JLS itself
  says to write `'\n'` instead. The same goes for `'''` (a quote) and `'\'` (a backslash).
- A `\u000A` inside a `//` comment ends the comment, and the rest of the line is **code** (see
  [Predict the output](#predict-the-output)).

Use escape sequences (`\n`, `\'`) for special characters, and Unicode escapes only for characters that are hard to
type or see, such as ` ` (a non-breaking space).

### 6. `boolean`: exactly two values

| Property | Value |
|---|---|
| Values | `true` and `false`, and nothing else (JLS §4.2.5) |
| Field default | **`false`** |
| Size | Not defined by the JLS (see [Under the hood](#under-the-hood)) |
| Conversions | None to or from any numeric type |

Your notes say "1 bit" and "default value is true". The default is `false` (verified on a JVM), and the size isn't
fixed. Java is strict where C isn't:

```java title="Rejected by the compiler"
boolean b = 1;           // error: int can't be converted to boolean
int n = (int) true;      // error: boolean can't be cast to int
if (count) { }           // error when count is an int: the condition must be a boolean
while (x = 5) { }        // error: an int assignment isn't a condition
```

To convert on purpose, write it out: `int bit = flag ? 1 : 0;` and `boolean flag = bit != 0;`.

The operators that produce or combine booleans:

| Operator | Meaning |
|---|---|
| `==`, `!=`, `<`, `<=`, `>`, `>=` | Comparisons produce a `boolean` |
| `!a` | Not |
| `a && b`, `a \|\| b` | And, or, **short-circuit**: the right side runs only if needed |
| `a & b`, `a \| b`, `a ^ b` | And, or, exclusive or, **both sides always evaluated** |
| `c ? x : y` | Choose a value by a condition |

[Arithmetic, Relational & Logical Operators](/lessons/operators-arithmetic-relational-logical/) covers them in detail.

Some `boolean` habits worth having:
- Name booleans as questions: `isActive`, `hasChildren`, `canRetry`, `shouldNotify`.
- Write `if (done)` and `if (!done)`, not `if (done == true)`. Besides being shorter, it avoids the classic typo
  `if (done = true)`, which **compiles** (it assigns `true` and then tests it) because `done` is a boolean.
- `Boolean.parseBoolean(s)` is `true` only for `"true"`, ignoring case; `"yes"`, `"1"` and `null` give `false`.

## Scenarios

<Tabs>
<TabItem label="Real world: truncating text without breaking emoji">

A column holds at most 11 characters, so the code cuts names with `substring`:

```java title="Truncate.java"
public class Truncate {
    public static void main(String[] args) {
        String name = "Emoji fan 😀😀";   // "Emoji fan 😀😀"
        String cut = name.substring(0, 11);                  // a limit of 11 chars
        System.out.println(cut.length());
        System.out.println(Character.isHighSurrogate(cut.charAt(10)));
        System.out.println(safeTruncate(name, 11).length());
    }

    /** At most maxChars chars, never ending in the middle of a surrogate pair. */
    static String safeTruncate(String s, int maxChars) {
        if (s.length() <= maxChars) {
            return s;
        }
        int end = maxChars;
        if (Character.isHighSurrogate(s.charAt(end - 1))) {
            end--;                                           // don't split the pair
        }
        return s.substring(0, end);
    }
}
```

```text output
11
true
10
```

`substring(0, 11)` keeps the first half of the emoji: an unpaired high surrogate. Encoded as UTF-8 it becomes `?`,
some databases reject the row, and JSON encoders may fail. `safeTruncate` steps back one `char` when the cut would
split a pair. For user-visible limits ("280 characters"), count code points or, better, grapheme clusters (see
[Doubts cleared](#doubts-cleared)).

</TabItem>
<TabItem label="Edge case: isDigit accepts more than 0 to 9">

Validating a PIN code with `Character.isDigit`:

```java title="Digits.java"
public class Digits {
    public static void main(String[] args) {
        String input = "١٢٣";                  // "١٢٣": Arabic-Indic digits
        System.out.println(Character.isDigit(input.charAt(0)));
        System.out.println(Integer.parseInt(input));
        System.out.println(input.matches("\\d+"));
        System.out.println(input.chars().allMatch(c -> c >= '0' && c <= '9'));
    }
}
```

```text output
true
123
false
false
```

`Character.isDigit` and `Integer.parseInt` understand every Unicode decimal digit, so `"١٢٣"` passes as 123. The
regex `\d` means only `[0-9]` unless you ask for Unicode classes. Neither is wrong, but mixing them in one validation
path gives inconsistent answers. For machine formats (PINs, IDs, protocols) check `c >= '0' && c <= '9'`; for human
input, decide deliberately whether other digits are welcome.

</TabItem>
<TabItem label="Real world: the Turkish i">

Case-insensitive comparisons that work everywhere, except on a server with a Turkish default locale:

```java title="TurkishI.java"
import java.util.Locale;

public class TurkishI {
    public static void main(String[] args) {
        Locale turkish = Locale.forLanguageTag("tr");
        String lower = "TITLE".toLowerCase(turkish);
        System.out.println(lower.equals("title"));
        System.out.println(lower.equals("tıtle"));                        // ı: dotless i
        System.out.println("TITLE".toLowerCase(Locale.ROOT).equals("title"));
        System.out.println("title".toUpperCase(turkish).equals("TİTLE")); // İ: dotted capital I
    }
}
```

```text output
false
true
true
true
```

Turkish has a dotted and a dotless i, so `I` lower-cases to `ı`. `toLowerCase()` **without** an argument uses the
JVM's default locale, so code comparing keywords, HTTP headers or enum names can break on a Turkish machine. Use
`toLowerCase(Locale.ROOT)` for machine text (identifiers, protocols) and the user's locale only for text shown to
people.

</TabItem>
<TabItem label="Anti-pattern → fix: boolean parameters">

```java title="Anti-pattern"
void export(String file, boolean compress, boolean overwrite, boolean includeHeader) { … }

export("q3.csv", true, false, true);          // which flag is which?
```

At the call site the booleans say nothing, it's easy to swap two of them, and the day you need a third kind of
compression the `boolean` can't grow.

```java title="Fix"
enum Compression { NONE, GZIP }
enum ExistingFile { KEEP, OVERWRITE }

record ExportOptions(Compression compression, ExistingFile existingFile, boolean includeHeader) { }

export("q3.csv", new ExportOptions(Compression.GZIP, ExistingFile.KEEP, true));
```

Enums name each choice at the call site and can gain values later. A single, well-named boolean is fine; three
positional ones aren't. The same goes for `Boolean` (the wrapper) used as a three-state "yes, no, unknown": unboxing
its `null` throws `NullPointerException`, so model the third state with an enum.

</TabItem>

## Under the hood

<details>
<summary>How the JVM and the String class store char and boolean</summary>

- **The JVM has no boolean arithmetic.** The JVM specification (§2.3.4) says boolean expressions are compiled to
  `int` operations, with `true` as 1 and `false` as 0. Boolean arrays use the byte-array instructions (`baload`,
  `bastore`), and in Oracle's JVM each element takes 8 bits. HotSpot also stores a `boolean` field in one byte.
  If you need millions of flags, `java.util.BitSet` packs them one bit each, into `long` words.
- **`char` values are zero-extended.** `caload` (reading a `char[]` element) zero-extends to `int`, where `baload`
  sign-extends a byte. `i2c` keeps the low 16 bits when an `int` is cast to `char`.
- **Compact strings (Java 9, JEP 254).** A `String` is backed by a `byte[]` plus a "coder" flag: text that fits in
  Latin-1 (U+0000 to U+00FF) is stored with **one byte per char**, anything else as UTF-16 with two. The API is
  unchanged: `charAt` still returns a `char`. Most strings in typical applications are Latin-1, so this halves the
  space their characters take.
- **Source files and the default charset.** Since Java 18 (JEP 400), `javac` reads source files and the Java APIs
  read and write text as UTF-8 by default, instead of an OS-dependent charset. Unicode escapes are translated before
  anything else (JLS §3.3), which is why they work even in comments.
- **Encodings are conversions at the edges.** Inside the JVM text is UTF-16 (or Latin-1); files, sockets and
  databases use bytes. Every `getBytes`, `new String(bytes, …)`, `Reader` and `Writer` is a conversion, and each should
  name its charset (`StandardCharsets.UTF_8`) so it doesn't depend on the machine.

</details>

## Myths vs facts

<MythVsFact myth="A char holds an ASCII value." audit="4.6">
A `char` holds a **UTF-16 code unit**: an unsigned 16-bit value from 0 to 65,535 (JLS §4.2.1). ASCII is only the first
128 values, which is why `'A'` is 65 in both. `'é'` (233) and `'漢'` (28,450) are ordinary `char` values, and
characters above U+FFFF, like emoji, need **two** `char`s: `"😀".length()` is 2 (verified on a JVM).
</MythVsFact>

<MythVsFact myth="The default value of a boolean is true." audit="4.11">
The default value of a `boolean` field or array element is **`false`** (JLS §4.12.5, verified on a JVM). A feature flag
that's never set is off. Local variables have no default at all: reading one before assigning it doesn't compile.
</MythVsFact>

<MythVsFact myth="A boolean takes 1 bit." audit="4.11">
The JLS doesn't specify the size. The JVM computes with booleans as `int`s (JVMS §2.3.4), and Oracle's JVM stores
each element of a `boolean[]` in a byte; HotSpot also gives a `boolean` field a byte. For one bit per flag, use
`BitSet` or bit masks in an `int` or `long`.
</MythVsFact>

<MythVsFact myth="String.length() returns the number of characters.">
It returns the number of `char` values (UTF-16 code units). An emoji counts as 2, `e` plus a combining accent as 2,
and a family emoji built from several people as many more. Count code points with `codePointCount`, and
user-perceived characters with a grapheme-aware tool.
</MythVsFact>

<MythVsFact myth={`'a' + 'b' gives "ab".`}>
Both operands are `char`, so they're promoted to `int` and added: 97 + 98 = **195**. `+` concatenates only when one
operand is a `String`: `"" + 'a' + 'b'` or `String.valueOf('a') + 'b'` gives `"ab"`.
</MythVsFact>

## Doubts cleared

<FaqItem q="Why is Java's char 16 bits when C's char is 8?">
Java was designed in the early 1990s around Unicode, which was then a 16-bit code, so 16 bits were enough for any
character. C's `char` is a byte and its text encoding depends on the platform. When Unicode outgrew 16 bits, Java kept
`char` and represented the new characters as surrogate pairs.
</FaqItem>

<FaqItem q="What's the difference between a char and a code point?">
A code point is Unicode's number for a character (U+0000 to U+10FFFF), stored in an `int`. A `char` is a 16-bit unit
of the UTF-16 encoding. For the BMP (up to U+FFFF) they're the same number; a supplementary code point is two `char`s.
Methods that take an `int` code point (`Character.isLetter(int)`, `appendCodePoint`) handle every character.
</FaqItem>

<FaqItem q="How do I loop over the characters of a string correctly?">
If the text may contain supplementary characters, loop over code points:
`s.codePoints().forEach(cp -> …)`, or step by code point with
`int cp = s.codePointAt(i);` and `i += Character.charCount(cp);` in a `while` loop. For what a reader
sees as one character, use grapheme clusters: `BreakIterator.getCharacterInstance()` or the regex `\X`.
</FaqItem>

<FaqItem q={'Why are "café" and "café" sometimes not equal?'}>
One may use the precomposed `é` (U+00E9) and the other `e` followed by a combining acute accent (U+0301). They display
identically but have different `char` values, so `equals` is false. Normalise both first:
`Normalizer.normalize(s, Normalizer.Form.NFC)` (in `java.text`). Do this before comparing, hashing or storing user
text that should match.
</FaqItem>

<FaqItem q="Why doesn't `char c = '\u000A';` compile?">
Unicode escapes are replaced before the compiler reads tokens (JLS §3.3), so the line becomes `char c = '`, a line
break, and `';`: an unterminated literal. Use the escape sequence `'\n'`. The JLS gives exactly this advice.
</FaqItem>

<FaqItem q="Is `'\u0000'` the same as `null`?">
No. `'\u0000'` is the NUL character, a real `char` with value 0 and the default of `char` fields. `null` means "no
object" and applies only to references: a `char` can't be `null`, but a `Character` (the wrapper) can.
</FaqItem>

<FaqItem q="Can I switch on a char or a boolean?">
`switch` on `char` (and `Character`) has always worked: `case 'y', 'Y' -> …`. Switching on a `boolean` is part of the
**primitive types in patterns** preview (JEP 532, fifth preview in JDK 27); in standard Java 25 use `if`.
</FaqItem>

<FaqItem q="How do I convert between boolean and int?">
There's no cast in either direction. Write `int bit = flag ? 1 : 0;` and `boolean flag = bit != 0;`. For sorting,
`Boolean.compare(a, b)` orders `false` before `true`.
</FaqItem>

<FaqItem q={'Why does `Boolean.getBoolean("true")` return false?'}>
`Boolean.getBoolean(name)` doesn't parse its argument: it reads the **system property** with that name and returns
true only if it's set to `"true"`. To parse a string, use `Boolean.parseBoolean(s)`.
</FaqItem>

<FaqItem q="Is `c - '0'` a safe way to get a digit's value?">
For ASCII digits, yes: `'0'` to `'9'` are consecutive (48 to 57), so `'7' - '0'` is 7. It gives nonsense for anything
else, so check `c >= '0' && c <= '9'` first. `Character.digit(c, 10)` also works, returns −1 for non-digits, and
accepts other scripts' digits too.
</FaqItem>

## Pitfalls and best practices

| ✅ Do | ❌ Don't |
|---|---|
| Treat `char` as a UTF-16 code unit; use code point methods for arbitrary text | Assume one `char` = one character on screen |
| Truncate and reverse text without splitting surrogate pairs | `substring` user text at a fixed `char` index |
| Pass `StandardCharsets.UTF_8` to every byte ↔ text conversion | Rely on the platform charset in old code paths |
| Use `toLowerCase(Locale.ROOT)` for identifiers and protocol text | Call `toLowerCase()` with no locale on machine text |
| Normalise (NFC) user text before comparing or storing it as a key | Compare user-typed text with `equals` directly |
| Write `if (done)` / `if (!done)` and name booleans `isX`/`hasX` | Write `if (done == true)`, or `if (done = true)` by mistake |
| Use enums for choices and three-state values | Pass several positional booleans, or use `Boolean` with `null` as a state |
| Parse with `Boolean.parseBoolean` | Use `Boolean.getBoolean` to parse (it reads system properties) |

## Senior lens

<Callout type="senior" title="Explain it to your team in 60 seconds">
"A Java `char` is a UTF-16 code unit, not a character. Emoji and some CJK and math characters are two `char`s, and
what a user sees as one character can be several code points. So we never cut or reverse user text by `char` index,
we name the charset on every conversion, we lower-case machine text with `Locale.ROOT`, and we normalise user text
before comparing it. Booleans are strictly true or false: no numbers, default `false`, and anything with a third state
or a future fourth option is an enum."
</Callout>

**Where text bugs hide in real systems**

| Place | Symptom | Prevention |
|---|---|---|
| Length limits (DB columns, SMS, UI fields) | Emoji cut in half, `?` in stored data | Truncate by code point or grapheme; define limits in the unit the product means |
| Database charset | Emoji rejected or stored as `????` | A 4-byte-capable charset (MySQL: `utf8mb4`, not the legacy 3-byte `utf8`) |
| Byte ↔ text conversions | Mojibake (`Ã©` instead of `é`) | Always pass `StandardCharsets.UTF_8`; test with non-ASCII data |
| Case conversion and comparison | Works everywhere but one locale | `Locale.ROOT` for machine text; `equalsIgnoreCase` for simple matching |
| User-typed identifiers (usernames, search) | Look-alike duplicates, failed lookups | NFC normalisation; consider confusable-character checks |
| Feature flags and options | Unreadable calls, impossible states | Enums and option records instead of boolean parameters |

**Code-review checklist**
- [ ] No `substring`/`charAt` loops over user-visible text that could split surrogate pairs.
- [ ] Every `getBytes`, `new String(byte[]…)`, `Reader`/`Writer` names its charset.
- [ ] `toLowerCase`/`toUpperCase` on machine text pass `Locale.ROOT`.
- [ ] No methods with two or more positional boolean parameters; no `Boolean` used as a tri-state.

/** Reference solution for the Caesar exercise. */
public final class Caesar {

    private Caesar() {
    }

    public static String encode(String text, int shift) {
        int k = Math.floorMod(shift, 26);   // 0..25, also for negative shifts
        StringBuilder out = new StringBuilder(text.length());
        for (int i = 0; i < text.length(); i++) {
            char c = text.charAt(i);
            if (c >= 'a' && c <= 'z') {
                out.append((char) ('a' + (c - 'a' + k) % 26));
            } else if (c >= 'A' && c <= 'Z') {
                out.append((char) ('A' + (c - 'A' + k) % 26));
            } else {
                out.append(c);              // surrogates are copied one by one, so pairs stay intact
            }
        }
        return out.toString();
    }
}

package track.char_and_boolean;

/** Reference solution for the CodePoints exercise. */
public final class CodePoints {

    private CodePoints() {
    }

    public static int count(String s) {
        int count = 0;
        for (int i = 0; i < s.length(); i++) {
            if (startsPair(s, i)) {
                i++;                               // skip the low surrogate of the pair
            }
            count++;
        }
        return count;
    }

    public static String reverse(String s) {
        StringBuilder out = new StringBuilder(s.length());
        int end = s.length();
        while (end > 0) {
            int start = end - 1;
            if (start > 0 && startsPair(s, start - 1)) {
                start--;                           // keep the pair together, high surrogate first
            }
            out.append(s, start, end);
            end = start;
        }
        return out.toString();
    }

    public static String truncate(String s, int maxChars) {
        if (s.length() <= maxChars) {
            return s;
        }
        int end = maxChars;
        if (end > 0 && Character.isHighSurrogate(s.charAt(end - 1))) {
            end--;                                 // the cut would split a pair: leave the pair out
        }
        return s.substring(0, end);
    }

    /** Does a surrogate pair start at index i? */
    private static boolean startsPair(String s, int i) {
        return Character.isHighSurrogate(s.charAt(i))
                && i + 1 < s.length()
                && Character.isLowSurrogate(s.charAt(i + 1));
    }
}

package track.char_and_boolean;

/** Reference solution for the Utf8 exercise. */
public final class Utf8 {

    private Utf8() {
    }

    public static int length(String s) {
        int bytes = 0;
        for (int i = 0; i < s.length(); i++) {
            char c = s.charAt(i);
            if (c < 0x80) {
                bytes += 1;
            } else if (c < 0x800) {
                bytes += 2;
            } else if (startsPair(s, i)) {
                bytes += 4;
                i++;                                   // the low surrogate is part of this code point
            } else if (Character.isSurrogate(c)) {
                bytes += 1;                            // unpaired: encoded as '?'
            } else {
                bytes += 3;
            }
        }
        return bytes;
    }

    public static byte[] encode(String s) {
        byte[] out = new byte[length(s)];
        int p = 0;
        for (int i = 0; i < s.length(); i++) {
            char c = s.charAt(i);
            if (c < 0x80) {
                out[p++] = (byte) c;
            } else if (c < 0x800) {
                out[p++] = (byte) (0xC0 | (c >> 6));
                out[p++] = (byte) (0x80 | (c & 0x3F));
            } else if (startsPair(s, i)) {
                int cp = Character.toCodePoint(c, s.charAt(++i));
                out[p++] = (byte) (0xF0 | (cp >> 18));
                out[p++] = (byte) (0x80 | ((cp >> 12) & 0x3F));
                out[p++] = (byte) (0x80 | ((cp >> 6) & 0x3F));
                out[p++] = (byte) (0x80 | (cp & 0x3F));
            } else if (Character.isSurrogate(c)) {
                out[p++] = '?';
            } else {
                out[p++] = (byte) (0xE0 | (c >> 12));
                out[p++] = (byte) (0x80 | ((c >> 6) & 0x3F));
                out[p++] = (byte) (0x80 | (c & 0x3F));
            }
        }
        return out;
    }

    private static boolean startsPair(String s, int i) {
        return Character.isHighSurrogate(s.charAt(i))
                && i + 1 < s.length()
                && Character.isLowSurrogate(s.charAt(i + 1));
    }
}

## Cheat sheet

<CheatSheet>

| Topic | Remember |
|---|---|
| **`char`** | unsigned 16-bit, 0..65,535, default `'\u0000'`; one UTF-16 **code unit**, not ASCII |
| **Literals** | `'A'` · `'\n'` `'\t'` `'\''` `'\\'` · `'\s'` (15) · `'é'` · `char c = 65;` (constant fits) |
| **Arithmetic** | `char` promotes to `int`: `'A' + 1 == 66`, `'a' + 'b' == 195`; `c++` and `c += 1` keep `char` |
| **Unicode** | code points U+0000..U+10FFFF; BMP = 1 `char`; above U+FFFF = surrogate pair (high D800–DBFF, low DC00–DFFF) |
| **Counting** | `length()` = chars · `codePointCount` = code points · `\X` / `BreakIterator` = what readers see |
| **Code point API** | `codePointAt`, `codePoints()`, `Character.toChars`, `charCount`, `toString(int)`, `appendCodePoint` |
| **Unicode escapes** | processed before tokens (JLS §3.3): `'\u000A'` doesn't compile; `\u000A` in a comment ends it |
| **Text hygiene** | name charsets (UTF-8), `Locale.ROOT` for machine text, NFC-normalise user text, don't split pairs |
| **`boolean`** | only `true`/`false`, default **`false`**, no casts to or from numbers, size not specified |
| **boolean traps** | `if (done = true)` compiles · `Boolean.getBoolean` reads system properties · `Boolean` null unboxing → NPE |
