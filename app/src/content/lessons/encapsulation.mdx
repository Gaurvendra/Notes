## Why this matters

A `Customer` class has private fields and a getter and setter for each, and passes every review. Then a new rule
arrives: an email address may only change after the new address is verified. `setEmail` has 47 callers in five
services, and each of them now has to remember the rule; the first one that forgets lets unverified addresses in. The
notes define encapsulation as private fields plus public getters and setters. That's a technique, not the goal. The
goal is an object that guards its own rules, so they hold whoever calls it, and whose inner representation can change
without breaking anyone.

## TL;DR

<Callout type="tldr">
- **Encapsulation** bundles data with the code that keeps it valid and exposes only what callers need. **Data hiding**
  (private fields) is its main technique, not a synonym (audit 1.11).
- A getter and a setter for every private field is not encapsulation: it's a public field with extra steps
  (audit 1.12). Encapsulation protects **invariants**, rules that are always true.
- Offer **behaviour** (`withdraw`, `ship`, `rename`), not raw state. Add a setter only for state that may change on its
  own, and validate it. Change related fields together, and fail before changing anything.
- **Don't leak mutable internals:** copy what comes in, and return copies or read-only views. Copy before you validate.
- Encapsulation lets the **representation change** without breaking callers: `String` switched from `char[]` to
  `byte[]` in Java 9 and no program noticed.
- Levels: private members, package-private classes, module exports. `private` prevents mistakes, not attacks.
</Callout>

## Mental model

A vending machine gives you buttons and a coin slot, never the cash box. Its rules (no snack without payment, never
sell what it doesn't have, always give change) hold for every customer, because the only way in is through the
buttons, and each button checks the rules. A machine with a `getCashBox()` button would depend on every customer's
honesty.

Where the picture breaks: a Java object can still be opened with tools such as reflection or a debugger. `private`
stops honest mistakes in normal code, not determined attackers.

## Concept, step by step

### 1. Encapsulation and data hiding

The notes (01 p5) say encapsulation bundles the data and the code working on that data into a single unit, "also known
as data hiding". The two are related but not the same (audit 1.11):

- **Data hiding** makes the representation inaccessible: `private` fields, package-private classes.
- **Encapsulation** puts the data together with the operations that keep it valid, behind a boundary that callers can
  only cross through those operations.

You can hide data without encapsulating anything: private fields with public setters for everything protect nothing.
And you can encapsulate without hiding everything: a record exposes all its components, read-only, and its compact
constructor still guarantees its invariants. Hiding is the means; protected rules are the end.

### 2. The notes' `Dog`, corrected

The notes' demo (01 p5–6) declares `private string Dog;`, then uses a field called `colour`, and calls `lab.getColor`
without parentheses (audit 1.13). Corrected:

```java title="Dog.java"
public class Dog {
    private String colour;

    public String getColour() {
        return colour;
    }

    public void setColour(String colour) {
        this.colour = colour;
    }

    public static void main(String[] args) {
        Dog lab = new Dog();
        lab.setColour("black");
        System.out.println(lab.getColour());
    }
}
```

```text output
black
```

The notes' point is right: callers no longer touch the field directly. But look at what the setter accepts: `""`,
`null`, `"purple"`, anything. As it stands, it protects exactly as much as `public String colour;` would (audit 1.12).
What the method does buy is a single place where rules can be added later, without changing any caller. The warm-up
exercise adds them.

### 3. Invariants: what encapsulation protects

An **invariant** is a rule that holds for every object of a class whenever no method is running: a balance is never
negative, a range's low end is never above its high end, reserved stock never exceeds stock on hand.

- **Constructors establish** the invariants; **every public method preserves** them.
- **Change related fields together.** With separate setters, a `Range` from 1 to 2 can't become 5 to 6 by calling
  `setLo(5)` first, because 5 > 2 for a moment (puzzle 4). One method that takes both values has no invalid moment.
- **Fail before changing anything** (failure atomicity, Effective Java item 76): check everything, then assign. A
  method that throws halfway leaves a broken object behind.

```java title="Range.java"
public final class Range {
    private int lo;
    private int hi;                                // invariant: lo <= hi

    public Range(int lo, int hi) {
        moveTo(lo, hi);
    }

    public void moveTo(int lo, int hi) {           // both ends at once
        if (lo > hi) {
            throw new IllegalArgumentException(lo + " > " + hi);   // before any assignment
        }
        this.lo = lo;
        this.hi = hi;
    }

    public int lo() {
        return lo;
    }

    public int hi() {
        return hi;
    }

    public int length() {
        return hi - lo;
    }
}
```

The same thinking replaces most setters with behaviour. A bank account doesn't need `setBalance`; it needs `deposit`
and `withdraw`, which can't produce a negative balance
([Classes & Objects in Depth](/lessons/classes-objects-deep/)).

### 4. Leaks: handing out what you should keep

A private field doesn't help if a method hands out the object it refers to, or keeps an object the caller still holds:

<LeakyGetter />

```java title="Course.java"
import java.util.ArrayList;
import java.util.List;

public final class Course {
    private static final int LIMIT = 30;
    private final List<String> students;

    public Course(List<String> students) {
        List<String> copy = List.copyOf(students);    // copy first, then check the copy
        if (copy.size() > LIMIT) {
            throw new IllegalArgumentException("more than " + LIMIT + " students");
        }
        this.students = new ArrayList<>(copy);
    }

    public void enrol(String student) {
        if (students.size() == LIMIT) {
            throw new IllegalStateException("course is full");
        }
        students.add(student);
    }

    public List<String> students() {
        return List.copyOf(students);                 // a read-only snapshot (unmodifiableList: a live view)
    }
}
```

- **On the way in**, copy mutable arguments you keep. **Copy before validating**: if you validate the caller's object
  and copy it afterwards, another thread can change it in between, and you keep something you never checked
  (Effective Java item 50).
- **On the way out**, return an unmodifiable view, a copy, or better, immutable objects that need no copying.
- **Arrays** are always mutable: return `array.clone()`. **`java.util.Date` and `Calendar`** are mutable too; use the
  immutable `java.time` types.

| | `Collections.unmodifiableList(list)` | `List.copyOf(list)` |
|---|---|---|
| Callers can change it | No | No |
| Shows your later changes | Yes: it's a view | No: it's a snapshot |
| Cost | A small wrapper | A copy of the elements |
| `null` elements | Allowed | Rejected |

### 5. Encapsulation lets the representation change

Because callers only use methods, the fields behind them can change. The best-known example is `String` itself: until
Java 8 it stored its characters in a `char[]`; since Java 9 (compact strings, JEP 254) it stores a `byte[]` plus a flag
saying whether each character takes one byte or two, which halves the memory used by most strings. Not one program had
to change, because no program could see the field. The same freedom lets a `Temperature` store kelvin internally while
offering Celsius and Fahrenheit, or a collection switch to a faster internal structure in a later release.

The opposite is just as true: anything callers can see becomes something you can't change. A public field, a getter
that returns an internal type, even an undocumented behaviour that callers come to rely on.

### 6. Getters, setters and JavaBeans

- **JavaBeans conventions** (`getName()`, `isActive()` for booleans, `setName(...)`) matter because tools use them:
  JPA, Jackson, expression languages and data-binding libraries find properties by these names. Records use `name()`
  instead, and modern versions of these libraries understand records.
- **A getter** only when callers need the value. Return immutable values, copies or read-only views.
- **A setter** only for state that may legitimately change on its own, and it validates. Everything else changes
  through behaviour methods, or not at all.
- **Immutable objects** are the strongest form of encapsulation: they need no setters, no copies on the way out, and no
  thought about who else holds them ([Immutable & Final Classes](/lessons/immutable-and-final-classes/)).
- **Generated accessors** (IDE templates, Lombok's `@Data`) are fine for data carriers, and wrong by default for
  objects with rules.

### 7. Levels of encapsulation

| Level | Mechanism | Hides |
|---|---|---|
| Member | `private` fields and methods | Representation and helpers inside a class |
| Class | package-private classes, private nested classes | Implementation classes inside a package |
| Package | Module `exports` | Whole internal packages ([Packages & Access Modifiers](/lessons/packages-access-modifiers/)) |
| API | Interfaces, factories returning interfaces | Which implementation is used |

None of these is a security boundary by itself. Reflection can read private fields of classes on the class path, and
serialization, debuggers and heap dumps see everything. Since JDK 16/17, the JDK's own internals are strongly
encapsulated: deep reflection into them fails unless a command-line option opens them.

## Scenarios

<Tabs>
<TabItem label="Real world: one rule, 47 setters">

```java title="Before"
customer.setEmail(newEmail);                   // in 47 places, in five services
```

```java title="After"
public void changeEmail(String newEmail, EmailVerifier verifier) {
    Email email = Email.of(newEmail);          // validated value object
    if (!verifier.isVerified(email)) {
        throw new IllegalStateException("verify " + email + " first");
    }
    this.email = email;
    this.emailChangedAt = Instant.now();       // a second field changed in the same step
}
```

With a setter, the rule had to be repeated by every caller, and the second field kept getting forgotten. With one
behaviour method, the rule lives where the data lives, and the setter can be deprecated and then removed. Most
"encapsulation" refactorings look like this: find the setters whose callers all repeat the same checks, and turn them
into methods named after what the business actually does.

</TabItem>
<TabItem label="Edge case: a final field that still changes">

```java title="Periods.java"
import java.util.Date;

public class Periods {
    static final class Period {
        private final Date start;
        private final Date end;

        Period(Date start, Date end) {
            if (start.compareTo(end) > 0) {
                throw new IllegalArgumentException(start + " is after " + end);
            }
            this.start = start;                // keeps the caller's mutable objects
            this.end = end;
        }

        Date start() {
            return start;
        }

        Date end() {
            return end;
        }
    }

    @SuppressWarnings("deprecation")
    public static void main(String[] args) {
        Date start = new Date();
        Date end = new Date();
        Period p = new Period(start, end);
        end.setYear(78);                       // the caller still holds the object the period uses
        System.out.println(p.end().before(p.start()));
    }
}
```

```text output
true
```

The fields are private and final, and the constructor checked the rule, yet the period now ends before it starts:
`final` fixes which `Date` the field refers to, not the date inside it. This is Effective Java's example for item 50.
Copy mutable arguments (`new Date(start.getTime())`) and mutable results, or, better, use `java.time.Instant`, which is
immutable.

</TabItem>
<TabItem label="Anti-pattern → fix: setters that encode a state machine">

```java title="Anti-pattern"
order.setPaid(true);
order.setShipped(true);                        // nothing stops shipping before paying, or un-paying afterwards
```

```java title="Fix"
public final class Order {
    public enum Status { NEW, PAID, SHIPPED }

    private Status status = Status.NEW;

    public void pay() {
        if (status != Status.NEW) {
            throw new IllegalStateException("can't pay an order that is " + status);
        }
        status = Status.PAID;
    }

    public void ship() {
        if (status != Status.PAID) {
            throw new IllegalStateException("can't ship an order that is " + status);
        }
        status = Status.SHIPPED;
    }

    public Status status() {
        return status;
    }
}
```

Two booleans allow four combinations, and only three are legal. One status field, changed only by methods that check
the current state, allows exactly the legal transitions.

</TabItem>

## Under the hood

<details>
<summary>Access checks, inlining and records</summary>

- **Access is checked twice:** by the compiler, and by the JVM when it links a class. A class compiled against an
  older version of a library in which a member was still accessible fails at run time with `IllegalAccessError`.
  Nested classes access each other's private members directly since Java 11 (nestmates, JEP 181).
- **Getters and setters cost nothing.** The JIT compiler inlines small methods, so `account.balance()` runs as fast as
  reading the field. Encapsulation's only runtime cost is the defensive copies you choose to make.
- **Records** compile to a final class with private final fields, public accessors and a canonical constructor. A
  compact constructor runs before the fields are assigned, so it can validate or normalise the components
  ([Records & Pattern Matching](/lessons/records-and-pattern-matching/)).
- **Strong encapsulation of the JDK** (JEP 396, JEP 403): `setAccessible(true)` on internals throws
  `InaccessibleObjectException` unless the JVM is started with `--add-opens`.

</details>

## Myths vs facts

<MythVsFact myth="Encapsulation and data hiding are the same thing." audit="1.11">
Data hiding (making the representation private) is the main technique. Encapsulation is the goal: data bundled with the
code that keeps it valid, so callers can only change it in ways that respect its rules.
</MythVsFact>

<MythVsFact myth="Private fields with a getter and a setter for each are encapsulation." audit="1.12">
If every field has an unchecked setter, callers can still put the object into any state they like. Encapsulation means
protecting invariants: validated changes, no setters for state that mustn't change, behaviour methods, defensive
copies, immutability.
</MythVsFact>

<MythVsFact myth="Getters and setters are slower than accessing fields directly." audit="1.12">
The JIT compiler inlines them. The cost of encapsulation is a design decision, such as a defensive copy, never the call
itself.
</MythVsFact>

<MythVsFact myth="private string Dog; and lab.getColor are fine in the demo." audit="1.13">
Java is case-sensitive, so the type is `String`; the field the methods use is `colour`; and a method call needs
parentheses: `lab.getColour()`.
</MythVsFact>

<MythVsFact myth="Making fields private makes the data secure." audit="1.12">
Access modifiers prevent mistakes in ordinary code. Reflection, serialization, debuggers and heap dumps still see
private data. Protect secrets with other means, and keep them out of objects that get logged.
</MythVsFact>

## Doubts cleared

<FaqItem q="Should every field have a getter?">
No. Add one when callers need the value. Many fields are internal details, and every getter is a promise you'll have
to keep.
</FaqItem>

<FaqItem q="Should every field have a setter?">
No. Only state that can legitimately change on its own gets a setter, and the setter validates. IDs, creation times and
anything derived from other fields get none; related fields change together through one method.
</FaqItem>

<FaqItem q="Are records encapsulated?">
They don't hide their components, which are all readable. But they're immutable, their compact constructor can enforce
invariants, and their representation is their API by design. That's the right trade-off for data carriers; for objects
with behaviour and hidden state, use a class.
</FaqItem>

<FaqItem q="Should a getter return a copy or a read-only view?">
A view is cheaper and always up to date; a copy is a stable snapshot that later changes won't affect. Choose by what
callers need, and document it. Immutable collections need neither.
</FaqItem>

<FaqItem q="How do frameworks like JPA and Jackson work with private fields?">
Through reflection, either on the fields directly or through JavaBeans getters and setters, depending on
configuration. Jackson can also use constructors and records. Some frameworks need a no-argument constructor
([Constructors](/lessons/constructors-basics/)), which you can make protected.
</FaqItem>

<FaqItem q="Is protected access part of encapsulation?">
It opens the class to subclasses, which then depend on its internals; a change can break subclasses you've never seen.
Treat protected members as part of your public API ([Inheritance](/lessons/inheritance/)).
</FaqItem>

<FaqItem q="Is Lombok's @Data a good idea?">
For simple data carriers it saves typing, though records do the same job in plain Java. For domain objects it generates
a setter for every field, which is exactly the anti-pattern this lesson is about.
</FaqItem>

<FaqItem q="Can encapsulation hurt performance?">
The method calls don't, because they're inlined. Defensive copies allocate memory, which matters only in hot code;
immutable types avoid the copies altogether.
</FaqItem>

## Pitfalls and best practices

| ✅ Do | ❌ Don't |
|---|---|
| Name methods after what the object does (`withdraw`, `ship`) | Generate a setter for every field |
| Validate and normalise in constructors and methods | Accept any value and hope callers are careful |
| Change related fields in one method; check before assigning | Leave the object invalid when a check fails halfway |
| Copy mutable inputs, then validate the copy | Store the caller's array, list or `Date` |
| Return immutable values, copies or read-only views | Return internal mutable objects |
| Keep implementation classes package-private | Make everything public "just in case" |

## Senior lens

<Callout type="senior" title="Explain it to your team in 60 seconds">
"Private fields are the tool; protected rules are the point. Each class owns its invariants: the constructor sets them
up, every public method keeps them, and nothing mutable leaks in or out. So we expose behaviour, not setters, we copy
or freeze what crosses the boundary, and we keep fields we don't need to expose out of the API, because whatever
callers can see, we can never change."
</Callout>

**Where it goes wrong in production**

| Symptom | Cause | Fix |
|---|---|---|
| The same validation repeated (and missing) in many services | Setters instead of behaviour methods | Move the rule into the object |
| Objects in states that "can't happen" | Independent setters for related fields | One method per meaningful change |
| Data changes nobody can trace | A getter returned an internal collection | Read-only views or copies |
| A library upgrade breaks callers | Internal types or fields exposed | Hide representation; return interfaces or values |
| Secrets in logs and heap dumps | Assuming `private` means secure | Keep secrets out of logged objects |

Encapsulation is also about teams: a class with a small, behaviour-shaped API can be owned and changed by one team
without coordinating every change with everyone who calls it. Wide APIs of getters and setters spread the
responsibility for the rules across the whole codebase.

**Code-review checklist**
- [ ] Every field is private; setters exist only for state that may change on its own, and they validate.
- [ ] Related fields change together, and methods check before they assign.
- [ ] No getter returns a mutable internal object; constructors copy mutable arguments before validating.
- [ ] Public types and methods are the minimum callers need.
- [ ] Domain objects aren't generated with setters for everything.

```java title="Inventory.java (solution)"
package track.encapsulation;

import java.util.Collections;
import java.util.HashMap;
import java.util.Map;
import java.util.TreeMap;

/** Reference solution for the Inventory exercise. */
public final class Inventory {
    /** Per SKU: [0] units on hand, [1] units reserved. Invariant: 0 <= reserved <= onHand. Never leaves this class. */
    private final Map<String, int[]> stock = new HashMap<>();

    public void receive(String sku, int quantity) {
        check(sku, quantity);
        int[] s = stock.get(sku);
        int onHand = Math.addExact(s == null ? 0 : s[0], quantity);   // may throw: nothing has changed yet
        if (s == null) {
            s = new int[2];
            stock.put(sku, s);
        }
        s[0] = onHand;
    }

    public void reserve(String sku, int quantity) {
        check(sku, quantity);
        int[] s = stock.get(sku);
        if (s == null || quantity > s[0] - s[1]) {
            throw new IllegalStateException("only " + available(sku) + " of " + sku + " available");
        }
        s[1] += quantity;
    }

    public void release(String sku, int quantity) {
        int[] s = reservedAtLeast(sku, quantity);
        s[1] -= quantity;
    }

    public void ship(String sku, int quantity) {
        int[] s = reservedAtLeast(sku, quantity);
        s[0] -= quantity;
        s[1] -= quantity;
    }

    public int onHand(String sku) {
        return numbers(sku)[0];
    }

    public int reserved(String sku) {
        return numbers(sku)[1];
    }

    public int available(String sku) {
        int[] s = numbers(sku);
        return s[0] - s[1];
    }

    public Map<String, Integer> snapshot() {
        Map<String, Integer> copy = new TreeMap<>();
        for (Map.Entry<String, int[]> e : stock.entrySet()) {
            if (e.getValue()[0] > 0) {
                copy.put(e.getKey(), e.getValue()[0] - e.getValue()[1]);
            }
        }
        return Collections.unmodifiableMap(copy);
    }

    private int[] reservedAtLeast(String sku, int quantity) {
        check(sku, quantity);
        int[] s = stock.get(sku);
        if (s == null || quantity > s[1]) {
            throw new IllegalStateException("only " + reserved(sku) + " of " + sku + " reserved");
        }
        return s;
    }

    private int[] numbers(String sku) {
        checkSku(sku);
        int[] s = stock.get(sku);
        return s == null ? new int[2] : s;
    }

    private static void check(String sku, int quantity) {
        checkSku(sku);
        if (quantity <= 0) {
            throw new IllegalArgumentException("quantity must be > 0: " + quantity);
        }
    }

    private static void checkSku(String sku) {
        if (sku.isBlank()) {                                       // NullPointerException for null
            throw new IllegalArgumentException("blank SKU");
        }
    }
}
```

```java title="Editor.java (solution)"
package track.encapsulation;

import java.util.Objects;

/** Reference solution for the Editor part of the Editor exercise. */
public final class Editor {

    /** A saved state: only Editor can create one or look inside. */
    public static final class Snapshot {
        private final Editor owner;
        private final String text;
        private final int cursor;

        private Snapshot(Editor owner, String text, int cursor) {
            this.owner = owner;
            this.text = text;
            this.cursor = cursor;
        }
    }

    private final StringBuilder text = new StringBuilder();
    private int cursor;                                  // invariant: 0 <= cursor <= text.length()

    public void type(String s) {
        text.insert(cursor, Objects.requireNonNull(s, "s"));   // insert(int, String) would add "null" for null
        cursor += s.length();
    }

    public void backspace(int n) {
        if (n < 0) {
            throw new IllegalArgumentException("negative count: " + n);
        }
        int from = Math.max(0, cursor - n);
        text.delete(from, cursor);
        cursor = from;
    }

    public void moveCursor(int position) {
        if (position < 0 || position > text.length()) {
            throw new IllegalArgumentException("cursor outside the text: " + position);
        }
        cursor = position;
    }

    public String text() {
        return text.toString();
    }

    public int cursor() {
        return cursor;
    }

    public Snapshot save() {
        return new Snapshot(this, text.toString(), cursor);
    }

    public void restore(Snapshot snapshot) {
        if (snapshot.owner != this) {                    // NullPointerException for null
            throw new IllegalArgumentException("a snapshot of another editor");
        }
        text.setLength(0);
        text.append(snapshot.text);
        cursor = snapshot.cursor;
    }
}
```

```java title="History.java (solution)"
package track.encapsulation;

import java.util.ArrayDeque;
import java.util.Deque;
import java.util.Objects;

/** Reference solution for the History part of the Editor exercise. */
public final class History {
    private final Editor editor;
    private final int limit;
    private final Deque<Editor.Snapshot> undo = new ArrayDeque<>();
    private final Deque<Editor.Snapshot> redo = new ArrayDeque<>();

    public History(Editor editor, int limit) {
        if (limit < 1) {
            throw new IllegalArgumentException("limit must be at least 1: " + limit);
        }
        this.editor = Objects.requireNonNull(editor);
        this.limit = limit;
    }

    public void checkpoint() {
        push(undo, editor.save());
        redo.clear();
    }

    public boolean undo() {
        if (undo.isEmpty()) {
            return false;
        }
        push(redo, editor.save());
        editor.restore(undo.pop());
        return true;
    }

    public boolean redo() {
        if (redo.isEmpty()) {
            return false;
        }
        push(undo, editor.save());
        editor.restore(redo.pop());
        return true;
    }

    public int undoDepth() {
        return undo.size();
    }

    public int redoDepth() {
        return redo.size();
    }

    private void push(Deque<Editor.Snapshot> stack, Editor.Snapshot snapshot) {
        stack.push(snapshot);
        if (stack.size() > limit) {
            stack.removeLast();                          // drop the oldest
        }
    }
}
```

## Cheat sheet

<CheatSheet>

| Topic | Remember |
|---|---|
| **Encapsulation** | Data + the code that keeps it valid, behind a boundary; hiding is the technique |
| **Getters/setters** | Not encapsulation by themselves; add only what callers need; setters validate |
| **Invariants** | Constructors establish, every public method preserves; check before assigning |
| **Related fields** | Change together in one method (`moveTo(lo, hi)`), never through separate setters |
| **Behaviour** | `withdraw`, `ship`, `changeEmail` instead of `setBalance`, `setShipped`, `setEmail` |
| **Leaks** | Copy mutable inputs (before validating); return copies, views or immutables |
| **View vs copy** | `unmodifiableList`: read-only, live. `List.copyOf`: snapshot, rejects nulls |
| **Representation** | Hidden fields can change freely (String: `char[]` → `byte[]` in Java 9) |
| **Levels** | private members, package-private classes, module exports, interfaces |
| **Security** | `private` ≠ secure: reflection, serialization, dumps |

</CheatSheet>
