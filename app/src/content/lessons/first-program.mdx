## Why this matters

For almost thirty years, Java's first program forced beginners to type `public`, `class`, `static`, `void` and
`String[]` before they had learned what any of them meant. Experienced developers, meanwhile, kept writing fragile
shell scripts because "a Java program needs a project and a build". Both habits are out of date. Since Java 11 you can
run a source file directly, since Java 22 a program spread over several files, and since **Java 25** a complete
program can be three lines. This lesson shows every way to run Java, what each piece of the classic `main` means, and
how to read the errors you'll see first.

## TL;DR

<Callout type="tldr">
- Install a **JDK 25** (any vendor), then check `java --version` and `javac --version`.
- Classic path: `javac Hello.java` writes `Hello.class`; `java Hello` runs it. You pass a **class name** to `java`,
  not a file name.
- **Source-file mode:** `java Hello.java` compiles in memory and runs, with no `.class` file (Java 11; several files
  since Java 22).
- **jshell** (Java 9) runs snippets interactively: the fastest way to try an expression.
- **Java 25 (JEP 512):** a file can be just `void main() { IO.println("Hello"); }`. The class is implicit, `main` needs
  no `public static` and no parameters, and the whole `java.base` module is imported.
- `public static void main(String[] args)` still works everywhere and is what you'll read in most code.
</Callout>

## Mental model

Java code goes through two stages: **compile** (source → bytecode) and **run** (bytecode → JVM). The three ways to run
a program differ only in *where the compiled bytecode goes*: to a file on disk, into memory for one run, or into a
long-lived interactive session.

<RunPaths />

Where the analogy of "script vs program" breaks: even in source-file mode and jshell, the code **is** compiled by the
real `javac` compiler first. Java never interprets source code line by line; errors are compile errors, found before
anything runs.

## Concept, step by step

### 1. Install a JDK

1. Download a **JDK 25** from a vendor (Eclipse Temurin, Amazon Corretto, Azul Zulu, Oracle, Microsoft…), or use a
   package manager: SDKMAN! (`sdk install java 25-tem`) on macOS and Linux, `winget` on Windows, Homebrew on macOS.
2. Make sure the JDK's `bin` folder is on your `PATH`, and set `JAVA_HOME` to the JDK folder (most installers do both;
   build tools such as Maven read `JAVA_HOME`).
3. Check both tools. They must report the same version:

```shellsession captured="JDK 25.0.4.1 (Ubuntu build, Linux x64)"
$ java --version
openjdk 25.0.4.1 2026-08-18
OpenJDK Runtime Environment (build 25.0.4.1+1-1-24.04.4-Ubuntu)
OpenJDK 64-Bit Server VM (build 25.0.4.1+1-1-24.04.4-Ubuntu, mixed mode, sharing)
```

If `javac` is "not found" while `java` works, you have only a runtime on your `PATH`, not a JDK
([JDK, JRE & JVM](/lessons/jdk-jre-jvm/) explains the difference). Any editor works; an IDE such as IntelliJ IDEA,
Eclipse or VS Code with the Java extensions adds completion and one-click running.

### 2. The classic program, word by word

```java title="Hello.java"
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, World!");
    }
}
```

| Piece | Meaning |
|---|---|
| `public class Hello` | Declares a class named `Hello`. A **public** class must live in a file with the same name: `Hello.java`. |
| `{ … }` | Braces group the class body and the method body. |
| `public` | The method can be called from anywhere, including by the launcher. |
| `static` | It belongs to the class, so the launcher can call it without creating an object first. |
| `void` | It returns nothing. (To report failure, a program calls `System.exit(1)`.) |
| `main` | The name the launcher looks for. |
| `String[] args` | The command-line arguments, as an array of strings: `java Hello a b` gives `args = {"a", "b"}`. |
| `System.out.println("…")` | `System` is a class in `java.lang`; `out` is its standard-output stream; `println` prints a line. |
| `;` | Every statement ends with a semicolon. |

Java is **case-sensitive**: `System`, `String` and `Hello` are not the same as `system`, `string` or `hello`.

Compile and run:

```shellsession title="Terminal"
$ javac Hello.java
$ java Hello
Hello, World!
```

`javac` created `Hello.class` next to the source file. `java Hello` then starts a JVM, loads the class named `Hello`
from the current directory (the default class path) and calls its `main` method.

**With a package.** Real code lives in packages, and the folder structure mirrors the package name:

```java title="src/greetings/Hello.java"
package greetings;

public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello from a package");
    }
}
```

```shellsession title="Terminal"
$ javac -d out src/greetings/Hello.java
$ java -cp out greetings.Hello
Hello from a package
```

`-d out` tells `javac` where to write class files (it creates `out/greetings/Hello.class`). `-cp out` tells `java`
where to look, and the class is named by its **fully qualified name**, `greetings.Hello`. Build tools such as Maven and
Gradle do all of this for you; knowing it helps when something goes wrong.

### 3. Source-file mode: run a `.java` file directly

```shellsession title="Terminal"
$ java Hello.java
Hello, World!
```

Since **Java 11** (JEP 330) the launcher accepts a source file. It compiles the file **in memory** with the real
compiler and runs the first class declared in it. No `.class` file is written, so there's nothing to clean up.

- Since **Java 22** (JEP 458), the program may use other classes in other `.java` files in the same directory tree;
  the launcher compiles them on demand. Small multi-file tools no longer need a build tool.
- Arguments after the file name go to `main`: `java Hello.java Ada` gives `args = {"Ada"}`.
- On Linux and macOS, a file can even start with a "shebang" line and run as a script:
  `#!/usr/bin/env -S java --source 25`. Give such a file a name without `.java` (for example `largest`) and make it
  executable; `--source` tells the launcher to treat it as Java source anyway.

### 4. jshell: try things instantly

`jshell` (Java 9, JEP 222) is a REPL: it reads a snippet, compiles and runs it, prints the result and waits for the next
one. You don't need a class, a `main` method or even semicolons at the end of a line:

```text title="jshell session (example)"
jshell> 1 + 2
$1 ==> 3

jshell> int x = 42
x ==> 42

jshell> "Java " + x
$3 ==> "Java 42"

jshell> /exit
```

Useful commands: `/vars` (your variables), `/methods`, `/list` (everything you typed), `/open File.java` (load a file),
`/help`. jshell imports common packages such as `java.util` and `java.util.stream` for you. Use it to check a
detail of the language in seconds, for example what `7 / 2` gives.

### 5. Java 25: compact source files and instance `main`

**JEP 512**, final in Java 25, removes the ceremony for small programs:

```java title="Hello.java (Java 25)"
void main() {
    IO.println("Hello, World!");
}
```

That is the whole file. Three things make it work:

1. **An implicit class.** A file with methods or fields outside any class declaration is a *compact source file*. The
   compiler wraps its members in a class named after the file (`Hello`). You can't refer to that class by name from
   other code: it's meant for small programs.
2. **Instance main methods.** `main` may be non-`static`, non-`public` (anything but `private`) and may drop the
   `String[] args` parameter. If `main` is an instance method, the launcher creates an object of the class first.
3. **Implicit imports.** A compact source file automatically imports every public class of the packages that the
   `java.base` module exports: `List`, `Map`, `ArrayList`, `Path` and friends work without `import` lines. And the new
   class **`java.lang.IO`** gives simple console input and output: `IO.println`, `IO.print` and `IO.readln`.

```java title="Greet.java (Java 25)"
void main() {
    String name = IO.readln("What's your name? ");
    List<String> letters = List.of(name.split(""));
    IO.println("Hello, " + name + "! Your name has " + letters.size() + " letters.");
}
```

A compact source file grows naturally into a normal one: when the program gets bigger, wrap it in
`class Greet { … }`, add the imports, and nothing else changes.

### 6. The first errors you'll meet

| You see | Cause | Fix |
|---|---|---|
| `javac: command not found` (or "not recognized" on Windows) | No JDK on your `PATH`, or only a runtime | Install a JDK; put its `bin` on `PATH` |
| `error: class Hello is public, should be declared in a file named Hello.java` | File name and public class name differ | Rename the file or the class, respecting case |
| `error: ';' expected` | A statement without a semicolon | Add the `;` on the line the compiler points to (or the line before) |
| `error: cannot find symbol` | A misspelt name (`System.out.prinln`), wrong case, or a missing import | Check spelling and case; add the `import` |
| `Error: Could not find or load main class Hello.class` | You passed a **file name** to `java` in class mode | Run `java Hello`, not `java Hello.class` |
| `Error: Could not find or load main class Hello` | Wrong directory, wrong class path, or a class in a package run by its short name | `cd` to the right folder, pass `-cp`, and use the full name `greetings.Hello` |
| `UnsupportedClassVersionError` | Compiled with a newer JDK than the one running it | Run on the newer JDK, or compile with `--release N` ([JDK, JRE & JVM](/lessons/jdk-jre-jvm/#6-class-file-versions-forward-compatible-only)) |

Read compiler errors from the **first** one: later errors are often consequences of it.

## Scenarios

<Tabs>
<TabItem label="Real world: a one-file tool">

A developer needs to find the largest files in a folder. Instead of a shell script, one Java 25 file:

```java title="Largest.java (Java 25)"
void main(String[] args) throws IOException {
    Path dir = Path.of(args.length > 0 ? args[0] : ".");
    try (Stream<Path> files = Files.walk(dir)) {
        files.filter(Files::isRegularFile)
             .sorted(Comparator.comparingLong(this::size).reversed())
             .limit(5)
             .forEach(p -> IO.println(size(p) + "\t" + p));
    }
}

long size(Path p) {
    try {
        return Files.size(p);
    } catch (IOException e) {
        return 0;
    }
}
```

Run it with `java Largest.java ~/Downloads`. `Path`, `Files`, `Stream`, `Comparator` and `IOException` need no
imports because a compact source file imports all of `java.base`. The helper `size` is an ordinary instance method of
the implicit class, which is why `this::size` works. (Streams and lambdas come later in the track; here they just
show that a "script" can use the full language.)

</TabItem>
<TabItem label="Real world: several files, no build tool">

Since Java 22 the launcher compiles the other source files a program needs:

```java title="Main.java"
public class Main {
    public static void main(String[] args) {
        System.out.println(Greeter.greet("team"));
    }
}
```

```java title="Greeter.java"
public class Greeter {
    static String greet(String who) {
        return "Hello, " + who + "!";
    }
}
```

```shellsession title="Terminal (Java 22+)"
$ java Main.java
Hello, team!
```

`Main.java` refers to `Greeter`; the launcher finds `Greeter.java` in the same directory and compiles it too. On Java
11 to 21 the same command fails with a "cannot find symbol" error, because source-file mode compiled only one file.

</TabItem>
<TabItem label="Edge case: which main wins?">

```java title="TwoMains.java"
public class TwoMains {
    public static void main(String[] args) {
        System.out.println("static main with args");
    }

    void main() {
        System.out.println("instance main without args");
    }
}
```

Both methods are legal in Java 25, because they have different parameter lists (they are *overloads*). The launcher
prefers the one with a `String[]` parameter, so `java TwoMains.java` prints `static main with args`. Having two
`main` methods is legal but confusing: don't do it in real code.

</TabItem>
<TabItem label="Anti-pattern → fix: everything in the default package">

```text title="Anti-pattern: classes without a package, run from anywhere"
project/
  Hello.java        // no package line
  Util.java
$ javac *.java      // .class files mixed with sources
$ cd .. && java Hello
Error: Could not find or load main class Hello
```

Classes without a `package` line live in the *unnamed package*. They can't be imported by code in named packages, and
running them depends on the current directory.

```text title="Fix: a package, sources and classes apart"
project/
  src/app/Hello.java     // package app;
  src/app/Util.java      // package app;
$ javac -d out src/app/*.java
$ java -cp out app.Hello
```

Better still, let Maven or Gradle manage the layout (`src/main/java/app/Hello.java`) once a program has more than a
couple of files. Compact source files are fine for scripts and experiments, and they can't be in a package anyway.

</TabItem>
</Tabs>

## Under the hood

<details>
<summary>What <code>java</code> does with a class name, a source file, and <code>main</code></summary>

- **Class mode** (`java Hello`): the launcher starts the JVM, which asks the *application class loader* to find
  `Hello.class` on the class path (`-cp`, the `CLASSPATH` variable, or the current directory by default). It loads,
  links and verifies the class, then looks for `main`.
- **Source-file mode** (`java Hello.java`): the launcher notices the `.java` suffix, calls the compiler through its
  Java API (the `jdk.compiler` module), keeps the resulting bytecode in memory, and loads it with a special in-memory
  class loader. That's why a runtime without `jdk.compiler` (for example a `jlink` image with only `java.base`)
  can run class files but not source files.
- **Choosing `main`** follows the protocol in the diagram above. For an instance `main`, the launcher calls the class's
  non-private no-argument constructor, then calls `main` on that object.
- **Exit code:** when `main` returns and no other (non-daemon) threads are running, the JVM exits with status 0. An
  uncaught exception prints a stack trace and exits with status 1. `System.exit(n)` ends the JVM with status `n`.
- **Compact source files** compile to an ordinary, `final` class in the unnamed package; `javap` shows it like any
  other class ([How Java Runs](/lessons/how-java-runs/) introduces `javap`).

</details>

## Myths vs facts

<MythVsFact myth="Every Java program must declare a class with public static void main(String[] args)." audit="2.11">
That was true until Java 24. Since **Java 25** (JEP 512) a compact source file can contain just `void main() { … }`:
the class is implicit, and `main` can be an instance method, non-public and without parameters. The classic form still
works and remains the standard in libraries and frameworks.
</MythVsFact>

<MythVsFact myth="Java programs always need a separate compile step and a build tool.">
`java Hello.java` compiles and runs a file in one step (Java 11), and since Java 22 it compiles the other source files
the program uses. Build tools are for dependencies, tests and packaging, not for running a few files.
</MythVsFact>

<MythVsFact myth="In source-file mode, Java interprets the source code line by line.">
The launcher runs the real `javac` compiler first, in memory, and then runs bytecode on the JVM. A syntax error anywhere
in the file stops the program before its first line runs.
</MythVsFact>

<MythVsFact myth="You run a compiled program with java Hello.class.">
`java` takes a **class name** in class mode: `java Hello`. With a `.class` suffix it looks for a class literally named
`Hello.class` and fails with "Could not find or load main class".
</MythVsFact>

## Doubts cleared

<FaqItem q="Why must the file name match the class name?">
Only a **public** top-level class must be in a file of the same name. It lets the compiler and tools find a class's
source from its name. A file may contain several top-level classes, but at most one public one.
</FaqItem>

<FaqItem q="What is `args` if I pass no arguments?">
An empty array (`args.length == 0`), never `null`. So `args[0]` throws `ArrayIndexOutOfBoundsException` if you don't
check the length first.
</FaqItem>

<FaqItem q="Can `main` return an int, like in C?">
No: `main` must return `void`. To give the operating system an exit code, call `System.exit(code)`. Returning
normally means exit code 0 (once no other non-daemon threads are running).
</FaqItem>

<FaqItem q="What's the difference between `System.out.println` and `IO.println`?">
`IO.println` (Java 25, `java.lang.IO`) is a short, beginner-friendly way to print to the console; `IO.readln` reads a
line. `System.out.println` is the classic way, available in every version, and `System.out` is a `PrintStream` with
many more methods (`printf`, `print`, `flush`…). In production code you'd usually use a logging library instead of
either.
</FaqItem>

<FaqItem q="Can a compact source file have more than one method, or fields?">
Yes. Everything declared at the top level of the file (methods and fields) becomes a member of the implicit class, so
`main` can call your other methods and use your fields. What it can't have is a `package` declaration, and other
classes can't refer to it by name.
</FaqItem>

<FaqItem q="Does `java Hello.java` leave a `Hello.class` file behind?">
No. The bytecode lives only in memory for that run, so every run compiles again. For a program you run very often, or
that is large, compile once with `javac` (or a build tool) instead.
</FaqItem>

<FaqItem q="Can I use preview features in source-file mode?">
Yes, but you must say which Java version the source is for: `java --enable-preview --source 25 Hello.java`. The same
two options are needed with `javac`, plus `--enable-preview` again when running the compiled class.
</FaqItem>

<FaqItem q="Is jshell only for beginners?">
No. It's handy for anyone checking an API, a regular expression, a date calculation or a language rule without
creating a project. You can also load your classes into it with `--class-path`.
</FaqItem>

<FaqItem q="Which IDE should I use?">
Any of IntelliJ IDEA, Eclipse or VS Code with the Java extensions. What matters is that the IDE uses the same JDK version
as your command line and build (check the project SDK setting); many "it works in the IDE but not in the terminal"
problems are two different JDKs.
</FaqItem>

## Pitfalls and best practices

| ✅ Do | ❌ Don't |
|---|---|
| Check `java --version` and `javac --version` match | Assume the `java` on your `PATH` is the JDK you installed |
| Run a single file with `java File.java` while learning | Create a build-tool project for a five-line experiment |
| Use `jshell` to check a rule in seconds | Guess what an expression does |
| Put real code in packages; compile with `-d out`, run with `-cp out pkg.Main` | Leave classes in the unnamed package and run them from "the right folder" |
| Read the first compiler error first | Fix errors from the bottom of the list up |
| Check `args.length` before reading arguments | Read `args[0]` blindly |
| Use `System.exit(nonZero)` to signal failure from a tool | Print "error" and exit with status 0, so scripts think it worked |

## Senior lens

<Callout type="senior" title="Explain it to your team in 60 seconds">
"You don't need a project to run Java any more. `java Tool.java` compiles and runs a file, and since Java 22 it pulls
in the other source files it needs. Since Java 25, a file can be just a `void main()` with no imports for anything in
`java.base`. So for small internal tools we can use Java instead of Bash, with types, a debugger and our existing
libraries' knowledge. For anything that needs dependencies, tests or packaging, we still use the build tool."
</Callout>

**When is a single-file Java program the right tool?**

| Situation | Good fit? | Why |
|---|---|---|
| Ops script that parses files, calls HTTP APIs, transforms JSON | ✅ Java 25 file | `java.net.http`, `java.nio.file`, records; typed and debuggable |
| Reproducing a bug in a tiny test case | ✅ single file or jshell | Easy to share and run anywhere with a JDK |
| Tool that needs third-party libraries | ⚠️ | Source mode has no dependency management: use `-cp` with JARs or a build tool |
| Performance-critical CLI run thousands of times | ❌ source mode | It compiles on every run; package a compiled JAR (or a native image) |
| Team service | ❌ | Needs a build, tests, CI and packaging |

**Onboarding:** a new developer's first hour should be "install one JDK, run `java --version`, run a file". Put the
exact JDK version and install command in the README, and make the build check it (Maven Enforcer or Gradle
toolchains), so the "wrong Java" class of problems never reaches code review.

**Code-review checklist**
- [ ] Programs signal failure with a non-zero exit code.
- [ ] No compact source files (or multiple `main` methods) in production modules.
- [ ] The README states the JDK version and how to run the program.
- [ ] Scripts that run often are compiled, not recompiled from source on every run.

```java title="CommandLine.java (solution)"
package track.first_program;

import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

/** Reference solution for the CommandLine exercise. */
public final class CommandLine {

    public record Parsed(Map<String, String> options, List<String> positional) {
    }

    private CommandLine() {
    }

    public static Parsed parse(String[] args) {
        Map<String, String> options = new LinkedHashMap<>();   // keeps the order given
        List<String> positional = new ArrayList<>();
        boolean onlyPositional = false;
        for (String arg : args) {
            if (onlyPositional || !arg.startsWith("--")) {
                positional.add(arg);
            } else if (arg.equals("--")) {
                onlyPositional = true;
            } else {
                String body = arg.substring(2);
                int eq = body.indexOf('=');
                String key = eq < 0 ? body : body.substring(0, eq);
                String value = eq < 0 ? "true" : body.substring(eq + 1);
                if (key.isEmpty()) {
                    throw new IllegalArgumentException("Empty option name: " + arg);
                }
                if (options.put(key, value) != null) {
                    throw new IllegalArgumentException("Option given twice: " + key);
                }
            }
        }
        return new Parsed(options, positional);
    }
}
```

```java title="MainFinder.java (solution)"
package track.first_program;

import java.lang.reflect.Constructor;
import java.lang.reflect.Method;
import java.lang.reflect.Modifier;

/** Reference solution for the MainFinder exercise. */
public final class MainFinder {

    private MainFinder() {
    }

    public static String chosenMain(Class<?> type) {
        Method withArgs = candidate(type, String[].class);
        Method chosen = withArgs != null ? withArgs : candidate(type);
        if (chosen == null) {
            throw new IllegalArgumentException("No non-private main method in " + type.getName());
        }
        boolean isStatic = Modifier.isStatic(chosen.getModifiers());
        if (!isStatic && !hasUsableConstructor(type)) {
            throw new IllegalArgumentException("Instance main needs a non-private no-arg constructor: " + type.getName());
        }
        String params = chosen.getParameterCount() == 1 ? "String[]" : "";
        return (isStatic ? "static" : "instance") + " main(" + params + ")";
    }

    /** The declared, non-private main method with these parameter types, or null. */
    private static Method candidate(Class<?> type, Class<?>... parameterTypes) {
        try {
            Method m = type.getDeclaredMethod("main", parameterTypes);
            return Modifier.isPrivate(m.getModifiers()) ? null : m;
        } catch (NoSuchMethodException e) {
            return null;
        }
    }

    private static boolean hasUsableConstructor(Class<?> type) {
        try {
            Constructor<?> c = type.getDeclaredConstructor();
            return !Modifier.isPrivate(c.getModifiers());
        } catch (NoSuchMethodException e) {
            return false;
        }
    }
}
```
